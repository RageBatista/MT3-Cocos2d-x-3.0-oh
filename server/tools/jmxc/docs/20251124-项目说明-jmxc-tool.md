# jmxc 工具项目说明（jmxc Tool Project Overview）

## 1. 项目定位与使用场景
- **用途**：jmxc 是一个基于 JMX 的远程管理与运维 CLI，面向 MT3 服务器集群，用于执行关服、心跳、在线人数查询、GM 指令、缓存刷新等日常维护动作。
- **运行方式**：通过 `java jmxc <username> <password> <ip> <port> <function> [args...]` 直接调用 `jmxc` 主类；凭据与网络信息在命令行传入，工具内部拼接 `service:jmx:rmi://.../jndi/rmi://.../jmxrmi` 形式的服务 URL。
- **超时容错**：所有远程调用都封装了连接和调用超时，防止卡住运维脚本；心跳与在线人数查询在失败时会输出 `0` 供外层脚本判断。

## 2. 目录与构建要点
| 路径 | 说明 |
| --- | --- |
| `src/jmxc.java` | 核心命令行入口与全部业务逻辑。 |
| `src/ConnectTask.java` | 早期的连接辅助线程实现，目前未被引用，可用于后续扩展并发连接。 |
| `src/com/jmxservice/mt3interfaces/GameOnlineNumBean.java` | 远程 MBean `getOnlineNum` 的数据传输对象，包含 0~150 档在线人数区间。 |
| `src/com/jmxservice/mt3interfaces/LogInfo.java` | 远程调用统一的审计上下文（操作者、原因等）。 |
| `build.xml` / `build.bat` / `build.sh` | Ant 构建脚本与跨平台包装；`jmxc-new.jar` 为最近打包产物。 |

构建建议：
1. 使用已存在的 `build.bat`（Windows）或 `build.sh`（类 Unix）来调用 Ant；无需额外依赖安装。
2. 生成的可执行 Jar 默认输出到仓库根目录，可替换旧版 `jmxc.jar`。

## 3. 关键功能与命令映射
`jmxc` 主函数允许的 `function` 参数与内部方法映射如下，均位于 `jmxc.java`：

| function | 方法 | 描述 | 返回/输出 |
| --- | --- | --- | --- |
| `shutdownGs [waitSec]` | `shutdownGs(Integer)` | 告知游戏服延时停服，默认 300 秒。 | 无输出，异常即 CLI 退出。 |
| `shutdownUn` | `shutdownUn()` | 通知 UN 进程停止。 | 成功无输出，异常静默吞掉。 |
| `shutdownAuany` | `shutdownAuany()` | 停止 Auany 服务。 | 同上。 |
| `keepAlive` | `keepAlive()` | 调用 `IWEB:type=GameControl` 的心跳；成功打印 `1`，失败打印 `0`。 |
| `GetMaxOnlineNum` | `GetMaxOnlineNum()` | 查询当前在线人数与档位，成功打印 `GameOnlineNumBean.curronlinenum`。 |
| `getUserNumInQueue` | `getUserNumInQueue()` | 获取排队人数。 |
| `reload` | `reload()` | 触发 `IWEB:type=Reload`，常用于配置热加载。 |
| `refreshRankList` | `refreshRankList()` | 排行榜重算。 |
| `doExpState` | `doExpState()` | 执行经验状态同步。 |
| `getCacheInfo` | `getCacheInfo()` | 输出缓存状态字符串。 |
| `bindMacToLahu` | `bindMacToLahu()` | 执行 MAC 绑定动作，结果直接打印。 |
| `gm ...` | `execGM(String[] args)` | 解析额外的 `userId=`, `roleId=` 与 GM 指令文本，多行指令以 `\n` 连接。 |

## 4. 关键类与实现细节
### 4.1 `jmxc`
- **连接启动**：构造函数创建 `jmx.remote.credentials` 属性并调用 `connectWithTimeout`，默认超时 `7000ms`（`TimeUnit.MILLISECONDS`）。
- **线程池策略**：静态内部类 `DaemonThreadFactory` 将线程标记为 daemon，确保 CLI 退出时不被阻塞。
- **统一远程调用**：`invokeWithTimeout` 使用单线程执行器 + `Future#get(timeout)` 实现调用级别的超时，异常时会打印堆栈并返回 `null`，调用方需判空。
- **异常语义**：对 `keepAlive` / `GetMaxOnlineNum` 等查询型命令，失败时输出 sentinel（`0` 或 `-1`）；对关服类命令则直接吞掉 JMX 层抛出的 `UnmarshalException` 或 `ConnectException`，以避免重复报警。
- **GM 指令组装**：`execGM` 会把命令行第 6 个参数起的文本拼接成脚本体，并解析可选的 `userId` / `roleId` 键值对，随后调用 `gs.counter:type=GMProcMXBeant` 执行。

### 4.2 `GameOnlineNumBean`
- 17 个 `Integer` 字段分别对应当前在线人数与 0~150 之间的区间统计。
- 提供 `dump(PrintStream)` 和 `toString()`，便于调试输出。
- 采用固定序列化 UID（`7625085084251392283L`），与服务器端 MBean 的版本保持兼容。

### 4.3 `LogInfo`
- 封装审计上下文（操作者 ID、名称、原因），多数远程调用在构造 `LogInfo(-1, "jmxc", "...")` 后传给服务器，方便后端记录调用来源。

### 4.4 `ConnectTask`
- 继承自 `Thread`，封装 `JMXConnectorFactory.connect`；虽然当前未使用，但展示了早期的连接异步化方案，可在未来扩展批量连接或重试逻辑时复用。

## 5. 远程交互流程
1. **鉴权**：使用命令行用户名/密码填充 `jmx.remote.credentials`。
2. **地址拼装**：`ip` + `port` 构建 RMI URL，实际 JMX 服务端口为 `port + 2687`。
3. **连接超时控制**：`connectWithTimeout` 在 7 秒内轮询连接结果；失败会抛出 `SocketTimeoutException` 或透传原始异常。
4. **功能调度**：根据 `function` 字符串分派，部分命令允许额外参数。
5. **输出规范**：所有命令都以标准输出返回；适合被 Shell/批处理脚本解析。

## 6. 运行前置条件与限制
- 需要目标服务器开放对应 RMI/JMX 端口，且账号具备调用相关 MBean 的权限。
- 工具未内置 SSL/JMXMP 等高级协议支持，如需安全通道需借助外部隧道（VPN/SSH）。
- 没有参数校验与国际化，错误输入将直接触发异常或 `function not found!`。
- `ConnectTask` 未启用，当前所有操作均串行执行，无法同时管理多个节点。

## 7. 推荐的运维脚本模式
1. 将 `jmxc-new.jar` 加入现有自动化工具链，通过批处理或 PowerShell 调用。
2. 在外围脚本中解析返回码（`0` / `1` / `-1`）并按需重试。
3. 对 GM 指令，预先在文本文件中整理命令片段，通过 PowerShell 管道注入，避免长行命令易错。

## 8. 可扩展方向
- **多节点巡检**：复用或改造 `ConnectTask`，实现并行 keepAlive/统计。
- **命令注册表**：用枚举或 Map 维护 function->handler，便于增加新指令。
- **配置文件支持**：允许从 `yaml/json` 读取连接信息，避免凭据明文写在命令行。
- **日志记录**：增加本地日志，记录调用耗时与失败原因，方便审计。

## 9. 快速校验清单
- 运行 `java jmxc <user> <pwd> <ip> <port> keepAlive` 应在目标存活时输出 `1`。
- 断开网络后再执行 `keepAlive`，应在 7 秒内返回 `0`。
- 指定不存在的 `function` 会立即输出 `function not found!` 并退出。
- `gm` 命令至少需要 `userId=`、`roleId=` 与一条 GM 文本，否则远端可能返回 `-1`。

## 10. 功能优化升级方案
### 10.1 目标与原则
- **可观测性**：为关键操作增加本地日志与执行结果统计，便于审计与回溯。
- **可维护性**：采用命令注册表、配置化连接信息，降低硬编码与命令行输入成本。
- **可扩展性**：支持多节点并行探测与可插拔任务调度，以满足批量巡检需求。
- **安全性**：引入凭据管理与可选的 TLS/隧道配置，减少明文泄露风险。

### 10.2 战略路线图
| 阶段 | 时间（相对） | 范围 | 预期成果 |
| --- | --- | --- | --- |
| P0：基础可观测性 | T+1 周 | 增加 `--log-dir` 参数、本地滚动日志、统一返回码；补充 `keepAlive`/`GetMaxOnlineNum` 失败时的详细错误。 | 能够追踪每次调用的请求、响应、耗时。 |
| P1：命令与配置模块化 | T+3 周 | 引入 `CommandRegistry`，通过 JSON/YAML 描述连接信息和默认参数；`jmxc.conf` 加密凭据引用。 | 命令新增无需改主函数，脚本只需指定配置文件。 |
| P2：多节点并发 | T+5 周 | 启用/重写 `ConnectTask`，封装连接池；新增 `--targets targetA,targetB`，并行执行 keepAlive / stats。 | 同一命令在多个节点上 5 秒内完成，输出结构化汇总。 |
| P3：安全增强 | T+7 周 | 支持 TLS JMX / SSH 隧道预热；兼容凭据保存在 Windows Credential Manager 或 Linux 密钥环。 | 运维无需在命令行传入明文密码；可在公网环境安全使用。 |

### 10.3 关键改动清单
1. **日志与监控**
   - 新增 `Logger` 封装（可使用 `java.util.logging`），输出到控制台和文件。
   - 在 `invokeWithTimeout` 记录入口参数、耗时、异常类型；失败时返回标准化错误码。
2. **命令注册表**
   - 建立 `Map<String, CommandHandler>`，使用 lambda 或单独类实现，替代 `if-else` 链。
   - 为 GM 指令提供 DSL/脚本模板，允许在配置文件中定义常用指令集。
3. **配置与凭据管理**
   - 引入 `--config path`，解析连接信息、超时、日志级别等；支持引用环境变量或凭据别名。
   - 在 Windows 利用 `cmdkey` 或 DPAPI 保存密码，Java 运行时读取解密后注入 `jmx.remote.credentials`。
4. **多节点执行框架**
   - 基于 `ExecutorService` + `CompletionService` 封装任务分发与收敛，复用/改造 `ConnectTask`。
   - 输出表格或 JSON，展示各节点状态、耗时、失败原因，供自动化平台直接消费。
5. **安全与协议选项**
   - 抽象连接器工厂，支持 RMI over SSL、JMXMP 或自定义隧道。
   - 提供 `--tunnel "ssh -L ..."` 预热脚本钩子，在命令执行前后自动拉起/回收隧道。

### 10.4 验收指标
- 日志功能上线后，95% 的失败调用能够在本地日志中定位原因。
- 配置化后，新增命令从需求到上线的改动集中在单个命令处理类，主入口零修改。
- 并发模式下对 10 个节点执行 keepAlive，总耗时不超过 8 秒，且提供可机读输出。
- 安全增强后，默认示例命令行不再包含明文密码，并通过代码审查确保敏感信息不写入日志。

## 11. 泄露与盗刷风控方案
### 11.1 风险假设
- 攻击者获取 `jmxc` 工具或 Jar 包、账号密码，即可调用关键 MBean 执行关服、GM、充值类操作。
- JMX 暴露在半公开网络（IDC 互通区）时，可能被内网潜伏者或被盗机器滥用。

### 11.2 分层防护策略
1. **接入层隔离**
   - 将 JMX 端口限制在管理专网/VPN，所有生产机默认关闭外网访问。
   - 利用防火墙或 SD-WAN ACL，对 `service:jmx:rmi://` 端口进行源 IP 白名单控制。
2. **身份与凭据管理**
   - 强制使用一次性凭据（OTP/短期 Token），登录后按操作类型动态授权。
   - 为 `jmxc` 加入硬件绑定（本地证书/机器指纹），同时在服务器侧校验调用方证书。
   - 使用堡垒机代理，把真实账号隐藏在堡垒机中，由堡垒机托管操作日志。
3. **命令级审计与风控**
   - 在服务器端增加 `GM`、`bindMacToLahu` 等高危操作的额度、频率、金额限制；超出阈值需二次审批。
   - 为每次调用生成唯一流水号，写入审计日志，并同步到风控系统做实时检测。
   - 对关服/停服等危险命令要求双人确认：运维发起后需二次签名方能真正执行。
4. **数据与行为校验**
   - 针对充值/发奖类操作，引入服务端二次验证（例如对 GM 请求附加服务器端签名或挑战响应）。
   - 对输出异常（例如短时间内大量 `gm` 操作）触发自动封禁或锁定工具。
5. **泄露后的快速响应**
   - 构建凭据吊销与密钥轮换流程，能够在分钟级撤销被盗账号。
   - 部署 SIEM 监控 JMX 调用量、失败率、IP 变动，出现异常时自动通知。
6. **工具加固**
   - 对 `jmxc` 增加代码混淆、完整性校验和防调试逻辑，阻碍逆向。
   - 将命令配置与凭据解密逻辑放入安全模块（如 Windows DPAPI），即使 Jar 泄露也无法直接复用。

### 11.3 处置流程（建议）
1. 发现勒索/盗刷迹象 → 立即冻结相关凭据与目标节点的 JMX 端口。
2. 通过审计日志定位所有异常操作和来源 IP → 在风控系统拉黑。
3. 根据流水号对受影响的游戏资产做回滚或补偿。
4. 复盘后更新 ACL、凭据策略与工具版本，并通知相关团队强制升级。
