# 部署指南（生产口径）

> 适用范围：`web_app`（ThinkPHP 8 多应用）  
> 代码真值源：`../03-参考_Reference/00-源码静态分析与对齐基线.md`  
> 架构总览：`../03-参考_Reference/13-现代Web管理后台全生命周期架构说明.md`

## 1. 部署前判断

在部署前先确认当前目标形态：

1. 单机部署：当前最稳妥、最贴近源码默认假设的形态
2. 多节点部署：可做，但必须处理 Session 粘滞或共享 Session 存储

原因：

1. `config/session.php` 固定使用 `store=file`
2. 玩家与后台登录态、CSRF、短时操作签名都依赖 Session

## 2. 软件要求

### 2.1 基础组件

1. PHP >= 8.0，建议 8.1
2. MySQL >= 5.7
3. Nginx 或 Apache
4. Composer 2.x
5. Redis

### 2.2 Redis 的现实地位

虽然 `config/cache.php` 允许默认缓存降级为 File，但生产环境仍强烈建议把 Redis 视为必需组件，因为以下链路直接依赖 `Cache::store('redis')`：

1. 支付下单锁
2. 支付回调幂等锁
3. 转区状态锁与执行锁
4. 玩家限频与可疑访问计数

若 Redis 缺失，典型影响包括：

1. 支付下单返回“系统繁忙”
2. 转区执行失败
3. 安全限频语义退化

## 3. PHP 扩展

最小建议：

1. `pdo_mysql`
2. `mbstring`
3. `openssl`
4. `json`
5. `xml`
6. `fileinfo`
7. `gd`
8. `redis`

## 4. 代码与依赖

```bash
git clone <仓库地址> web_app
cd web_app
composer install --no-dev --optimize-autoloader
```

## 5. 环境变量

```bash
cp .env.example .env
```

必须替换的关键项：

1. `DB_*`
2. `ADMIN_AUTH_SECRET_KEY`
3. `OP_SECRET_SALT`
4. `MASTER_VERIFY_PASSWORD`
5. `JMX_USERNAME`
6. `JMX_PASSWORD`
7. `JMX_TOKEN`

关键建议：

1. `OP_SECRET_SALT`、`ADMIN_AUTH_SECRET_KEY` 至少使用 32 位强随机串
2. 生产环境 `APP_ENV=production`
3. HTTPS 站点建议设置 `COOKIE_SECURE=1`
4. 若要启用 Bind Ticket，再补 `BIND_TICKET_*`

## 7. 单机 Web 服务配置

单机 Nginx 示例：

```nginx
server {
    listen 80;
    server_name your-domain.com;
    root /var/www/web_app/public;
    index index.php index.html;

    location / {
        try_files $uri $uri/ /index.php?s=$uri&$args;
    }

    location ~ \.php$ {
        include fastcgi_params;
        fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
        fastcgi_param HTTPS $https if_not_empty;
        fastcgi_param HTTP_X_FORWARDED_PROTO $scheme;
        fastcgi_pass unix:/run/php/php8.1-fpm.sock;
    }

    location ~ /\.(?!well-known).* { deny all; }
    location ~ /\.env { deny all; }
    location ~ ^/(runtime|vendor)/ { deny all; }
}
```

说明：

1. `HTTP_X_FORWARDED_PROTO` 有助于 `config/cookie.php` 正确判断 HTTPS
2. 敏感目录的公网隔离必须依赖 Web 服务器规则

## 8. 多节点负载均衡建议

### 8.1 当前默认限制

当前代码默认不适合直接做“无状态轮询”：

1. Session 在本地文件
2. CSRF Token 依赖 Session
3. 后台与玩家登录态都保存在 Session

### 8.2 推荐方案

优先顺序如下：

1. 最推荐：单机或主备部署
2. 次推荐：L7 负载均衡 + 会话粘滞
3. 再考虑：改造 Session 到共享 Redis/存储后取消粘滞

### 8.3 反向代理示例

若必须做多节点 HTTP 负载均衡，可参考：

```nginx
upstream web_app_backend {
    ip_hash;
    server 10.0.0.11:8080;
    server 10.0.0.12:8080;
}

server {
    listen 80;
    server_name your-domain.com;

    location / {
        proxy_pass http://web_app_backend;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

说明：

1. `ip_hash` 只是最小可用方案，不代表最佳弹性方案
2. 如果客户端大量共用出口 IP，会造成节点分布不均
3. 真正要做高弹性多节点，建议先改造共享 Session

## 9. 健康检查建议

当前仓库没有专用 `/healthz` 端点。

读操作健康检查建议：

1. `GET /index.php?s=/player/auth/login`
2. `GET /index.php?s=/player/admin/login`

不要把以下接口作为健康检查：

1. 支付接口
2. GM/JMX 接口
3. 需要写库的业务接口

## 10. 权限与目录

确保可写目录：

1. `runtime/`
2. `runtime/log/`
3. `runtime/cache/`

Linux 示例：

```bash
chmod -R 755 runtime
chown -R www-data:www-data runtime
```

## 11. 上线后验证清单

建议按顺序访问：

1. `/index.php?s=/player/admin/login`
2. `/index.php?s=/player/auth/login`
3. `/index.php?s=/player/cdk/index`

并检查：

1. 登录页返回 200
2. `runtime/log/` 无致命错误
3. 管理员登录后能进入后台
4. 玩家登录后能进入玩家中心
5. CDK 授权成功后能进入控制台
6. Redis 连通，支付/转区锁可正常工作
7. HTTPS 场景下 Cookie 正确带 `secure/httponly/samesite`

## 12. 常见误区

1. 不要把 Redis 仅视为“可选缓存”，关键并发链路依赖它。
2. 不要在多节点环境下直接关闭会话粘滞，除非已改造共享 Session。
3. 不要暴露 `runtime/`、`.env`、`vendor/` 给公网。
4. 不要假设只有显式路由会被访问，隐式路由同样存在可达面。
5. 不要把 `COOKIE_SECURE=1` 用在纯 HTTP 环境，否则可能误判导致登录态异常。

## 13. 更新部署流程

```bash
cd /var/www/web_app
git pull
composer install --no-dev --optimize-autoloader
```

更新后建议：

1. 检查 `.env` 是否被覆盖
2. 核验 Redis、MySQL、PHP-FPM、Nginx 状态
3. 回归登录、支付、转区、GM/CDK 关键链路
4. 若是多节点部署，确认会话粘滞仍生效

## 14. 回滚建议

最小回滚包：

1. 代码快照
2. 数据库备份
3. `.env`
4. Nginx/Apache 配置
5. Redis 拓扑与连接配置说明

故障处理顺序建议：

1. 先确认网关和 PHP 是否可达
2. 再确认 MySQL / Redis 是否正常
3. 然后回滚代码与配置
4. 最后回看业务日志定位一致性问题
