## 2. 修复详情

### Fix-1 & Fix-2：Token 版本号吊销机制

**问题根因**：原 Token 为 `hash.timestamp` 两段格式，无状态验证仅依赖时间戳和签名。改密后旧 Token 在 24 小时有效期内仍然有效，存在被盗用的窗口期。

**修复方案**：引入 Redis 存储 `token_version:{userId}` 版本号，Token 升级为 `hash.timestamp.version` 三段格式。

**数据流**：

```
登录时：
  _getOrCreateTokenVersion(uid)
    → Redis GET token_version:{uid}
    → nil 时初始化为 1，SET EX 2592000（30天）
    → 正常时刷新 TTL，返回当前版本
  generatePlayerToken($user)
    → data = uid|username|timestamp|version
    → token = sha256(data + salt) + "." + timestamp + "." + version

验证时：
  verifyPlayerToken($user, $token)
    → explode('.', $token)
    → 3段格式：校验 hash，然后 Redis GET token_version:{uid}
    → token.version !== Redis.version → 403 拒绝（已吊销）
    → 2段旧格式：跳过版本校验，记录 info 日志（向下兼容）

主动吊销：
  invalidatePlayerTokens(uid)
    → Redis INCR token_version:{uid}（TTL 30天）
    → Redis DEL player_user:{uid}（清除用户缓存）
    → 所有已签发旧 Token 下次请求时版本校验失败，立即失效
```

**修改文件**：
- `app/player/common.php`：新增 `_getOrCreateTokenVersion()`、`invalidatePlayerTokens()`；升级 `generatePlayerToken()`、`verifyPlayerToken()`
- `app/player/controller/Profile.php`：`updatePassword()` 成功后调用 `invalidatePlayerTokens()`
- `app/player/controller/Auth.php`：`doResetPassword()` 成功后调用 `invalidatePlayerTokens()`
- `app/player/service/AuthService.php`：`generateToken()`、`verifyToken()` 同步升级

**降级策略**：Redis 不可用时 `_getOrCreateTokenVersion()` 返回 `0`；`verifyPlayerToken()` 中 `version=0` 表示跳过版本校验（可用性优先）。

### Fix-3：敏感字段过滤

**问题根因**：`Player::getPlayerInfo()` 直接返回数据库行数据，包含 `password`、`pay_password` 等敏感字段。这些字段会通过 `$request->player` 注入到所有控制器，存在意外序列化/日志输出导致泄漏的风险。

**修复方案**：在 `getPlayerInfo()` 返回前统一过滤：

```php
$sensitiveFields = ['password', 'pay_password', 'secret_key', 'pay_key', 'salt'];
foreach ($sensitiveFields as $field) {
    unset($playerInfo[$field]);
}
```

**修改文件**：`app/player/model/Player.php`

**设计原则**：在数据源头过滤，而非依赖所有调用方各自过滤（防御深度原则）。

### Fix-4：登录限流 Lua 原子化

**问题根因**：原 `checkLoginRateLimit()` 使用 Redis GET → PHP 判断 → SET 的三步操作。在 PHP-FPM 多进程并发场景下，两个进程同时读到 count=4，都认为未到阈值，同时 SET count=5，实际允许了不应放行的请求。

**修复方案**：Lua 脚本原子执行（Redis 单线程执行 Lua，绝对原子）：

```lua
local cnt = redis.call('INCR', KEYS[1])
if cnt == 1 then
    redis.call('EXPIRE', KEYS[1], ARGV[1])  -- 首次 INCR 时原子绑定 TTL
end
return cnt
```

**同步修复 `recordLoginAttempt()`**：
- 登录成功：改为 `Redis DEL [key, key:locked]`（原子批量删除）
- 登录失败：计数已由 `checkLoginRateLimit()` 的 Lua INCR 处理，不再重复 INCR

**修改文件**：`app/player/common.php`

### Fix-5：请求频率限流 Sorted Set 升级

**问题根因**：原 `checkRequestRateLimit()` 将时间戳数组序列化后存入 Redis 字符串键，GET→array_filter→SET 的操作有竞争窗口，且序列化/反序列化开销大，精度为秒级。

**修复方案**：Redis Sorted Set + Lua 毫秒级滑动窗口：

```lua
ZREMRANGEBYSCORE key 0 (now-window)  -- 移除过期记录
ZCARD                                 -- 当前窗口内计数
ZADD key {now} {now}_{rand}          -- member 加随机后缀防覆盖
PEXPIRE key (window+1000)            -- 毫秒级 TTL，key 自动清理
return cnt
```

**优势**：
- 精度：秒级 → 毫秒级
- 原子性：Lua 脚本，无竞争窗口
- 存储：每个请求仅存一个浮点数（score），远比序列化数组紧凑
- 清理：`ZREMRANGEBYSCORE` O(log N + M)，无需读全量反序列化

**修改文件**：`app/player/middleware/PlayerSecurity.php`

### Fix-6：全链路 trace_id

**问题根因**：系统无请求 ID，多个日志条目无法关联到同一请求，问题排查依赖时间戳和 IP 的组合，在高并发下难以精确定位。

**修复方案**：新建 `TraceId` 中间件，注册为 Player 模块第一个中间件（在限流、认证之前执行）：

```php
// 透传或生成
$traceId = isValidUuidV4($incoming) ? $incoming : generateUuidV4();

// 三处注入
$request->traceId = $traceId;              // 控制器
$_SERVER['TRACE_ID'] = $traceId;           // 全局辅助函数
$response->header(['X-Request-ID' => $traceId]);  // 响应头（前端/代理可读）
```

`logPlayerAction()` 同步更新，自动携带 `trace_id` 字段（无需调用方修改）。

**UUID v4 生成**：`random_bytes(16)` + RFC 4122 位操作，密码学安全，无循环依赖。

**修改文件**：
- 新增：`app/player/middleware/TraceId.php`
- 更新：`app/player/middleware.php`（首位注册）
- 更新：`app/player/common.php::logPlayerAction()`

### Fix-7：文件上传磁盘配额

**问题根因**：头像上传目录缺乏总大小控制，恶意用户可通过频繁上传消耗磁盘空间，导致服务器磁盘打满。

**修复方案**：上传前遍历 `/uploads/avatar` 目录统计总大小，超过 500MB 时拒绝上传：

```php
$it = new RecursiveIteratorIterator(new RecursiveDirectoryIterator($avatarBaseDir, SKIP_DOTS));
foreach ($it as $fileInfo) { $totalSize += $fileInfo->getSize(); }
if ($totalSize >= 500MB) {
    Log::warning('uploadAvatar: disk quota exceeded', [...]);
    return json(['code' => 0, 'msg' => '存储空间已满']);
}
```

**注意**：RecursiveIteratorIterator 遍历在文件数量极多时有性能开销；生产环境可改为异步 cron 统计后缓存结果（优化方向，本次未实现）。

**修改文件**：`app/player/controller/Profile.php`

### Fix-8：缓存穿透防护

**问题根因**：`PlayerAuth` 中间件未对不存在的玩家 ID 做保护：当攻击者使用大量不存在的 ID 发起请求时，每次都会穿透 Redis 缓存直接查询 MySQL。

**修复方案**：Null Object Cache 模式：

```php
$cached = Cache::get('player_user:' . $playerId);
if ($cached === '__NOT_FOUND__') {
    // 命中空值标记，不查库，直接阻断
    return redirect($loginRedirect);
}
// ...查库...
if (!$playerInfo) {
    Cache::set('player_user:' . $playerId, '__NOT_FOUND__', 60);  // 60s 短 TTL
}
```

**TTL 设计**：
- 正常玩家数据：600s（缓存命中率优化）
- 不存在 ID（`__NOT_FOUND__`）：60s（短 TTL 避免影响新注册用户）

**修改文件**：`app/player/middleware/PlayerAuth.php`

### Fix-9：OP_SECRET_SALT 强随机化

**问题根因**：`.env` 中 `OP_SECRET_SALT=CHANGE_ME_OP_SALT`（16 字节，全为 ASCII 可打印字符），熵值远低于 HMAC-SHA256 的安全要求。`generatePlayerToken()` 中已有盐值强度检查，但该检查仅告警不阻断。

**修复方案**：使用 PHP `bin2hex(random_bytes(32))` 生成 64 字符十六进制字符串（256 位熵），替换默认值。

```
OP_SECRET_SALT=f59c0c71f7f2877ad0a13951e266b0cdd8920f78495c4e03527aa2313f170b6a
```

> ⚠️ **重要**：此变更导致所有已签发的 player_token 立即失效（签名 salt 变化）。所有在线用户需重新登录。建议在低峰期执行。

**修改文件**：`.env`

## 3. 向下兼容设计

本批次修复在安全性与向下兼容之间做了明确取舍：

| 场景 | 兼容策略 |
|------|---------|
| 旧格式 Token（2段）验证 | 跳过版本校验，记录 info 日志，正常通行 |
| Redis 不可用时的版本号获取 | 返回 `0`，跳过版本校验（可用性优先）|
| Redis 不可用时的限流 | 降级文件锁，LOCK_EX 防并发，保留基础防护 |
| 旧格式 req_rate:{ip} 键 | 已改为 `req_rate:{ip}`（Sorted Set），旧字符串键在 TTL 后自然过期 |

> 注意：`OP_SECRET_SALT` 变更是本批次唯一的**非向下兼容**变更，会导致已登录用户 Token 全量失效。
