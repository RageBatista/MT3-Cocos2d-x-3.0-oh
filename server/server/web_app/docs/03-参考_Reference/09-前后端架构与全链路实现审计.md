# 前后端架构与全链路实现审计（源码对齐版）

> 更新时间：2026-04-21  
> 审计范围：`app/`、`config/`、`route/`、`public/static/`、`database/mhxy.sql`  
> 参考总览：`13-现代Web管理后台全生命周期架构说明.md`

## 1. 审计总论

从源码来看，项目当前采用的是“SSR 管理后台 + 服务化单体后端 + 外部 JMX/支付协作”的整体方案。

全链路审计必须基于以下事实展开：

1. 前端不是 SPA，而是 ThinkPHP 模板输出的多页面后台。
2. 路由不是纯显式模式，隐式控制器动作仍可达。
3. 鉴权不是 JWT/OAuth2，而是 Session + 签名 Token。
4. 一致性不是微服务分布式事务，而是本地事务 + 锁 + 状态机 + 补偿。

## 2. 请求接入链路

### 2.1 入口

请求入口由以下组件构成：

1. `public/index.php`
2. `public/.htaccess` 或 Nginx `try_files`
3. `route/app.php`
4. `route/player.php`
5. `config/route.php`

### 2.2 中间件装配

全局链路：

```text
CheckRequestCache -> SessionInit -> Check -> PermissionGuard -> Controller
```

Player 应用链路：

```text
TraceId -> PlayerSecurity -> PlayerAuth -> CsrfToken -> Controller
```

注意：

1. `Security` 中间件已实现但默认不在全局链中。
2. 生产环境 `url_route_must=true`（强制路由），开发环境允许隐式路由，安全审计需同时覆盖两种模式。

## 3. 前端渲染模型审计

### 3.1 Admin / Agent 后台

当前后台的前端主形态是：

1. 首屏 SSR
2. 列表页 `bootstrap-table`
3. 表单页 jQuery/AJAX 提交
4. 弹窗和提示使用 `sweetalert2`、`bootstrap-notify`

典型模式：

1. `GET` 页面模板
2. `GET/POST` 列表数据接口返回 `{total, rows}`
3. 操作接口返回 `{code, msg}`

这解释了为什么后台页面在“首屏可达性”和“表格操作效率”上表现较好，但前端工程化程度有限。

### 3.2 Player / Login 侧

玩家侧与授权控制台采用另一套更轻量的交互模型：

1. 服务端输出登录/资料/授权控制台 HTML
2. 页面用 jQuery 或 `fetch` 做局部请求
3. CSRF Token 通过 meta 或隐藏表单字段注入
4. `auth.css`、`player.css` 提供移动端优先布局

关键事实：

1. `app/player/view/layout/login.html` 会设置全局 `X-CSRF-TOKEN` 请求头。
2. `app/player/view/senditem/index.html` 按需加载物品列表，不在页面初始 HTML 中内联全量数据。
3. `app/login/view/layout/*.html` 与 `public/static/auth/css/auth.css` 构成一套独立的授权控制台视觉体系。

## 4. 登录与鉴权全链路

### 4.1 管理员登录链

链路如下：

```text
player/admin/login
    -> player/Admin::doLogin
    -> verifyCsrfToken()
    -> captcha_check()
    -> AuthService::adminLogin()
    -> Session::regenerate(true)
    -> 写入 player_admin_*
    -> 全局 Check 中间件校验
    -> /admin/* 或 /agent/* 页面
```

安全与行为要点：

1. 超级管理员需要额外的 `MASTER_VERIFY_PASSWORD`。
2. `Check` 会校验当前应用和管理员类型一致。
3. 历史 `login/Index::submit()` 仍写入旧 Session 键，并将后台认证结果写入 `admin_auth_log`，形成兼容链。

### 4.2 玩家账号登录链

链路如下：

```text
player/auth/login
    -> player/Auth::doLogin
    -> verifyCsrfToken()
    -> checkLoginRateLimit()
    -> User::getUsername()
    -> generatePlayerToken()
    -> 写入 player_id / player_username / player_token
    -> PlayerAuth 校验
    -> /player/index
```

真实行为：

1. 登录成功/失败统一写入 `player_event_log`（`category=login`）
2. 登录失败会记录失败日志并累积限频计数
3. `PlayerAuth` 失败时会主动清理玩家会话

### 4.3 CDK 授权链

链路如下：

```text
player/cdk/index
    -> player/Cdk::auth 或 existing
    -> AuthService::cdkAuth / cdkExistingAuth
    -> 写入 player_* 会话（id 为角色 ID）
    -> player/cdk/dashboard
    -> player/SendItem / rechargeXianyu
```

必须强调：

1. 该链路中的 `id` 语义不同于账号登录。
2. 部分逻辑必须按“角色级会话”解释，而不是“用户级会话”。

## 5. SendItem / 运维操作全链路

### 5.1 页面交互

`app/player/view/senditem/index.html` 的交互顺序如下：

1. 页面首屏渲染区组下拉与表单
2. 选择区组后调用 `switchServer`
3. 再调用 `getItemList` 按需拉取白名单物品
4. 选择物品后先调 `prepareOp` 获取签名
5. 最终提交 `sendItem` 或 `rechargeXianyu`

### 5.2 服务端防护

后端顺序如下：

1. 验证会话是否已完成 CDK 授权
2. 校验 `item_token`
3. 校验 `op_ts + op_sig`
4. 验证数量范围
5. 通过 GM/JMX 指令发货或充值

该链路的设计目标是“高风险操作最小暴露”，而不是把 GM 能力无条件暴露给前端。

## 6. 支付全链路审计

### 6.1 下单

`api/Pay::getpay` 的顺序是：

1. 参数白名单接收，防止变量覆盖
2. 校验账号、角色、区服、商品
3. 获取 `pay_order_lock:{roleid}:{payid}` 锁
4. 在锁内检查 `daylimit/rolelimit`
5. 查询并缓存支付通道 `pay_channels:{type}`
6. 生成订单号
7. 本地事务写入 `user_order`
8. 返回支付链接

### 6.2 回调

`api/Call::epay` 的顺序是：

1. 日志脱敏
2. 校验订单存在且未支付
3. 可选 `timestamp + nonce` 防重放
4. 获取 `pay_callback_lock:{orderid}` 幂等锁
5. 开事务重新读取订单状态
6. 验签
7. 调 `send()` 发货
8. 更新订单状态并记日志

### 6.3 审计结论

优点：

1. 已有较完整幂等、防重放和事务保护
2. 状态机与锁粒度比较清晰

边界：

1. 发货本身是对游戏服的外部调用，不受 MySQL 回滚控制
2. 若“游戏服成功、数据库失败”，理论上仍需依赖幂等与人工审计兜底

## 7. 转区全链路审计

### 7.1 申请与审核

链路如下：

```text
player/Transfer::submit
    -> Transfer::createTransfer()
    -> admin/Transfer
    -> Transfer::updateStatus()
```

状态机为：

```text
0(待审核) -> 1(审核通过)/2(拒绝)
1(审核通过) -> 3(处理中)/2(拒绝)
3(处理中) -> 4(完成)
```

### 7.2 执行

`TransferExecutionService::executeTransfer()` 的顺序如下：

1. 获取 `transfer_execution_lock:{id}`
2. 事务内读取转区单
3. 校验状态必须为 `PROCESSING`
4. 读取源服/目标服/角色绑定
5. 默认模式下只更新绑定与转区状态
6. 若显式开启 GM 迁移，则调用在线检查、备份、迁移、恢复
7. 更新 `user_transfer` 与 `user_bind`
8. 发送转区通知

### 7.3 审计结论

1. 默认模式不是 GM 全量迁移，而是 `binding_only`。
2. GM 全量迁移链路属于补偿式模式，不是强一致事务。
3. 文档、运维说明和用户预期必须明确这一点。

## 8. 数据层与缓存层审计

### 8.1 ORM / SQL 组合方式

源码显示当前数据层是混合模式：

1. `Model` 适合基础封装和状态机
2. `Db::name/table()` 负责大多数查询
3. `Db::query/execute()` 用于复杂 SQL 与兼容逻辑

这比“纯 ORM 项目”灵活，但也意味着：

1. 查询规范更依赖开发约定
2. 文档必须说明具体路径，而不能只描述抽象 Repository 层

### 8.2 关键缓存

| 缓存键 | 用途 | TTL |
|------|------|------|
| `player_user:{id}` | 玩家资料缓存 | 600 秒 |
| `pay_channels:{type}` | 支付通道缓存 | 300 秒 |
| `admin:server:online:{server}:{port}` | 在线人数探针 | 30 秒 |
| `login_limit:{ip}` | 登录限频 | 300 秒 |
| `request_rate:{ip}` | 玩家请求频率 | 120 秒 |

### 8.3 缓存与一致性审计

1. Session 固定文件存储，不能把“缓存用了 Redis”误解成“系统已经无状态”。
2. Redis 缺失时，玩家限频可降级，但支付和转区关键锁会失去预期语义。
3. 多数缓存为时间驱动失效，不是事件驱动失效。

## 9. 响应协议与前端消费审计

### 9.1 响应类型

项目当前至少存在四类响应：

1. 标准 JSON：`{code, msg, data}`
2. 表格 JSON：`{total, rows}`
3. 纯文本：如 `success/fail/1/0`
4. HTML 视图：`view(...)`

### 9.2 前端消费方式

因此前端必须区分：

1. `bootstrap-table` 期望分页结构
2. 表单/弹窗逻辑期望 `code/msg`
3. 历史兼容接口可能仍按文本协议返回

这也是当前前端无法简单抽象成统一 SDK 的根本原因。

## 10. 性能与渲染优化审计

当前已落地的优化主要是“后台效率型优化”，不是“前端框架型优化”：

1. 首屏 SSR，减少空白页等待
2. 列表页服务端分页，避免全量大表一次性渲染
3. 在线人数探针做 30 秒缓存，减少 JMX 压力
4. Player 资料做 600 秒缓存，减少重复查库
5. 物品列表按需拉取，降低授权控制台初次载荷

尚未形成的平台能力包括：

1. 统一静态资源版本管理
2. 前端打包与模块拆分
3. 统一接口 SDK
4. 全站统一响应 DTO

## 11. 全链路审计结论

1. 当前系统最适合定义为“SSR 管理后台 + 服务化单体 + 外部系统协作”。
2. 现代后台能力中的“网关、JWT/OAuth2、微服务、分布式事务”在本项目里都应写成“局部吸收”而非“完整落地”。
3. 已落地的现代化能力主要集中在：幂等锁、状态机、防重放、CSRF、移动端适配、服务端分页、运维操作签名。
4. 文档和部署规范的重点不是过度美化架构，而是让读者知道哪些能力已经可用、哪些只是演进方向。
