# 项目架构说明（源码对齐版）

> 更新时间：2026-04-10  
> 参考基线：`00-源码静态分析与对齐基线.md`  
> 生命周期总览：`13-现代Web管理后台全生命周期架构说明.md`

## 1. 架构定位

`web_app` 当前是一个基于 ThinkPHP 8 多应用模式构建的服务化单体，而不是独立网关、独立认证中心、独立业务微服务组成的分布式平台。

其真实特征是：

1. 以 `admin / agent / api / player / login / index / sdk` 多应用划分业务边界。
2. 以控制器、服务类、模型和中间件承担大部分平台职责。
3. 通过 MySQL、Redis、文件缓存、JMX/GM、支付回调与外部系统协作。
4. 通过 SSR 模板与 jQuery/AJAX 输出后台页面和玩家端页面。

## 2. 总体拓扑

```text
浏览器 / 手机端
    -> 反向代理 / Web 服务器 / 负载均衡器
    -> public/index.php
    -> route/*.php + config/route.php
    -> 中间件链
    -> Controller
    -> Service / Model / Db
    -> MySQL / Redis / 文件系统 / JMX(GM) / 支付平台
    -> HTML / JSON / 文本响应
```

部署边界说明：

1. 入口重写由 `public/.htaccess` 或 Nginx `try_files` 完成。
2. 网关层职责主要由外部 Web 服务器承担，应用内部没有内建 API Gateway。
3. `config/route.php` 中 `url_route_must` 取决于环境变量 `ROUTE_MUST`（默认跟随 `APP_ENV`）：生产环境默认强制路由（仅显式路由可达），开发环境允许隐式路由。

## 3. 应用模块边界

| 应用 | 主要职责 | 关键说明 |
|------|------|------|
| `admin` | 管理后台、GM（已拆分为5个子控制器）、配置、转区审核、日志 | 受全局 `Check` + `PermissionGuard` 中间件保护 |
| `agent` | 代理后台、玩家管理、提现/结算 | 与 `admin` 共用管理员会话体系 |
| `api` | 支付、回调、语音、兼容接口、开放 API | 同时承担历史接口兼容层 |
| `player` | 玩家中心、资料、订单、反馈、转区、CDK、新登录链路 | 拥有独立中间件链 |
| `login` | 历史授权与后台登录兼容入口 | 与 `player` 新链路并存 |
| `index` | 前台活动/CDK 页面 | 轻量前台壳应用 |
| `sdk` | SDK 壳入口 | 对接外部接入流程 |

## 4. 核心中间件与鉴权平面

### 4.1 全局中间件

来自 `app/middleware.php`：

1. `\think\middleware\CheckRequestCache`
2. `\think\middleware\SessionInit`
3. `\app\middleware\Check`
4. `\app\middleware\PermissionGuard`

作用：

1. 请求缓存检查
2. 初始化 Session
3. 对 `admin` 与 `agent` 应用做后台会话校验
4. 拦截部分针对历史兼容路径的扫描请求
5. 细粒度权限点校验（基于 `config/permission.php` 规则）

### 4.2 Player 应用中间件

来自 `app/player/middleware.php`：

1. `TraceId`
2. `PlayerSecurity`
3. `PlayerAuth`
4. `CsrfToken`

作用：

1. 全链路追踪（UUID v4 trace_id，首个中间件执行，后续日志可读）
2. 登录限频与可疑请求审计
3. 玩家会话/Token 验证
4. CSRF Token 生成与校验

### 4.3 安全中间件现状

`app/middleware/Security.php` 已实现 SQL/XSS/IP 黑白名单检测，但只在 `config/middleware.php` 注册 alias/priority，默认未全局挂载。

这意味着：

1. 生产安全不能假设所有请求都经过该中间件。
2. 网关/WAF/ACL 仍然是边界安全的第一道防线。

## 5. 现代后台五层映射

| 层级 | 项目当前实现 | 关键文件 |
|------|------|------|
| 网关层 | 外部 Nginx/Apache/LB + 应用路由 + 少量扫描拦截 | `public/.htaccess`、`route/*.php`、`app/middleware/Check.php` |
| 鉴权层 | Session + HMAC Token + CSRF + Captcha + 二次验证 + Bind Ticket + TraceId | `app/player/common.php`、`app/player/service/AuthService.php`、`app/service/BindTicketService.php`、`app/player/middleware/TraceId.php` |
| 业务层 | 多应用单体 + 服务类编排 + 外部 JMX/支付对接 | `app/service/*.php`、`app/player/service/*.php` |
| 数据层 | ThinkPHP Model + Query Builder + 原生 SQL + Redis/File Cache | `app/model/*.php`、`config/cache.php`、`config/session.php` |
| 前端层 | SSR 模板 + jQuery/AJAX + Bootstrap Table + 移动端适配 CSS | `app/*/view/*`、`public/static/*` |

## 6. 核心业务协作模式

### 6.1 支付

支付由 `api/Pay` 和 `api/Call` 组成：

1. 下单前使用 Redis 锁做角色/商品粒度互斥
2. 下单写库使用本地事务
3. 回调使用 `timestamp + nonce` 防重放
4. 回调用 `pay_callback_lock:{orderid}` 做幂等
5. 订单状态由 `UserOrder` 状态机控制

### 6.2 转区

转区由 `player/Transfer`、`admin/Transfer`、`TransferExecutionService` 协同完成：

1. 前台提交申请
2. 后台审核与状态推进
3. 执行阶段使用锁、状态机、本地事务
4. 默认只做 `binding_only` 绑定迁移

### 6.3 玩家授权与 GM 操作

玩家授权以 `player/Cdk` 和 `player/SendItem` 为核心：

1. CDK 授权建立角色级会话
2. SendItem 使用 `item_token + op_sig`
3. 实际发货通过 JMX/GM 指令调用游戏服

## 7. 数据与缓存架构

### 7.1 数据访问模式

当前数据层不是“纯 ORM”，而是混合模式：

1. 模型类负责基础封装与状态机
2. 查询构造器承担大部分条件拼装
3. 原生 SQL 用于统计、兼容查询、DDL 或精细控制

### 7.2 缓存与会话

1. 默认缓存驱动：Redis 优先、File 降级
2. Session：固定 `store=file`
3. 业务显式锁：大量代码直接调用 `Cache::store('redis')`

关键结论：

1. 多节点部署必须处理 Session 粘滞或共享 Session 存储。
2. Redis 对支付、转区、限频与热点缓存具备关键意义。

## 8. 前端与响应模型

### 8.1 渲染方式

项目采用 SSR 为主、局部异步为辅的后台模式：

1. 登录页、控制台、管理页由服务器直接输出 HTML
2. 列表页使用 `bootstrap-table` 走服务端分页
3. 高频操作页使用 jQuery 或 `fetch` 做局部提交

### 8.2 响应格式

当前响应协议未完全统一，常见形态包括：

1. `{code, msg, data}`
2. `{total, rows}`
3. 纯字符串
4. `view(...)` 输出 HTML

因此，前端和外部调用方不能假定全站只有单一 DTO 规范。

## 9. 当前架构约束

1. 当前没有标准 JWT/OAuth2 鉴权中心。
2. 当前没有服务注册发现、消息总线或微服务治理平面。
3. 当前没有真正的分布式事务框架，主要依赖本地事务、锁、状态机和补偿。
4. 当前 `Security` 中间件默认未全局启用。
5. 当前 `login/*` 与 `player/*` 兼容链路并存，发布回归必须双链覆盖。
6. `admin` GM 当前由 `GmPlayer`、`GmServer`、`GmMail`、`GmCdk`、`GmCleanData` 五个子控制器 + `GmBase` 基类组成（均继承 `GmBase`，受 `PermissionGuard` 细粒度权限控制）。
7. 全局 `PermissionGuard` 中间件基于 `config/permission.php` 执行细粒度权限点校验，仅对 `admin`/`agent` 应用生效。
