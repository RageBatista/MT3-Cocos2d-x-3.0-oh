# 业务逻辑说明（源码对齐版）

> 更新时间：2026-04-10  
> 参考基线：`00-源码静态分析与对齐基线.md`

## 1. 代理与佣金

## 1.1 代理层级

核心表与模型：

- `admin_account`（`app/model/Agent.php`）
- `agent_relation`（`app/model/AgentRelation.php`）
- `agent_commission`（`app/model/AgentCommission.php`）

关键字段：

- `type`：1 管理员 / 2 代理
- `lastagent`、`agent_tree`：代理关系链

## 1.2 分佣触发

主链路：

- 订单状态变更（`UserOrder`）触发 `CommissionService`

当前实现中使用三层分佣处理：

- 直属代理：70%
- 一级上级代理：5%
- 二级上级代理：5%

佣金明细写入 `agent_commission` 表，汇总字段更新到 `admin_account.total_commission`。

触发条件：`UserOrder::upOrderStatus()` 在订单状态变更为 `STATUS_PAID` 时自动调用 `CommissionService::distributeCommission()`。

## 2. 支付业务

## 2.1 下单流程（`api/Pay::getpay`）

1. 白名单参数校验（防变量覆盖）
2. 用户/角色/服务器/商品合法性校验
3. 获取下单锁 `pay_order_lock:{roleid}:{payid}`
4. 在锁内校验 `rolelimit/daylimit`
5. 读取支付通道缓存 `pay_channels:{type}`（300 秒）
6. 事务写入 `user_order`
7. 返回支付 URL（base64）

## 2.2 回调流程（`api/Call::epay`）

1. 解析回调参数并记录脱敏日志
2. 幂等短路（已支付订单直接 `success`）
3. 防重放（`timestamp/nonce`）
4. 获取 `pay_callback_lock:{orderid}`
5. 事务内验签、发货、更新订单状态
6. 返回 `success/fail`

## 2.3 发货流程（`Call::send`）

1. 校验用户与角色绑定
2. 计算并发安全日限（Redis 计数）
3. 处理角色限购
4. 累计充值入账（`user_bind.charge/daycharge`）
5. 执行 GM 发放（仙玉/VIP/邮件）

## 3. 玩家认证与授权

## 3.1 账号登录（Player）

入口：`player/Auth::doLogin`

1. CSRF 校验
2. 账号密码校验
3. 登录频率限制
4. 生成 token（`generatePlayerToken`）
5. 写入 `player_*` Session

## 3.2 CDK 授权（Player）

入口：`player/Cdk::auth`、`player/Cdk::existing`

1. 首次授权：`cdks` 绑定 UID、区服、授权密码
2. 已有授权：校验 `pass` 并恢复会话
3. 统一由 `AuthService` 完成会话落地

## 3.3 历史授权链路（Login）

`login/Auth.php` 仍保留完整授权链路（隐式路由可达），与 `player/cdk` 并存。

## 3.4 旧协议绑定兼容链路（Enlist/LegacyRole/Game）

核心入口：

1. `/enlist/submit_code` -> `api/Enlist::submitCode`（含根应用兜底）
2. `/user/api/index.php/role/set|get` -> `api/LegacyRole::{set,get}`
3. `/api/game/bind` -> `Game::bind`

共性机制：

1. 统一调用 `RoleBindService` 完成绑定/刷新绑定
2. 可选消费 `bind_ticket` 并做账号/区服/角色一致性校验
3. 兼容旧客户端文本协议（`1/0`）与新 JSON 结构并存

## 4. SendItem 业务

入口：`player/SendItem.php`

核心规则：

1. 必须是 CDK 授权会话（含 `cdk` 标记）
2. 必须已选区组（`serverid`）
3. `sendItem` 必须先持有 `item_token` + `op_sig`
4. 物品白名单来自 `public/txt/itemid.txt`
5. 发送失败时尝试邮件补发

## 5. 转区业务

## 5.1 玩家提单（`player/Transfer::submit`）

1. 校验源服/目标服/角色/联系方式/原因
2. 校验角色归属与资格
3. 拒绝同角色未完成申请
4. 写入 `user_transfer`（`status=0`）

## 5.2 后台审核（`admin/Transfer.php`）

- `approve`：`0 -> 1`
- `reject`：`0 -> 2`
- `process`：`1 -> 3`
- `complete/autoExecute`：仅 `3` 可执行

## 5.3 执行服务（`TransferExecutionService`）

1. 执行锁：`transfer_execution_lock:{transferId}`
2. 事务内更新状态、绑定关系、通知
3. 默认 `binding_only`（不执行 GM 全量迁移）
4. 仅在 `transfer.gm_migration_enabled=true` 时走 GM 迁移链路

## 6. 语音业务

入口：`api/Voice::receive`、`api/Voice::iat`

现状：

1. 仅接受通过 AMR 头校验的数据
2. 落地文件固定 `.amr`
3. 识别结果当前为占位文本 `未能识别语音`
4. 元数据写入 `user_voice`

## 7. 业务一致性要点

1. 支付回调：幂等 + 防重放 + 事务一致性
2. 转区状态：状态机 + 锁 + CAS
3. SendItem：白名单 + item_token + 操作签名
4. 玩家会话：`player_*` 统一键空间
