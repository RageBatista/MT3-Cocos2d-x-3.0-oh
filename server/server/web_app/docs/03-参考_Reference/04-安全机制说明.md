# 安全机制说明（与当前代码对齐）

> 更新时间：2026-02-27  
> 说明：本文档只描述当前仓库代码中的真实安全机制与已知约束。

## 1. 认证与会话

## 1.1 Admin/Agent 认证（`Check` 中间件）

文件：`app/middleware/Check.php`

核心逻辑：

1. 仅对 `admin`、`agent` 应用执行认证
2. Session 键：
   - Admin：`username_1`、`auth_token_1`、`password_1(兼容旧Session)`
   - Agent：`username_2`、`auth_token_2`、`password_2(兼容旧Session)`
3. 若命中旧 Session（仅密码hash），会自动迁移为 token 方案
4. token 生成使用 HMAC-SHA256 + `hash_equals()` 比较

P0 变更要点：

- 密钥不再硬编码，读取 `config('security.admin_auth.secret_key')`
- 若密钥为空，`generateToken()` 直接抛异常并拒绝高权限鉴权

## 1.2 Player 认证（`PlayerAuth` 中间件）

文件：`app/player/middleware/PlayerAuth.php`

关键行为：

1. 非公开控制器/动作必须登录
2. 从 Session 读取 `id/username/token`
3. 调用 `verifyPlayerToken()` 校验
4. 失败时清理玩家 Session 并阻断请求（Ajax 401，页面跳登录）
5. 玩家信息缓存键：`player_user:{id}`，TTL=600 秒

公开路由白名单（当前代码，按“控制器+动作”匹配）：

- `Auth`：`login/register/forgot/doLogin/doRegister/doForgot/resetPassword/doResetPassword/logout`
- `Cdk`：`index/auth/existing/servers`
- `Admin`：`login/doLogin/captcha`
- `Index`：`index`

说明：

- `SendItem` 不在公开白名单，需先通过玩家会话校验；
- 同时 `SendItem` 控制器内要求存在 `cdk` 授权会话标记，避免普通账号会话直接执行 GM 发放操作。

## 1.3 Player Token 生成/验证

文件：`app/player/common.php`

当前实现：

- 格式：`{sha256}.{timestamp}`
- 摘要输入：`id|username|timestamp + OP_SECRET_SALT`
- 最大有效期：24 小时（`86400` 秒）

P1-A 要点：

- `OP_SECRET_SALT` 为空时拒绝生成/验证 Token
- 盐值长度不足会记录告警

## 2. 请求防护

## 2.1 全局 Security 中间件

文件：`app/middleware/Security.php`

按 `config/security.php` 配置执行：

1. SQL 注入关键字检测
2. XSS 标签/属性检测
3. IP 黑白名单检查

命中后行为：

- 记录攻击日志（`Log::warning`）
- 直接 403 阻断

## 2.2 PlayerSecurity（频率与恶意IP）

文件：`app/player/middleware/PlayerSecurity.php`

机制（实现能力）：

1. 恶意 IP 黑名单拦截
2. 登录频率限制：5 分钟最多 5 次（覆盖 `doLogin/doRegister/doForgot` 与 CDK 的 `auth/existing`）
3. 请求频率限制：1 分钟超过 60 次进入可疑计数
4. 可疑计数达到阈值后封禁 1 小时

降级：

- Redis 不可用时回退文件缓存记录频率状态

说明：

- `PlayerSecurity` 已在 `app/player/middleware.php` 中统一挂载，随 Player 应用请求生效。

## 2.3 CSRF 防护

文件：`app/player/middleware/CsrfToken.php`、`app/player/common.php`、`app/BaseController.php`

当前行为：

- `CsrfToken` 中间件具备 GET 生成、写操作验证的实现逻辑
- Player 控制器侧大量通过 `generateCsrfToken()` / `verifyCsrfToken()` 显式校验
- Admin `Transfer` 写操作使用 `BaseController::checkToken()` 校验

此外：

- `CsrfToken` 已在 `app/player/middleware.php` 中统一挂载；控制器中的 `verifyCsrfToken()` 显式校验仍保留作为防御冗余。

## 3. 支付回调安全（P0）

文件：`app/api/controller/Call.php`，配置：`config/security.php -> pay_callback`

### 3.1 幂等与并发控制

1. 订单已支付直接返回 `success`
2. Redis 幂等锁：`pay_callback_lock:{orderid}`
3. 事务内二次检查订单状态，防并发重复发货

### 3.2 防重放

1. 可选时间戳检查（`timestamp_ttl`）
2. nonce 去重：`pay_callback_nonce:{nonce}`
3. 上游不提供 nonce 时记录告警并降级

### 3.3 日志脱敏

- 根据 `mask_fields` 对 GET/POST 和解析参数做脱敏后再记日志

### 3.4 测试入口限制

- `/api/call/epay1` 在 `APP_ENV=production` 时返回 403

## 4. 并发一致性安全（业务侧）

## 4.1 支付下单

文件：`app/api/controller/Pay.php`

- 锁：`pay_order_lock:{roleid}:{payid}`
- 限购检查在锁内执行
- 订单写入事务
- 随机号改为 `random_int()`

## 4.2 订单状态机

文件：`app/model/UserOrder.php`

- `STATUS_TRANSITIONS` 定义合法迁移
- CAS 风格条件更新（按旧状态更新）
- 退款使用锁：`order_refund_lock:{id}`

## 4.3 转区状态机与执行锁

文件：`app/model/Transfer.php` + `app/service/TransferExecutionService.php`

- 状态更新锁：`transfer_status_lock:{id}`
- 执行锁：`transfer_execution_lock:{transferId}`
- 均在事务中保证一致性

## 5. GM 命令执行安全

文件：`app/gm/Gm.php`

现有防护：

1. `buildJmxBaseCommand()` 统一 `escapeshellarg()`
2. 端口、玩家ID、IP 进行基础校验
3. JMX 配置优先尝试 `app/admin/security_config.php`，其次 `config/security.php`

P0 现状补充：

- 转区相关 GM 方法（如 `createRole`、`getRoleData` 等）当前为显式未实现并返回 `error`，避免“假成功”。

## 6. 已知差异与历史兼容项

1. `MASTER_VERIFY_PASSWORD` 用于 `AuthService::adminLogin()` 的超级管理员二次验证；未配置时会拒绝超级管理员登录。
2. `app/login/controller/Auth.php::opSecret()` 仍保留 `CHANGE_ME_OP_SALT` 回退（历史兼容路径）。
3. Player 安全链路当前为“应用中间件统一挂载 + 控制器显式校验”组合。
