## 1. 升级范围

本次收敛的交付链为：

```text
Win32 平台
  cocos2d-x-3.0-oh -> CEGUI-0.7.9-r5 -> engine -> FireClient -> MT3.exe
```

- `engine/engine.win32.vcxproj` 使用 `cocos2d-x-3.0-oh` 头文件与静态库。
- `client/MT3Win32App/FireClient.win32.vcxproj` 与 `mt3.win32.vcxproj` 使用 `tools/CEGUI-0.7.9-r5`。
- CEGUI Cocos2D renderer 接入 Cocos 3.0-oh 的 kazmath 矩阵模式与 GL 状态缓存。
- Android/iOS 的物理 Cocos 依赖仍是 `cocos2d-x-2.2.6`，不在本次 Win32 交付范围内。

## 2. 代码与配置变更

- Cocos 3.0-oh 的 Win32 生成工程统一补齐 `GLEW_STATIC`，保证静态 GLEW 链接宏一致。
- kazmath 增加当前矩阵模式查询，并在矩阵栈空弹出时记录诊断信息、跳过非法弹出。
- Cocos GL 状态缓存增加保留矩阵栈的失效入口，避免 CEGUI 结束渲染时释放外层 Cocos 矩阵栈。
- CEGUI Cocos2D renderer 保存并恢复进入渲染前的矩阵模式；renderer 头文件显式包含 kazmath matrix 类型定义。
- CEGUI Lua 绑定与 `.pkg` 同步 `MessageTips` 类型转换。

### 6.1 Win32 canonical 基线与 ABI 重编

#### 现象

单个工程显示编译成功，但启动期、链接期或 UI 运行期仍出现不稳定行为；也可能因把不同 `PlatformToolset`、公共头或 renderer 版本的 `.obj/.lib` 拼入同一交付物而留下隐蔽 ABI 问题。

#### 取证/排查

先用 `tools/scripts/Build-MT3-Exe-Canonical.ps1` 和工程文件确认 `Upgrade30`、`v120`、Windows SDK 8.1；再核对实际链接输入与产物时间戳。固定依赖次序为：

```text
cocos2d-x-3.0-oh -> CEGUI-0.7.9-r5 -> engine -> FireClient -> MT3
```

`client/Build-MT3-v120.ps1` 的内部 SafeChain 是 ABI 安全边界；公共头、renderer、对象布局、虚函数、模板实例或影响布局的宏发生变化时，增量链接不足以证明一致性。

#### 根因

Win32 模块之间通过静态库和公共 C++ 头传播对象布局、宏展开和 CRT 约束。仅刷新上游库或下游可执行文件，会令调用方与被调用方的 ABI 版本不一致。

#### 修复

固定 canonical 链为 `v120 / SDK 8.1 / Upgrade30`，并按依赖方向重编。Cocos、CEGUI、公共 renderer 头或其他 ABI 敏感内容变更后，必须通过 SafeChain 继续执行 `engine -> FireClient -> MT3` 的下游重编；禁止使用跨工具集二进制、`/FORCE` 或局部替换掩盖问题。

#### 验证

本记录第 4 节的 Release 构建和运行依赖审计已验证该链的构建闭环。每次后续改动仍应从构建日志确认每一层实际重编，而不是只看最终 `MT3.exe` 存在。

#### 预防/回滚

提交前记录改动触发的最小重编范围；一旦发现疑似 ABI 混编，停止继续增量补链，从受影响的最上游项目开始按下游顺序 `Rebuild`。回滚也必须回滚同一 ABI 补丁集并整链重编，不能只替换单个 `.lib`。

### 6.2 Cocos/CEGUI 渲染状态交接

#### 现象

登录或选服 UI 向右偏移，字体、背景或后续场景绘制异常；这类问题常在 Cocos 与 CEGUI 先后绘制后出现，单独查看 layout 坐标并不能解释。

#### 取证/排查

同时检查 Cocos、CEGUI renderer、`engine` 与最终工程的 `GLEW_STATIC` 宏；沿 Cocos/CEGUI 交界核对 kazmath 当前矩阵模式、矩阵栈 push/pop、GL 状态缓存和 renderer 进入/退出时的状态。renderer 头必须显式包含所需 kazmath 矩阵类型，不能依赖偶然的间接 include。

#### 根因

CEGUI 绘制会改变 OpenGL 和 kazmath 状态。若 renderer 未恢复调用前矩阵模式、空矩阵栈仍继续弹出，或 Cocos 状态缓存仍认为 GL 状态未改变，后续绘制会使用错误的投影/模型视图状态。

#### 修复

本次链路统一了 `GLEW_STATIC`；kazmath 增加矩阵模式查询和空栈保护；Cocos GL 状态缓存提供保留矩阵栈的失效入口；CEGUI Cocos2D renderer 保存并恢复进入渲染前的矩阵模式，并显式包含 kazmath 定义。这些变更必须与 renderer 及其下游一起重编。

#### 验证

构建闭环已验证。仍需在交互桌面人工检查冷启动、登录、选服、切换分辨率和返回流程中的坐标、字体和背景；尚无人工视觉证据时，不将画面问题标记为完成。

#### 预防/回滚

新增 renderer 调用前先写明它读写的矩阵、GL 状态和缓存状态；调试时以最小状态跟踪定位，确认后清除临时渲染追踪日志。回滚必须以整组矩阵/缓存交接补丁为单位，并再次执行 SafeChain 下游重编。

### 6.3 CEGUI Lua 扩展与生成物边界

#### 现象

Lua 调用 CEGUI 控件时出现类型转换、工厂注册或方法缺失，特别是 MT3 自定义控件和 `MessageTips` 等类型在 C++ 存在而 Lua 不可达。

#### 取证/排查

先从实际 Lua 调用点反查类型、工厂和转换路径，再检查 `*.pkg` 源定义、生成的 `lua_CEGUI.cpp`、CEGUI 工厂注册和最终链接库。`lua_CEGUI.cpp` 是产物，不是长期手写源。

#### 根因

只改生成的绑定文件会在下一次 tolua 生成时丢失；把所有 C++ 类型无差别导出也会扩大绑定面，并不等于解决实际 Lua 可达性。

#### 修复

以 `.pkg` 为源，只迁移实际 Lua 可达的类型；补齐 MT3 控件、工厂注册和类型转换，包括 `MessageTips`，然后重新生成 `lua_CEGUI.cpp` 并重编 CEGUI 与下游。

#### 验证

验证生成结果确实包含所需类型转换和注册，再由相关 Lua 对话框创建路径验证。选服链的当前日志已证明 Lua 对话框能够创建；这不等同于所有自定义控件和所有场景均已人工验收。

#### 预防/回滚

评审时同时提交 `.pkg`、生成步骤和必要的产物差异，禁止仅提交手改的 `lua_CEGUI.cpp`。回滚优先恢复 `.pkg` 与生成产物的一致版本，再执行对应库和下游重编。

### 6.4 Scheme、资源加载与登录点击链

#### 现象

登录或选服点击后发生长时间卡顿、资源重复初始化，或因临时 bootstrap scheme 缺少完整 look'n'feel、字体、imageset 而出现控件和资源异常。

#### 取证/排查

检查 [`GameUIManager.cpp`](../client/FireClient/Application/Manager/GameUIManager.cpp) 中 `InitGameUI`、`InitGameUIPostInit` 与 [`LoginManager.cpp`](../client/FireClient/Application/Manager/LoginManager.cpp) 的调用时序；检查原始 `taharezlook.scheme`、`taharezlook2.scheme` 和 layout/资源声明链。对于 XML 报错，再核对 [`LJXMLParser`](../tools/CEGUI-0.7.9-r5/cegui/src/XMLParserModules/LJXMLParser/CEGUILJXMLParser.cpp) 实现，而不是先批量改 XML。

#### 根因

完整 Scheme 的 fonts、imagesets 和 look'n'feel 如果被放入登录点击同步路径，会把资源加载与状态切换耦合。拆分加载后若在 primary 完成时提前发布完整 UI 就绪状态，登录/选服仍会访问尚未注册的 secondary 窗口类型。`LJXMLParser::parseXMLFile` 接收但不使用 schema 参数，因而把 CEGUI 新版 `xml_schemas` 批量替换到资源文件并不能改变该运行时解析行为。

#### 修复

保留 bootstrap、primary、secondary 三阶段逐帧加载：bootstrap 只满足登录首屏，primary 完成后启动 secondary，但不发布完整 UI 就绪状态；secondary 完成并校验关键 Imageset/WindowFactory、执行 `CChatCellManager.Initialize_` 后，才设置 `m_bUIPostInited=true`。`InitGameUIPostInit` 只做完整就绪检查，登录和选服回调未就绪时进入 pending，由 `LoginManager::Run` 在门禁转绿后恢复。

#### 验证

检查冷启动后完整 Scheme、登录 Imageset、`TaharezLook/Editbox` 和 `TaharezLook/FrameWindowtouming` 均已就绪，再检查点击登录、打开选服和返回是否保持响应。18:49 日志显示 `secondary scheme ready postInit=1` 后才出现 `LoginManager::Run resumes deferred server selection`，且新 CEGUI 日志无 Error/Exception/布局加载失败；桌面点击体感与完整选服返回仍应继续人工回归。

#### 预防/回滚

资源问题按 `scheme -> look'n'feel -> imageset/font -> layout -> Lua/C++ 绑定 -> 打包输出` 顺序排查，禁止把完整资源加载重新塞进点击回调。回滚时恢复原始 Scheme 加载时序，不以批量 schema 替换作为修复手段。

### 6.5 IME、Editbox、Lua 事件、分辨率与字体

#### 现象

点击 Editbox 后键盘不弹出、文本未注入、焦点丢失，或不同分辨率下文字与控件位置异常；这类症状不能仅凭“资源已加载”下结论。

#### 取证/排查

沿 `AttachIME -> DelegateAttach -> DetachIME`、键盘目标窗口、`canEdit`、focus、layout、字体/分辨率配置和 Lua 事件订阅逐段记录。18:27 日志显示 `switchaccount/accountbox` 为有效键盘目标，`DelegateAttach` 返回成功，说明该次账号输入链已到达。

#### 根因

键盘显示与文字输入跨越 CEGUI 焦点、控件可编辑状态、IME delegate、平台输入桥、Lua 事件以及逻辑/物理分辨率换算。任何一段断开都可能表现为“没有键盘”，但根因未必在资源文件。

#### 修复

以当前焦点和 delegate 状态为起点修复实际断点，保持 `AttachIME`、`DelegateAttach` 和 `DetachIME` 的生命周期配对；同时核对控件类型、`canEdit`、Lua 绑定、layout 与字体资源。不要为输入问题新增与其无关的 Scheme 或网络改动。

#### 验证

当前日志已验证账号输入的可达性。仍需人工覆盖中文/英文输入、切换焦点、返回登录、不同分辨率与字体显示；这些视觉和交互项未完成前不标为全量通过。

#### 预防/回滚

为输入问题保留可关联目标窗口的短期诊断，完成定位后删除临时噪声；回滚必须同时恢复相关的焦点/IME 生命周期修改，避免留下单边 attach 或 detach。

### 6.6 Spine、背景和层级问题

#### 现象

登录背景黑屏、Spine 特效不显示或被其他窗口遮挡；仅看到对象创建日志不足以判断纹理、atlas、json、slot 绘制和层级是否全部正确。

#### 取证/排查

按 `纹理 -> atlas -> json -> slot 绘制 -> UI 窗口层级` 逐项查看日志和资源路径，并在需要时确认背景帧是否处于正确的窗口层级。调试中应区分资源加载失败、绘制未发生和已绘制但被覆盖三类事实。

#### 根因

Spine 资源三件套和 slot 绘制链中任一项缺失都会导致不可见；即使绘制成功，背景帧若未置后仍会遮挡交互 UI 或被其遮挡。

#### 修复

对照纹理、atlas、json 与 slot 绘制证据修复实际缺口，将背景帧通过 `moveToBack` 置于正确层级；完成定位后清除临时渲染追踪日志，避免长期把调试输出当成业务日志。

#### 验证

构建和日志可确认路径已执行，但背景、特效和层级的最终正确性必须在交互桌面人工目视确认，尤其需要覆盖登录、选服和返回流程。

#### 预防/回滚

每次只调整一个资源或层级变量并保留截图/日志证据；回滚时恢复同一资源或层级变更，不要同时替换 Spine 资源和 renderer 状态补丁。

### 6.7 日志严重级别与 ServerAttr 探测判读

#### 现象

日志中出现大量 Lua `(Error)`，或出现 `OnAutoFailed op=7/3 accountLen=0 detail=server attr`，容易被直接误判为账号丢失、选服失败或连接失败。

#### 取证/排查

先追踪日志发射点与前后因果：[`selectserverentry.lua`](../client/resource/res/script/logic/selectserverentry.lua) 和 [`selectserversdialog.lua`](../client/resource/res/script/logic/selectserversdialog.lua) 的诊断函数会对同一信息同时调用 `LogErr` 与 `LogInfo`。再对照 [`FNet.h`](../common/cauthc/net/FNet.h)、[`FNet.cpp`](../common/cauthc/net/FNet.cpp) 与 [`NetConnection.cpp`](../client/FireClient/Application/Framework/NetConnection.cpp) 的枚举、发射和处理分支。

#### 根因

`accountLen=0` 属于服务器状态 probe 的专用连接，而不是此前账号输入被清空。`FNet.cpp` 在用户名为空的 Challenge 分支保存 ServerAttr、关闭该 probe session，并显式回调 `NETOP_SERVERATTR=7`；`NetConnection.cpp` 的对应分支注明“不是错误。只是为了接收ServerAttr”，再经 `NetLoginModule_GetServerInfo` 与 `SetServerLoad` 回传负载。紧随其后的 `NETOP_FIRENET=3` 是关闭该 probe session 的伴随回调。

#### 修复

将诊断规则固定为“日志文本 + 发射点 + 操作码 + 前后事件”联合判读，不能只看字面 `(Error)` 或函数名 `OnAutoFailed`。对于同一条诊断的 `LogErr`/`LogInfo` 镜像，只保留一次因果事件；对于 probe，单独记录 `ServerAttr`、负载回写和关闭回调。

#### 验证

2026-08-03 18:27 的 `mt3_ct.log` 已记录：账号/会话长度为 6、进入 `OpenSelectServerEntry`、服务器列表数量为 1、`loadServerSuccess=true`、选服对话框四个关键控件均已创建，并从 `SelectServersDialog.getInstanceAndShow` 返回。该日志中的 `op=7` 说明接收到了服务状态；随后的 `op=3` 不是登录失败。历史 17:50 样本中的 `NETOP_CONNECT=1` 才是连接失败，应与本次实际的 ServerAttr 回包严格区分。

#### 预防/回滚

新增诊断日志时不要复用错误级别表达正常状态，或至少在统一前缀中显式标注诊断性质；排障报告必须列出发射点和相邻事件。真实账号进入游戏世界仍需以服务端协议和可用性的端到端回归为准，不能用已到达账号输入/选服页面的证据替代。

### 6.8 Canonical 脚本宿主兼容性

#### 现象

canonical 外层脚本在 `Ensure-MT3-Win32-LinkDeps.ps1` 报错后返回失败，但同次底层 MSBuild 日志显示 `0 errors`。

#### 取证/排查

先查看外层 canonical 日志的首个异常，再查看其引用的项目 MSBuild 日志。本次 `build_logs/canonical_debug_current.log` 指向宿主中缺少 `Get-FileHash`；同一日志的 MT3 tail 为 77 warnings、0 errors，CEGUI、FireClient 和 MT3 的子项日志均已成功结束。

#### 根因

`Ensure-MT3-Win32-LinkDeps.ps1` 在比较文件内容时调用 `Get-FileHash`。当前 PowerShell 宿主没有该 cmdlet，导致依赖修复脚本失败；该失败发生在脚本宿主能力层，不是 C++ 编译或链接错误。

#### 修复

把该样本归类为脚本宿主兼容性风险：先检查 `Get-Command Get-FileHash`，再使用满足脚本前置条件的宿主或补齐经验证的兼容实现。不要因外层脚本失败而回退已经成功的 C++ 编译产物，也不要把它记录成代码编译失败。

#### 验证

验证分两层进行：外层脚本须在具备哈希能力的宿主中成功完成；底层构建须分别核对 MSBuild 退出码和 `0 errors`。二者都通过后，才可把 canonical 命令的成功退出码作为完整构建结论。

#### 预防/回滚

在 canonical 入口增加或执行宿主能力预检，并把“首个脚本错误”和“首个 MSBuild 错误”分开记录。回滚脚本兼容性变更时保留原有 v120 构建参数与 SafeChain，不改变 C++ 工具链。

### 6.9 标准化开发、构建与人工回归流程

1. **先分域**：先确定问题是 ABI/构建、渲染状态、资源/Scheme、Lua 绑定、IME 输入、Spine 层级或网络状态探测；不要在未定因时跨域叠加补丁。
2. **回到源定义**：协议和资源回到源定义；CEGUI Lua 回到 `.pkg`；布局问题同时检查 Scheme、look'n'feel、imageset/font、layout 及 Lua/C++ 绑定；生成物只作为验证结果。
3. **按影响面重编**：公共头、renderer、Cocos 或 CEGUI 变更走 SafeChain；仅业务实现变更也至少覆盖实际依赖的 `FireClient -> MT3`。完整命令以 Windows 构建指南和命令速查为准。
4. **先做机械验证，再做运行时取证**：检查工程配置、MSBuild 日志、产物和依赖审计；运行时按事件顺序保留登录、选服、IME、渲染或网络 probe 的最小日志，不以单一日志级别下结论。
5. **人工回归清单**：冷启动、登录首屏、账号输入/焦点切换、选服创建与返回、登录点击响应、常用分辨率、字体、背景/Spine 层级、无临时追踪日志残留，以及真实账号进入游戏世界。前八项是客户端视觉/交互回归，最后一项还需要端到端协议与可用性验证。
6. **记录证据和回滚点**：记录所用 `EngineProfile`、构建层级、日志样本、未覆盖项和可独立回滚的补丁组。已验证、当前可达和待人工/端到端验收必须分开书写。

### 6.10 已识别、但尚未纳入完成清单的动画资源风险
