# 01-编译问题排查

> **适用范围**：MT3 Win32 主线 VS2013 / `v120` / Windows SDK 8.1。
> **原则**：先记录 canonical build 的首个错误与对应日志，再定位工具链、编译、链接、ABI 或运行时依赖。

## 1. 最小取证

```powershell
git status --short
powershell -ExecutionPolicy Bypass -File .\tools\scripts\Check-v120Toolset.ps1
Get-ChildItem .\build_logs -Filter 'msbuild_*_Win32.log' | Sort-Object LastWriteTime -Descending | Select-Object -First 10
```

记录：

- 实际命令、配置、平台和构建模式；
- 进程退出码；
- 第一个失败的 step 与日志路径；
- 首个编译/链接错误，而不是最后一条级联错误；
- `engine.lib`、`FireClient.lib`、`MT3.exe` 的时间戳。

构建入口必须是 `tools/scripts/Build-MT3-Exe-Canonical.ps1`。内部 `client/Build-MT3-v120.ps1` 只用于脚本链路和专项调试。

## 2. 工具链错误

### MSB8020：找不到 v120

直接阻塞点：VS2013 C++ 工具集未安装、`VS120COMNTOOLS` 指向错误目录，或工程被改成其他 toolset。

```powershell
$vcvars = Join-Path $env:VS120COMNTOOLS '..\..\VC\vcvarsall.bat'
Test-Path -LiteralPath $vcvars
powershell -ExecutionPolicy Bypass -File .\tools\scripts\Check-v120Toolset.ps1
```

恢复 VS2013/v120 环境；不要把主线工程改成 v140+ 来消除 MSB8020。

### MSBuild 版本错误

```powershell
$msbuild = if ($env:MT3_MSBUILD_PATH) {
    $env:MT3_MSBUILD_PATH
} else {
    Join-Path ${env:ProgramFiles(x86)} 'MSBuild\12.0\Bin\MSBuild.exe'
}
& $msbuild /version /nologo
```

主版本应为 `12`。如果命中了新版本 MSBuild，先修正 `$env:MT3_MSBUILD_PATH`，不要修改解决方案格式。

### Windows SDK 8.1 缺失

确认 VS2013 安装包含 Windows SDK 8.1，并检查主线 `.vcxproj` 的 SDK/目标平台设置。不要用 WinRT/WP8/vendor 示例工程的配置推翻 Win32 主线事实。

## 3. 编译错误

### C2001：常量中有换行符

若错误集中在中文字符串附近：

1. 检查文件是否为交给 VS2013 `cl.exe` 的 C/C++ 源文件；
2. 检查前三字节是否为 UTF-8 BOM `EF BB BF`；
3. 若原文件应为 UTF-8 BOM，按原换行恢复 BOM；
4. `Rebuild` 受影响工程；
5. BOM 正确后再检查真实字符串拼接、宏和物理换行。

```powershell
Format-Hex -Path SOURCE_FILE | Select-Object -First 1
```

不要把 Markdown、JSON、Lua 或 `.rc` 文件一律转换成 UTF-8 BOM；各文件按原编码写回。

### C1083：找不到头文件

先检查首个缺失头的来源：

```powershell
rg -n --fixed-strings 'MISSING_HEADER' .
```

然后核对当前工程的 `AdditionalIncludeDirectories`、配置条件和相对路径。不要通过把历史绝对 include 路径批量复制到所有工程来修复。

### 源码 NUL 字节

```powershell
powershell -ExecutionPolicy Bypass -File .\tools\scripts\Test-SourceNoNulBytes.ps1 -RepoRoot . -IncludeRoots 'client/FireClient/Application,client/MT3Win32App,engine,common,tools/scripts'
```

按脚本报告定位首个文件，恢复正确文本内容和原编码。

## 4. 链接错误

### LNK1104：打不开 `.lib`

先运行链接依赖补齐脚本：

```powershell
powershell -ExecutionPolicy Bypass -File .\tools\scripts\Ensure-MT3-Win32-LinkDeps.ps1 -Configuration Release -Platform Win32 -Json
```

检查 JSON 中的 `built`、`staged`、`verified` 和对应 `build_logs/ensure-linkdeps_*.log`。不要从未知目录手工复制同名库。

### LNK2001 / LNK2019 / LNK1120：未解析外部符号

按顺序核对：

1. 声明与实现签名、命名空间、调用约定是否一致；
2. 实现源文件是否进入当前配置；
3. 正确的 `.lib` 是否进入 `AdditionalDependencies`；
4. Debug/Release、Win32/x64 和宏分支是否一致；
5. 公共头变更后是否按下游顺序重编。

不使用 `/FORCE` 掩盖符号冲突。

### LNK4098：CRT 冲突

主线基线为 Debug `/MDd`、Release `/MD`。先找出引入其他 CRT 的具体库，再针对该库核对工程配置；不要递归替换全仓 `RuntimeLibrary`。

### LNK2038 或迭代器/运行库不匹配

这通常表示配置、CRT、工具集或宏不一致。确认所有进入最终链接的产物均来自 v120 和同一配置，从最上游不一致的库开始重编。

## 5. ABI 混编与启动崩溃

高风险信号：

- fresh process 初始化期在 `std::map`、`std::vector` 或 `this + offset` 访问处崩溃；
- dump/PDB 中同名类型出现两套 `sizeof` 或成员偏移；
- 只重链 `MT3.exe` 后问题出现；
- `engine.lib`、`FireClient.lib`、`MT3.exe` 时间戳不符合依赖顺序。

恢复顺序：

- `engine/**.h` 或引擎公共 ABI：`Rebuild engine -> Rebuild FireClient -> Build MT3`；
- `client/FireClient/Application/**.h` 公共 ABI：`Rebuild FireClient -> Build MT3`；
- Cocos2d-x 公共 ABI：对应 Cocos 库 -> `engine -> FireClient -> MT3`。

优先执行：

```powershell
powershell -ExecutionPolicy Bypass -File .\tools\scripts\Build-MT3-Exe-Canonical.ps1 -Configuration Release -Platform Win32 -BuildMode SafeChain -MaxParallelJobs 8 -StrictRuntimeAudit
```

## 6. 构建成功但运行失败

### 缺少 DLL 或 runtime audit 失败

```powershell
powershell -ExecutionPolicy Bypass -File .\tools\scripts\Audit-RuntimeDependencies.ps1 -ScanRoots 'client\resource\bin\Release' -ReportPath 'build_logs\runtime-audit-manual-release.json'
Get-ChildItem .\client\resource\bin\Release -Filter '*.dll' | Sort-Object Name
```

以 runtime audit 报告中的第一个 High/缺失项为直接阻塞点。运行目录是 `client/resource/bin/<Configuration>/`，不要只检查中间输出目录。

### 资源仍是 Git LFS pointer

```powershell
rg -a -n 'version https://git-lfs.github.com/spec/v1' client/res_win/res client/resource/bin
git lfs status
```

发现 pointer 后先按真实路径执行 `git lfs pull` 或 `git lfs checkout`，再重新构建/启动。

### 生成 DMP

Win32 入口会在进程当前工作目录生成按日期和时间命名的 `.dmp`。将 DMP、匹配的 EXE/DLL/PDB、日志和构建信息一起保存，按 [DMP 调试与崩溃栈分析](./05-DMP调试与崩溃栈分析.md) 处理。
