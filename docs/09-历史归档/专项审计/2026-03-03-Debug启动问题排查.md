## 问题现象

- `client/resource/bin/Debug/MT3.exe` 启动后闪退或卡死。
- 典型报错：
  - CEGUI `invalidRequestException`（动画 XML 含不支持节点）。
  - `Run-Time Check Failure #0 - ESP was not properly saved`（调用约定不匹配）。
  - 启动日志停在 `GameConfigManager::ApplyConfig` 音频阶段。

## 根因定位

1. CEGUI 动画 XML 使用了 0.7.1 不支持的 `<Event>` 节点。
2. Win32 FMOD 桥接存在调用约定风险，导致栈破坏（ESP 异常）。
3. `FmodAudioPlayer` 初始化失败时缺少充分空指针防御。
4. Win32 启动动画默认读取 `/cfg/video/MT3.wmv`，而当前资源仅有 `MT3.mp4`。

## 修复内容

1. 移除 `res/ui/animations/sample.xml` 中非法 `<Event>` 节点。
2. 修复 FMOD Win32 桥接：
   - 使用 `stdcall` 方式桥接 `_FMOD_System_Create@4`。
   - `GetProcAddress("FMOD_System_Create")` 后按 `__stdcall` 函数指针调用。
3. 强化 `FmodAudioPlayer` 防御：
   - 构造初始化 `pSystem/pChannelGroup`。
   - 初始化与常用接口增加空指针保护，避免初始化失败后二次崩溃。
4. 启动视频回退策略：
   - Win32 先检查 `MT3.wmv` 是否存在，不存在则回退 `MT3.mp4`。

- `CCHttpRequest::setResponseCallback` 的回调对象必须是 `CCObject`。
- 直接把非 `CCObject` 类作为回调目标，容易引发编译错误或调用约定/栈破坏问题（典型为 RTC 的 ESP 异常）。
- 建议固定使用 `CCObject` 代理回调，再转发到业务管理类处理。

## 主城高密度场景时装模型“发白/发虚”排查沉淀（2026-03-07）

### 1. 现象与边界

- 现象：建邺城等高密度地图中，使用时装模型的角色/NPC 会出现“泛白、发虚、局部丢层”。
- 对照：东海湾等低密度地图通常显示正常。
- 结论：不是“地图配置本身不同”导致，而是“高负载下纹理句柄时序/可用性”触发渲染降级失败。

### 2. 根因链路（C++）

1. `ComponentSprite` 在模型切换时，`m_vShaderType` 仅 `resize` 未清零，旧模型染色状态可能残留到新模型层。
2. `type=1/type=3` 染色路径都依赖 `pBigPicPart`（分区贴图），旧逻辑仅在部分分支处理缺失回退。
3. `CCShader_PositionTextureColorHSV` 片元 shader 固定采样 `u_texture_part`；当 part 纹理缺失但仍走 HSV 分支时，会把整模型按错误分区重染，表现为发白/发虚。
4. 早期修复只覆盖 `iShaderType==3` 的回退，未覆盖 `iShaderType==1`，高密度场景下仍会复现白化。
5. 高密度场景贴图回收/异步加载更频繁，`part` 贴图“句柄非 0 但实际不可用”的窗口更大，问题被显著放大。
6. `DrawPicture` 普通贴图分支未显式 `push` 默认 shader，上一笔 HSV/ETC draw 的 shader 可能串到后续 draw，导致非时装对象也被错误着色。

### 3. 修复清单（仅 C++，未改 Lua/素材）

#### 3.1 `engine/sprite/nucomponentsprite.cpp`

- `SetModel`：`m_vShaderType.resize(m_nLayerCount)` 改为 `m_vShaderType.assign(m_nLayerCount, 0)`，彻底清空旧 shader 状态。
- `RenderALayer`：
  - `hasPartTexture` 判定增加 `pRenderer->IsTextureExist(pic.pBigPicPart->handle)`。
  - `iShaderType!=0` 且分区贴图不可用时，统一回退普通渲染（`iShaderType=0`）。
  - `DrawPicture` 失败重试改为同时检查主贴图与分区贴图句柄；检测失效后 `assureLoadPic` 重载，并重新组装 `handle/handlePart/iShaderType` 再绘制。
- `SetDyePartIndex`：
  - 增加 `level/part` 越界保护。
  - `part>0 && m_bDyeEnable<=1` 时清位并恢复默认参数。
  - `GetDyeParam` 失败时回滚该 part 的 shader 位并恢复默认参数，避免脏状态残留。

#### 3.2 `engine/renderer/nucocos2d_render.cpp`

- `DrawPicture` 增加 `usePartShader` 守卫：
  - 仅当 `param.iShaderType!=0 && texInfoPart.m_pTexture!=NULL && !isEtcTexture` 才走 HSV 染色 shader。
  - 否则强制走普通贴图 shader，避免 `u_texture_part` 采样空纹理导致整模型错误重染。
- 普通贴图（非 ETC、非 HSV）分支恢复显式 `pushShader(kCCShader_PositionTextureColor)`，并在末尾 `popShader`，消除 shader 状态串帧污染。

### 4. 为什么“同屏数量多”会放大问题

- 同屏越多，动画帧切换与纹理申请/回收越频繁。
- 分区贴图（part texture）在某些帧可能先于主贴图失效或延迟就绪。
- 旧逻辑把 part 贴图缺失视为致命错误，导致整层直接不画；高密度地图触发概率显著增加。

## 建邺城时装 NPC 泛白/发虚（二次根因修复，2026-03-08）

### 12. 根因结论（本轮新增）

- 触发条件：高密度地图（建邺城）里，时装/染色模型显著多于普通地图。
- 关键原因：P1 纹理清晰化后，`/shape/` 路径贴图统一进入了 mipmap 策略，导致**染色分区图**（`...part`）也被错误启用 mipmap。
- 结果：分区图是离散掩码，远距离/小尺寸采样时被 mipmap 混色，染色 shader 分区判定被污染，表现为人物整体发白、发虚、边缘模糊。

### 13. C++ 修复点（仅客户端 C++，未改 Lua/素材）

- `engine/renderer/nucocos2d_render.cpp`
  - 新增 `IsDyePartTextureUri(...)`：识别角色/坐骑分区贴图（后缀 `part`）。
  - 在 `ApplyTextureQualityPolicy(...)` 中对分区贴图强制走 `GL_LINEAR`（不生成 mipmap，不做各向异性）。
  - `IsTextureExist(...)` 改为校验“句柄存在 + 至少一个底层 `CCTexture2D` 有效且 `name!=0`”，避免空壳纹理被误判为可用。
  - `DrawPicture(...)` 增加纹理有效性门槛：主纹理 `name==0` 直接跳过；分区 shader 仅在分区纹理对象有效时启用。
- `engine/engine/nuanimanager.cpp`
  - `assureLoadPic(...)` 中主图/分区图 `loaded` 状态改为“仅当 `handle != INVALID_PICTURE_HANDLE` 才置 true”，避免加载失败被标记已就绪。
