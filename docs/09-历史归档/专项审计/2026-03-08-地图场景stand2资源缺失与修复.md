## 结论

本次问题的直接触发条件是：

1. 场景对象会周期性进入 `eActionStandRandom`。
2. Lua 将 `eActionStandRandom` 直接映射为 `stand2`。
3. 当前资源中，大量时装 `body/bodyonly/stand2.ani` 缺失，少量武器 `weapon/210/stand2.ani` 也缺失。
4. 缺失后引擎会尝试回退到 `/cfg/error/discard.ani`，但回退链中的图片前缀仍沿用原始缺失动作路径，导致错误占位资源不能完整命中。

因此，当前问题的核心不是“人多导致性能差”，而是“人多时更多对象触发 `stand2`，而 `stand2` 资源集不完整，且错误回退链实现不完整”。

## 根因链路

### 1. 场景随机站立会触发 `stand2`

- `SceneObject::StandRandomAction()` 会每隔一段时间尝试播放 `eActionStandRandom`。
- 文件：`client/FireClient/Application/SceneObj/SceneObject.cpp`

### 2. `eActionStandRandom` 在 Lua 中被映射成 `stand2`

- `GetActionName()` 中：
  - `eActionStand` -> `stand1`
  - `eActionStandRandom` -> `stand2`
  - `eActionBattleStand` -> `stand3`
- 文件：`client/resource/res/script/globalfunctionsforcpp.lua`

### 3. 时装主身体层正好使用 `bodyonly`

- 场景对象身体层组件名固定为 `bodyonly`。
- 文件：
  - `client/FireClient/Application/Common/SceneCommon.h`
  - `client/FireClient/Application/SceneObj/SceneObject.cpp`

### 4. 缺失 `stand2.ani` 后会进入错误占位回退

- `AniManager::syncLoadAni()` 在原始 `.ani` 读取失败后，会尝试改读 `/cfg/error/discard.ani`。
- 文件：`engine/engine/nuanimanager.cpp`

### 5. 错误占位回退链存在实现缺陷

- 虽然改读了 `/cfg/error/discard.ani`，但传给 `LoadAniFromPack()` 的 `packbaseuri` 仍然是原始缺失动作路径的 base。
- `LoadAniFromPack()` 会基于这个 `packbaseuri` 继续拼接图片前缀。
- 结果是：错误占位 ani pack 可能读到了，但它引用的图片路径仍指向原缺失目录，错误占位图不能完整命中。
- 文件：`engine/engine/nuanimanager.cpp`

### 6. 这不是贴图内存降级问题

- 当前配置中 `TotalPhysMemoryLimit=563200`，机器总物理内存远高于该值。
- 代码判断是 `limit < totalMemory` 时设置 `CCImage::IsNormal(true)`。
- 因此当前运行不会走半尺寸贴图降级路径。
- 文件：
  - `client/FireClient/Application/Framework/GameApplication.cpp`
  - `engine/engine/nuengine.cpp`
  - `cocos2d-2.0-rc2-x-2.0.1/cocos2dx/platform/CCImageCommon_cpp.h`

## 可落地修复方案

### 方案 A：资源热修复，先止血

适用目标：最快恢复场景显示，不再出现当前白模/发虚问题。

执行内容：

1. 对上面 `44` 个缺失路径，逐一补齐 `stand2` 资源。
2. 若原始动画资源暂时拿不到，先做临时热修：
   - `stand1.ani` 复制为 `stand2.ani`
   - `stand1_res*.png` 复制为 `stand2_res*.png`
   - 如果目录内存在 `stand1_res*.pngpart`，同步复制为 `stand2_res*.pngpart`
3. 这一步是临时修，不是最终美术交付；目标是让随机站立动作至少落回合法静态待机，不再命中错误占位链。

为什么这一步可行：

- 当前缺失目录基本都满足 `stand1` 存在。
- `stand1` 与 `stand2` 都属于站立态资源，临时复用不会破坏渲染链路，只会让“随机站立”退化成“普通站立”。

交付标准：

- 重新进入拥挤地图后，`mt3_ct.log` 中不再出现 `/model/*stand2.ani` 缺失。
- 截图中的角色主身体层不再出现大面积白模。

### 方案 B：资源正式补齐，恢复正确动作表现

适用目标：恢复真实的随机站立表现，不再用 `stand1` 代替。

执行内容：

1. 从原始美术资源源包补齐 `stand2.ani` 及其配套图片。
2. 优先级按影响面执行：
   - 第一批：本报告中的 `41` 个时装身体层
   - 第二批：`3` 个 `weapon/210`
   - 第三批：仓库中其他虽然未在本次日志直接命中、但同样缺 `stand2` 的 NPC/Boss 目录

建议优先顺序：

1. `fashion-*5`
2. `fashion-*6`
3. `fashion-*4`
4. `weapon/210`

### 方案 C：代码兜底，避免未来再被同类资源缺口打穿

适用目标：即使以后又有模型漏了 `stand2`，客户端也不再出现同类白模问题。

建议改动 1：

- 在动作装载入口增加模型级兜底：
  - 当请求动作名为 `stand2`
  - 且 `SpriteManager::GetAction(model, L"stand2") == NULL`
  - 自动回退到 `stand1`
- 最合适的落点：
  - `engine/sprite/nucomponentsprite.cpp`
  - `ComponentSprite::SetDefaultAction()`
  - `ComponentSprite::PlayAction()`

原因：

- 这里已经拿到了 `modelName`，可做模型级判断。
- 不需要把 Lua 的全局 `GetActionName()` 改成带模型上下文的函数。

建议改动 2：

- 修复 `discard.ani` 的 baseuri 传递：
  - 当 `syncLoadAni()` 或异步 XAP 读线程回退到 `/cfg/error/discard.ani` 时
  - 传给 `LoadAniFromPack()` 的 `packbaseuri` 也必须改为 `/cfg/error/discard`
  - 不能继续沿用原始缺失动作的 baseuri

原因：

- 这能保证错误占位资源在极端情况下也能完整显示，避免“ani pack 读到但图片路径仍失效”。

### 不建议的处理方式

- 不建议先调 `TotalPhysMemoryLimit` 或纹理内存阈值：与当前问题无关。
- 不建议先改资源根路径：当前 Debug 资源根路径已验证正确。
- 不建议只清日志不修资源：问题会稳定复现。

### 包裹和坐骑界面断言问题的最终定位（2026-03-09 补充）

`Debug` 版原先弹出的：

```text
Assertion Failed in sprite\nuspritemanager.cpp
Expr is 'hardref.IsValid()'
```

根因已经确认，不是资源缺失，而是“坐骑层动作过滤”和“Hold 语义”不一致：

1. 包裹预览和坐骑界面都会先创建角色 `UISprite`。
2. `ComponentSprite::GetActionNames()` 会把动作链里的 `link action` 全部收集进 `ActionNameSet`，其中可能同时包含 `stand*` 和 `riding_*`。
3. 骑乘层在 `Component::GetAni()` 中本来就只消费 `riding_*`；遇到非 `riding_*` 会直接 `m_needDraw = 0` 并跳过。
4. 旧逻辑下，`Component::PrefetchAction()` 在骑乘层遇到非 `riding_*` 时会提前 `return XPPR_OK`。
5. `Component::HoldAction()` 把 `XPPR_OK` 当作“全部 linked action 已可持有”，随后对 `m_anis[*it]` 执行 `XPASSERT(hardref.IsValid())`，从而在非 `riding_*` 条目上触发断言。

已落地的引擎侧最小修复：

1. `Component::PrefetchAction()`：骑乘层遇到非 `riding_*` 从“提前返回”改为“`continue` 跳过”，不再错误返回 `XPPR_OK`。
2. `Component::HoldAction()`：骑乘层显式跳过非 `riding_*`，并对 `hardref` 增加无效保护，避免无意义断言弹窗。

### 剩余问题能否继续热修

结论：不能按 `stand2 -> stand1` 这类规则继续做“无风险热修”。

原因如下：

1. 剩余 `69` 条里，有 `30` 条连父目录都不存在，属于整目录级缺失，无法从同目录复制。
2. 另外 `39` 条虽然父目录存在，但缺的是：
   - 特效配置 `.eff.inf`
   - 贴图格式 `.dds`
   - 或独立动画 `.ani`
3. 这些文件不像 `stand2` 一样存在明确的一对一退化源文件，不能凭名字猜测复制：
   - 例如 `acc10-hg` 目录里缺的是 `Cc.bdgj_.eff.inf`，但现有文件是 `Cc.bdgj_1.eff.inf`、`Cc.bdgj_2.eff.inf`
   - 例如 `acc1-dt` 目录里缺的是 `Cc.phyj1.eff.inf`、`Cc.phyj2.eff.inf`，但现有文件是 `Cc.phyj.eff.inf`
   - 例如 `targetring_res000.dds` 缺失时，同目录只有 `targetring_res000.png`，不能直接通过改扩展名伪造 `.dds`
4. 地图缺失的 `goto.dat`、`npc.dat` 属于结构化数据文件，也不能靠占位复制安全替代。

因此，剩余问题的处理方式只能分两类：

- 第一类：回源补齐原始资源
- 第二类：在代码层做更稳健的缺资源降级或禁用策略，但不能靠猜测性复制文件名解决
