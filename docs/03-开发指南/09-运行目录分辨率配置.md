# 运行目录分辨率配置说明

## 1. 适用范围

本文只说明 Win32 客户端运行目录 `client/resource/bin/<Configuration>/` 下两个分辨率配置文件的职责、格式和风险：

- `frameSize.txt`
- `frameResolutionSize.txt`

这两个文件都会在运行目录被 `MT3.exe` 直接按相对路径读取，因此修改后无需重新打包资源，但会直接影响启动行为与运行时适配结果。

---

## 2. 代码主链

当前 Win32 启动链中，这两个文件分属两个不同阶段：

1. `client/MT3Win32App/main.cpp`
   - 读取 `frameSize.txt`
   - 调用 `CCEGLView::setFrameSize(w, h)` 设置窗口尺寸
2. `client/FireClient/Application/Framework/ResolutionAdapter.cpp`
   - 读取 `frameResolutionSize.txt`
   - 计算逻辑分辨率、UI 逻辑分辨率和场景渲染分辨率

因此：

- `frameSize.txt` 控制窗口有多大
- `frameResolutionSize.txt` 控制窗口内部按什么逻辑分辨率进行适配和渲染

---

## 3. frameSize.txt

### 3.1 作用

`frameSize.txt` 用于设置 Win32 客户端窗口的客户区尺寸。若文件缺失或解析失败，当前代码会回退到默认值 `1280x720`。

对应代码入口：

- `client/MT3Win32App/main.cpp`

### 3.2 当前推荐写法

推荐始终使用最保守的空格分隔格式：

```txt
1280 720
```

当前已修复后的启动层兼容以下写法：

```txt
1280 720
1280x720
1280X720
1280,720
1280
720
```

说明：

- 兼容分隔符：空格、`x`、`X`、逗号、制表、换行
- 若宽高没有同时解析成功，启动层会保留默认 `1280x720`

### 3.3 历史风险

旧版 Win32 启动代码只按空格分隔 `frameSize.txt`。若写成 `1600x900` 这类格式，第一次能读出 `1600`，第二次会得到空指针，可能触发 Debug CRT 断言：

```txt
Expression: nptr != NULL
```

因此：

- 对新二进制：`1600x900` 已兼容
- 对旧二进制：仍建议只写 `1280 720` 这种空格分隔格式

---

## 4. frameResolutionSize.txt

### 4.1 作用

`frameResolutionSize.txt` 用于覆盖运行时内部的三条分辨率链：

1. 全局逻辑分辨率
2. UI 逻辑分辨率
3. 场景渲染分辨率

对应代码入口：

- `client/FireClient/Application/Framework/ResolutionAdapter.cpp`

### 4.2 文件格式

该文件当前通过 `std::fscanf(fp, "%ld", ...)` 读取，因此推荐且实际上要求使用“空白分隔整数”格式，不要写 `x` 或逗号。

支持 2 / 4 / 6 个整数：

```txt
renderW renderH
renderW renderH uiW uiH
renderW renderH uiW uiH sceneW sceneH
```

含义如下：

- 第 1、2 个数：全局逻辑分辨率目标
- 第 3、4 个数：UI 逻辑分辨率目标
- 第 5、6 个数：场景渲染分辨率目标

### 4.3 当前推荐写法

安全基线：

```txt
1136 720 1080 720
```

若需要把场景渲染也锁到固定基线，必须补齐第 5、6 个数，例如：

```txt
1280 720 1280 720 1280 720
```

或：

```txt
1136 720 1080 720 960 540
```

### 4.4 重要行为差异

当前客户端源码中：

- 若只写前 2 个数：只覆盖全局逻辑分辨率
- 若写前 4 个数：再额外覆盖 UI 逻辑分辨率
- 若不写第 5、6 个数：场景渲染分辨率不会自动继承前 2 个数，而是继续走默认分支

在 Win32 默认分支下，这通常意味着：

- 场景渲染尺寸更接近当前屏幕/视口尺寸
- UI 和场景可以分离，不会因为 UI 调整而自动降低场景分辨率

---

## 5. 两个文件的组合关系

典型组合如下：

### 5.1 固定窗口 1280x720，只调逻辑/UI 基线

`frameSize.txt`

```txt
1280 720
```

`frameResolutionSize.txt`

```txt
1136 720 1080 720
```

效果：

- 窗口固定为 `1280x720`
- UI 与逻辑坐标系按较低基线参与适配
- 场景渲染仍不单独降采样

### 5.2 固定窗口 1280x720，同时锁场景渲染基线

`frameSize.txt`

```txt
1280 720
```

`frameResolutionSize.txt`

```txt
1280 720 1280 720 1280 720
```

效果：

- 窗口固定为 `1280x720`
- 逻辑、UI、场景三条链都锁到同一基线

### 5.3 高分屏窗口下保留 UI 清晰度，同时单独降低场景成本

`frameSize.txt`

```txt
1600 900
```

`frameResolutionSize.txt`

```txt
1136 720 1080 720 960 540
```

效果：

- 窗口变大
- UI 逻辑分辨率仍保持较高基线
- 场景单独降到 `960x540`
- 更适合验证“UI 清晰度”和“场景性能”分离策略

---

## 6. 常见误区

### 6.1 把 frameResolutionSize.txt 当成窗口尺寸文件

错误理解：

- 改 `frameResolutionSize.txt` 就能改变窗口大小

真实行为：

- 改窗口大小要改 `frameSize.txt`
- `frameResolutionSize.txt` 只影响窗口内部的适配和渲染

### 6.2 只写前 4 个数就以为场景分辨率也被改了

错误理解：

- `1136 720 1080 720` 会让场景也降到 `1136x720`

真实行为：

- 当前客户端源码不会自动把前 2 个数继承到场景渲染目标
- 若要改场景渲染，必须写满第 5、6 个数

### 6.3 在 frameResolutionSize.txt 中使用 `x` 或逗号

错误写法：

```txt
1136x720 1080x720
```

```txt
1136,720,1080,720
```

真实风险：

- 当前 `fscanf("%ld")` 只接受空白分隔整数
- 这种格式可能导致只读到第一个数，后续值失效

---

## 7. 运行目录同步来源

这两个文件是运行目录内的独立配置文件，**不在** `client/Build-MT3-v120.ps1` 的 runtime-sync 覆盖范围内（该脚本 `Invoke-RuntimeSync` 的 `$runtimeMap` 只同步 `MT3.exe` 与各 DLL 等 PE 二进制，对 `frameSize.txt`/`frameResolutionSize.txt` 零引用）。

因此：

- 手动改运行目录可直接验证本地效果
- 重新执行构建脚本不会覆盖这两个文件；如需重置，需手工删除或修改

---

## 8. 推荐排查步骤

修改这两个文件后，建议按以下顺序检查：

1. 确认运行目录中的实际文件内容，而不是只看编辑器缓冲区
2. 启动 `client/resource/bin/<Configuration>/MT3.exe`
3. 观察窗口尺寸是否符合 `frameSize.txt`
4. 再观察 UI 尺寸、点击映射和场景清晰度是否符合 `frameResolutionSize.txt`

建议命令：

```powershell
Get-Content -Raw client/resource/bin/Debug/frameSize.txt
Get-Content -Raw client/resource/bin/Debug/frameResolutionSize.txt
```

---

## 9. 结论

这两个文件分别负责“外层窗口尺寸”和“内部分辨率契约”，不能混用：

- `frameSize.txt` 决定窗口大小
- `frameResolutionSize.txt` 决定逻辑/UI/场景三条适配链

默认建议：

```txt
frameSize.txt               => 1280 720
frameResolutionSize.txt     => 1136 720 1080 720
```

若目标是降场景渲染成本，必须显式补齐 `frameResolutionSize.txt` 的第 5、6 个整数。
