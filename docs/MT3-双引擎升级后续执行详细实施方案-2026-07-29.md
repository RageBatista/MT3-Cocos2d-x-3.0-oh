## 4. P0 详细实施步骤

### 4.1 P0-01：证据基线与动态依赖

已执行的严格审计命令：

```powershell
powershell -ExecutionPolicy Bypass -File .\tools\scripts\Audit-RuntimeDependencies.ps1 `
  -ScanRoots 'client\resource\bin\Debug' -FailOnIssues
```

后续每次最终链接后重复执行，并保留以下字段：`DriftHighCount`、`MissingDepHighCount`、`RuntimeImportHighCount`、`FamilyHighCount`。四项必须全部为 0。

PE 直接导入表只有系统 DLL、`websockets.dll`、`libcurld.dll` 和 Debug CRT。`cocos2d-x-3.0-oh`、`CEGUI-0.7.9-r5` 由项目中的静态库依赖提供，不在运行目录补放同名 DLL。

回滚点：只回滚本工作包产生的报告；不替换 `.exe/.dll/.lib` 二进制。

### 4.2 P0-02：恢复 4 类 Falagard 扩展元素

目标元素：

- `BorderEnableProperty`
- `BorderColourProperty`
- `DefaultBorderEnableProperty`
- `DefaultColourEnableProperty`

工程证据表明旧实现完整存在于 `dependencies/cegui/CEGUI/src/falagard/CEGUIFalagard_xmlHandler.cpp` 和 `CEGUIFalTextComponent.cpp`，因此优先移植旧行为，不批量删除 LookNFeel 标签。

实施步骤：

1. 对比旧树和 `tools/CEGUI-0.7.9-r5/cegui` 中 `TextComponent` 的字段、getter/setter、XML 序列化和 handler 分发。
2. 在 0.7.9-r5 源码补齐四个字段及其 XML element 常量、开始元素分支、序列化逻辑。
3. 保持 0.7.9 的基类接口和所有权模型，不复制旧工程文件或二进制。
4. 使用 v120 重编 `cegui-0.7.9_d.lib`，随后按 `CEGUI -> engine -> FireClient -> MT3` 重建 Debug。
5. 清理当前会话日志后冷启动，确认四类错误从 1209 次降为 0。

验收条件：四类错误均为 0；文本边框、默认颜色和关闭边框三种状态有 GPU 截图；Debug 60 秒无 WER/转储。

回滚点：CEGUI 源码单独提交；失败时回滚该提交并恢复对应静态库的 canonical 重建产物。

### 4.3 P0-03：恢复 `CompnentTip` 工厂链

当前 `CEGUICompnentTip.cpp` 已进入 `cegui-0.7.9.win32.vcxproj`，`CEGUISystem.cpp` 也存在 `addFactory<TplWindowFactory<CompnentTip>>`，运行时报工厂未注册，说明问题更可能位于初始化调用顺序、编译宏或工厂注册路径，而不是源文件完全缺失。

实施步骤：

1. 在 `CEGUI::System` 初始化前后用断点确认 `addStandardWindowFactories()` 是否执行。
2. 检查 `CompnentTip::WidgetTypeName` 是否严格为 `CEGUI/CompnentTip`，与 Scheme `TargetType` 保持一致。
3. 核对 `Falagard/CompnentTip` renderer factory 是否与窗口 factory 同时注册。
4. 修复初始化顺序或漏编对象后重建 CEGUI 全链。
5. 验证默认 tooltip 建立、文本尺寸、定位、目标控件切换和销毁。

验收条件：工厂错误由 1 次降为 0；默认 tooltip 显示且不泄漏；连续创建/销毁 100 次无异常。

### 4.4 P0-04：收敛 29 个未注册 Imageset

当前高频名称包括 `awaiguanyichu`、`ccuijscj`、`ccranse`、`qihun`、`common_sangongge3`、`zuoqiwenshihecheng` 等。

每个名称按以下顺序处理：

1. 在 `client/resource/res/ui/imagesets` 查找同名 `.imageset`。
2. 存在且图片实物有效：在实际启动 Scheme 中注册，不复制图片。
3. 名称不同但像素区域完全一致：新增最小别名 `.imageset`，记录来源坐标和哈希。
4. 只在历史 LookNFeel 出现且当前业务无引用：先追踪 layout/Lua/C++ 调用，再决定清理历史声明。
5. 缺少源图片或坐标证据：登记阻塞项，不创建空白占位图。
6. 每批最多处理 5 个名称，冷启动后比较错误计数，避免一次改动掩盖回归。

静态检查：

```powershell
powershell -ExecutionPolicy Bypass -File `
  .\.agents\skills\cegui-layout-integration\scripts\validate-cegui-resources.ps1 `
  -RepoRoot . -Json

powershell -ExecutionPolicy Bypass -File `
  .\tools\scripts\Test-MT3-ResourceUiGate.ps1 `
  -RepoRoot . -SkipUnpacked -SkipPatchLayout -Json
```

第二条命令先生成 `build_logs/resource-ui-gate.json`，再在脚本内部对比现有 baseline；不要脱离 gate 报告单独调用 baseline helper。

验收条件：29 个名称和 611 次事件全部归零；631 个 `.imageset` 的图片实物引用仍为 0 缺失；无新增资源基线阻塞。

回滚点：每批 Scheme/imageset 资源单独提交；图片源文件、声明文件和 Scheme 注册必须同批回滚。

### 4.6 P0-06：登录黑屏与 Renderer 闭环

实施步骤：

1. 在登录背景创建、纹理上传、GeometryBuffer 提交、裁剪、Blend/Depth/Scissor 状态和最终 `Director::drawScene()` 设置断点。
2. 对登录背景纹理记录源尺寸、GL texture id、pixel format、alpha、UV、viewport 和实际 draw call 数。
3. 在 CEGUI 绘制前后保存并比较 OpenGL 状态，重点核对 viewport、scissor、blend function、active texture、shader/program 和 framebuffer。
4. 验证 `beijingtu1-10` 中至少三张不同格式图片，覆盖 JPEG 与 PNG。
5. 分别关闭 UI、名称绘制和背景绘制进行单变量对照，锁定黑屏发生在资源加载、CEGUI 几何生成还是最终合成。
6. 使用真实 OpenGL 帧捕获或屏幕像素证据验收；GDI `CopyFromScreen` 结果只作辅助。

验收条件：登录背景、账号输入、服务器选择和进入按钮可见；输入/鼠标事件正确；连续启动 3 次一致；1024x768、1280x720、1920x1080 无裁剪或比例错误；无新增 CEGUI Error、GL error、WER 或转储。

| FPS | 旧版同场景 | 不低于基线 90% | 相同地图/角色/特效采样 |
| 内存 | 旧版峰值 | 增长小于 15% | 启动、入世界、战斗、切场景 |
| 启动时间 | 旧版到可交互 | 增长小于 20% | 至少 10 次，报告 P50/P95 |
| DrawCall | 旧版同页面 | 增长小于 10% | 登录、主界面、战斗 |
| 稳定性 | 无旧阻断 | 8 小时长稳无崩溃 | WER、转储、内存曲线 |
| 包体 | 旧版平台包 | 增长小于 20% | APK/IPA/Win32 分发目录 |

发布前必须完成 clean checkout 构建、产物哈希、依赖审计、核心业务矩阵、性能报告、长稳、灰度计划和回滚演练。

## 7. 风险、应对与回滚

| 风险 | 等级 | 触发信号 | 应对 | 回滚点 |
| --- | --- | --- | --- | --- |

| ABI 混编复发 | 致命 | 初始化期容器/成员访问崩溃 | CEGUI/Cocos/engine/FireClient 全链 SafeChain | clean 构建标签和产物哈希 |

## 8. 证据与状态更新规则

每个 WBS 完成后，同步更新综合方案 §8，并记录：

1. 执行命令和退出码。
2. 配置、EngineProfile、工具链版本。
3. 产物路径、大小、时间和 SHA256。
4. 日志路径、首个错误和错误计数变化。
5. 截图或帧捕获路径。
6. WER/转储新增数量。
7. 已知未覆盖边界和回滚提交。

状态变更规则：

- `[未启动] -> [进行中]`：已有责任人、输入和首个执行证据。
- `[进行中] -> [已完成]`：本工作包全部退出条件通过。
- 任一退出条件失败：保持 `[进行中]`，不得用“主体完成”代替验收。
