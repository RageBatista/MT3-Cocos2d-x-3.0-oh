# SpriteEditor 架构分析

> **当前可验证源码**：`SpritePackCoreService.*`、`SpritePackTypes.h`、`SpriteEditorOperationUi.*`、`SpriteEditorViewInteractionUtils.*`、`SpriteEditorViewRenderUtils.*`。
> **缺失边界**：`SpriteEditorDoc.cpp`、`SpriteEditorView.cpp`、完整工程、对话框源码和默认 `pack.ini` 当前未出现。
> **文档索引**：[docs/07-参考文档/02-文档索引.md](../../../07-参考文档/02-文档索引.md)

## 1. 当前增量架构

```text
历史 Doc/View 宿主（当前源码缺席）
  -> SpriteEditorOperationUi
  -> SpriteEditorViewInteractionUtils
  -> SpriteEditorViewRenderUtils
  -> SpritePackCoreService
       -> SpritePackTypes
       -> Nuclear render target / texture output
       -> ANI conversion output
```

当前可见源码证明工具已将部分 UI、视图交互、渲染和打包责任抽离到独立辅助/service。因此旧“所有功能集中在一个 God Object”不再适合作为当前结论。

## 2. 组件职责

| 组件 | 可验证职责 |
| --- | --- |
| `SpritePackCoreService` | 图集建立、MaxRects 装箱、大图尺寸、图片排列与 ANI 转换。 |
| `SpritePackTypes` | 打包输入/中间结果的数据类型。 |
| `SpriteEditorOperationUi` | 工具操作的 UI 结果呈现/辅助。 |
| `SpriteEditorViewInteractionUtils` | 视图交互和坐标/命中辅助。 |
| `SpriteEditorViewRenderUtils` | 视图渲染辅助。 |

## 3. 历史背景的使用方式

旧报告中的装备层 handler 数、大函数行数、SOLID 评分和重构工期：

- 可用于理解抽取 service/helper 的背景。
- 不用于宣告当前代码仍具有完全相同的统计。
- 需要对当前完整架构下结论时，先获取完整源码/工程并重新度量。

## 4. 打包算法层

`BuildAtlas()` 顺序调用：

```text
RectPacking
  -> GetBigPicSize
  -> PicArrange
```

`RectPacking()` 当前日志明确使用 MaxRects 风格装箱，并检查单图超过最大纹理尺寸的失败。

`WriteConvertedAni()` 是与 `BuildAtlas()` 分离的独立方法，不在上述调用链中；当前全仓 C/C++ 源码未发现其调用者。

## 5. 主要风险

- 源图片 ID 与 ANI 帧/方向/装备层映射错位。
- 图集边界渗色、透明通道和纹理上限。
- render target 创建/压栈/弹栈失败后的状态清理。
- 部分输出被误当成成功产物。
- 调用方 `pack.ini` 与实际输入/输出目录不一致。

## 6. 维护规则

1. 打包问题先落到 `SpritePackCoreService` 和调用方真实配置。
2. 视图交互或渲染问题先落到对应 helper，不与打包算法混改。
3. 工具整体 Doc/View 或对话框结论保留“阶段性研究”标签。
