## 概述

本文档定义了 CEGUI 0.7.9-r5 项目文档的长期维护机制，确保文档与项目代码持续保持同步。通过建立标准化的版本管理、审查流程、自动化验证和反馈渠道，提升文档质量和可维护性。

### 维护目标

- **一致性**: 文档与代码保持同步
- **准确性**: 文档内容准确反映项目状态
- **及时性**: 文档随代码变更及时更新
- **可追溯性**: 所有文档变更可追溯
- **质量可控**: 通过审查和验证确保质量

## 文档版本管理

### 版本号格式

采用语义化版本控制（Semantic Versioning）：

```
v主版本号.次版本号.修订号
```

- **主版本号（Major）**: 文档结构重大变更，不向后兼容
- **次版本号（Minor）**: 新增功能章节或重要内容更新，向后兼容
- **修订号（Patch）**: 小幅修改、错误修正、格式调整

**示例**:
- `v1.0.0` - 初始版本
- `v1.1.0` - 新增自动化验证章节
- `v1.1.1` - 修正版本号格式错误

### 最后更新日期格式

采用 ISO 8601 标准日期格式：

```
YYYY-MM-DD
```

**示例**:
- `2026-01-28` - 2026年1月28日

### 版本变更记录格式

每个文档应包含版本变更记录（Changelog），格式如下：

```markdown
## 版本历史（Version History）

| 版本 | 日期 | 变更类型 | 变更说明 | 作者 |
| --- | --- | --- | --- | --- |
| v1.1.0 | 2026-01-28 | 新增 | 新增自动化验证章节 | 张三 |
| v1.0.1 | 2026-01-25 | 修正 | 修正版本号格式错误 | 李四 |
| v1.0.0 | 2026-01-20 | 初始 | 初始版本发布 | 王五 |
```

**变更类型**:
- **初始**: 首次发布
- **新增**: 新增内容
- **修改**: 修改现有内容
- **删除**: 删除内容
- **修正**: 修正错误
- **重构**: 结构调整

### 版本管理最佳实践

#### 1. 版本发布流程

```
草稿 → 审查 → 批准 → 发布 → 归档
```

#### 2. 版本命名规范

- **草稿版本**: `vX.X.X-draft`（如 v1.1.0-draft）
- **发布版本**: `vX.X.X`（如 v1.1.0）
- **归档版本**: `vX.X.X-archived`（如 v1.0.0-archived）

#### 3. 文件命名规范

文档文件名应包含版本信息：

```
序号-文档标题-版本号.md
```

**示例**:
- `01-编译构建流程-v1.2.0.md`
- `02-环境准备-v1.0.0.md`

#### 4. 版本控制策略

- **主分支**: 包含最新稳定版本的文档
- **开发分支**: 包含正在开发的文档
- **归档分支**: 包含历史版本的文档

#### 5. 版本标签（Tag）

每次发布时创建 Git 标签：

```bash
git tag -a docs-v1.1.0 -m "文档版本 v1.1.0 发布"
git push origin docs-v1.1.0
```

## 文档审查流程

### 审查触发条件

文档在以下情况必须进行审查：

| 触发条件 | 审查类型 | 审查级别 |
| --- | --- | --- |
| 新文档创建 | 完整审查 | 高 |
| 文档结构重大变更 | 完整审查 | 高 |
| 文档内容重要更新 | 部分审查 | 中 |
| 文档小幅修改 | 快速审查 | 低 |
| 定期审查（每季度） | 完整审查 | 中 |

### 审查检查清单

#### 技术准确性检查

- [ ] 代码示例可运行
- [ ] 技术描述准确无误
- [ ] 命令行指令正确
- [ ] 路径和文件名正确
- [ ] 版本号与实际一致

#### 内容完整性检查

- [ ] 所有章节完整
- [ ] 必要的示例和图表齐全
- [ ] 参考链接有效
- [ ] 附录和索引完整

#### 格式规范检查

- [ ] Markdown 格式正确
- [ ] 标题层级合理
- [ ] 代码块语言标注正确
- [ ] 表格格式规范
- [ ] 链接可点击

#### 语言表达检查

- [ ] 语言简洁明了
- [ ] 术语使用一致
- [ ] 无错别字和语法错误
- [ ] 中英文混用规范

#### 一致性检查

- [ ] 与其他文档内容一致
- [ ] 与代码实现一致
- [ ] 与项目架构一致
- [ ] 版本号格式一致

### 审查批准流程

#### 完整审查流程

```
1. 提交审查请求
   ↓
2. 技术审查（技术负责人）
   ↓
3. 内容审查（文档负责人）
   ↓
4. 格式审查（文档维护者）
   ↓
5. 批准或驳回
   ↓
6. 修改后重新审查（如需要）
   ↓
7. 批准发布
```

#### 审查角色与职责

| 角色 | 职责 |
| --- | --- |
| **文档作者** | 撰写文档，提交审查请求 |
| **技术负责人** | 审查技术准确性 |
| **文档负责人** | 审查内容完整性和一致性 |
| **文档维护者** | 审查格式规范 |
| **批准人** | 最终批准发布 |

#### 审查时限

- **完整审查**: 5个工作日
- **部分审查**: 3个工作日
- **快速审查**: 1个工作日

## 自动化验证

### 文档与代码一致性验证

#### 验证方法

1. **代码示例验证**
   - 提取文档中的代码示例
   - 自动编译和运行
   - 验证输出结果

2. **API 引用验证**
   - 检查文档中的 API 引用
   - 验证 API 是否存在
   - 验证 API 签名是否正确

3. **路径引用验证**
   - 检查文档中的文件路径
   - 验证文件是否存在
   - 验证路径是否正确

#### 验证脚本框架

```powershell
# 文档验证脚本框架
# docs/scripts/Verify-Documentation.ps1

<#
.SYNOPSIS
    验证文档与代码的一致性
.DESCRIPTION
    自动化验证文档中的代码示例、API引用和路径引用
.PARAMETER DocPath
    文档路径
.PARAMETER ProjectRoot
    项目根目录
.EXAMPLE
    .\Verify-Documentation.ps1 -DocPath "docs/01-编译构建流程.md" -ProjectRoot "."
#>

param(
    [Parameter(Mandatory=$true)]
    [string]$DocPath,
    
    [Parameter(Mandatory=$true)]
    [string]$ProjectRoot
)

# 初始化
$ErrorActionPreference = "Stop"
$Results = @()

# 1. 验证代码示例
Write-Host "验证代码示例..." -ForegroundColor Cyan
$CodeBlocks = Select-String -Path $DocPath -Pattern "```(\w+)" -AllMatches
foreach ($Match in $CodeBlocks.Matches) {
    $Language = $Match.Groups[1].Value
    Write-Host "  发现 $Language 代码块" -ForegroundColor Gray
    # TODO: 提取并验证代码
}

# 2. 验证 API 引用
Write-Host "验证 API 引用..." -ForegroundColor Cyan
$ApiReferences = Select-String -Path $DocPath -Pattern "`[CEGUI\w+\.\w+\(\)`]" -AllMatches
foreach ($Match in $ApiReferences.Matches) {
    $ApiName = $Match.Value
    Write-Host "  检查 API: $ApiName" -ForegroundColor Gray
    # TODO: 验证 API 是否存在
}

# 3. 验证路径引用
Write-Host "验证路径引用..." -ForegroundColor Cyan
$PathReferences = Select-String -Path $DocPath -Pattern "`[\w+/\\]+\.\w+`]" -AllMatches
foreach ($Match in $PathReferences.Matches) {
    $FilePath = $Match.Value
    $FullPath = Join-Path $ProjectRoot $FilePath
    if (Test-Path $FullPath) {
        Write-Host "  ✓ $FilePath" -ForegroundColor Green
    } else {
        Write-Host "  ✗ $FilePath (不存在)" -ForegroundColor Red
        $Results += "路径不存在: $FilePath"
    }
}

# 4. 生成报告
Write-Host "`n验证完成" -ForegroundColor Cyan
if ($Results.Count -eq 0) {
    Write-Host "✓ 所有验证通过" -ForegroundColor Green
} else {
    Write-Host "✗ 发现 $($Results.Count) 个问题" -ForegroundColor Red
    foreach ($Result in $Results) {
        Write-Host "  - $Result" -ForegroundColor Red
    }
    exit 1
}
```

### 构建流程验证

#### 验证方法

1. **构建步骤验证**
   - 按照文档中的构建步骤执行
   - 验证每个步骤是否成功
   - 记录构建时间和结果

2. **产物验证**
   - 验证构建产物是否存在
   - 验证产物大小是否符合预期
   - 验证产物依赖是否完整

3. **运行时验证**
   - 验证示例程序是否可运行
   - 验证功能是否正常
   - 验证性能是否符合预期

#### 验证脚本框架

```powershell
# 构建流程验证脚本
# docs/scripts/Verify-Build-Process.ps1

<#
.SYNOPSIS
    验证文档中的构建流程
.DESCRIPTION
    按照文档中的构建步骤执行，验证构建流程的正确性
.PARAMETER DocPath
    文档路径
.EXAMPLE
    .\Verify-Build-Process.ps1 -DocPath "docs/04-从零构建.md"
#>

param(
    [Parameter(Mandatory=$true)]
    [string]$DocPath
)

# 初始化
$ErrorActionPreference = "Stop"
$BuildStartTime = Get-Date
$Results = @()

Write-Host "开始验证构建流程..." -ForegroundColor Cyan

# 1. 解析构建步骤
Write-Host "`n步骤 1: 解析构建步骤" -ForegroundColor Cyan
# TODO: 从文档中提取构建步骤

# 2. 执行构建
Write-Host "`n步骤 2: 执行构建" -ForegroundColor Cyan
# TODO: 按照文档执行构建

# 3. 验证产物
Write-Host "`n步骤 3: 验证产物" -ForegroundColor Cyan
$ExpectedOutputs = @(
    "cegui/bin/CEGUIBase.dll",
    "cegui/bin/CEGUIOpenGLRenderer.dll"
)

foreach ($Output in $ExpectedOutputs) {
    if (Test-Path $Output) {
        $Size = (Get-Item $Output).Length
        Write-Host "  ✓ $Output ($Size bytes)" -ForegroundColor Green
    } else {
        Write-Host "  ✗ $Output (不存在)" -ForegroundColor Red
        $Results += "产物不存在: $Output"
    }
}

# 4. 运行时验证
Write-Host "`n步骤 4: 运行时验证" -ForegroundColor Cyan
# TODO: 运行示例程序验证

# 5. 生成报告
$BuildEndTime = Get-Date
$BuildDuration = $BuildEndTime - $BuildStartTime

Write-Host "`n验证完成" -ForegroundColor Cyan
Write-Host "构建时间: $($BuildDuration.TotalSeconds) 秒" -ForegroundColor Gray

if ($Results.Count -eq 0) {
    Write-Host "✓ 所有验证通过" -ForegroundColor Green
} else {
    Write-Host "✗ 发现 $($Results.Count) 个问题" -ForegroundColor Red
    foreach ($Result in $Results) {
        Write-Host "  - $Result" -ForegroundColor Red
    }
    exit 1
}
```

### 验证失败处理流程

#### 失败处理流程图

```
验证失败
    ↓
记录失败信息
    ↓
分析失败原因
    ↓
    ├─ 文档错误 → 修正文档 → 重新验证
    ├─ 代码问题 → 修复代码 → 重新验证
    ├─ 环境问题 → 修复环境 → 重新验证
    └─ 脚本问题 → 修复脚本 → 重新验证
```

#### 失败处理步骤

1. **记录失败信息**
   - 记录失败的验证项
   - 记录错误信息
   - 记录环境信息

2. **分析失败原因**
   - 检查文档内容是否正确
   - 检查代码实现是否正确
   - 检查环境配置是否正确
   - 检查验证脚本是否正确

3. **修复问题**
   - 根据失败原因修复问题
   - 更新相关文档或代码
   - 重新运行验证

4. **重新验证**
   - 重新运行验证脚本
   - 确认问题已解决
   - 记录修复结果

### 反馈处理流程

#### 处理流程图

```
收到反馈
    ↓
分类和优先级
    ↓
    ├─ 高优先级 → 立即处理 → 24小时内响应
    ├─ 中优先级 → 计划处理 → 3个工作日内响应
    └─ 低优先级 → 排队处理 → 1周内响应
    ↓
分析反馈
    ↓
    ├─ 有效反馈 → 创建任务 → 分配责任人
    ├─ 重复反馈 → 关联已有任务
    └─ 无效反馈 → 关闭并说明原因
    ↓
执行修复
    ↓
验证修复
    ↓
通知反馈者
    ↓
关闭反馈
```

## 文档更新流程

### 代码变更后的文档更新触发条件

| 代码变更类型 | 文档更新要求 | 触发条件 |
| --- | --- | --- |
| **API 变更** | 必须更新 | API 签名、参数、返回值变更 |
| **新增功能** | 必须更新 | 新增模块、类、函数 |
| **删除功能** | 必须更新 | 删除模块、类、函数 |
| **行为变更** | 必须更新 | 功能行为发生改变 |
| **性能优化** | 建议更新 | 性能显著提升或下降 |
| **Bug 修复** | 建议更新 | 修复影响用户使用的 Bug |
| **重构** | 视情况更新 | 内部重构不影响外部接口可不更新 |
| **配置变更** | 必须更新 | 构建配置、依赖配置变更 |

### 文档更新责任分配

| 角色 | 责任 | 负责文档 |
| --- | --- | --- |
| **代码开发者** | 提交文档更新请求 | API 文档、功能文档 |
| **技术负责人** | 审核技术准确性 | 技术文档 |
| **文档负责人** | 协调文档更新 | 所有文档 |
| **文档维护者** | 执行文档更新 | 格式和结构 |
| **测试工程师** | 验证文档准确性 | 测试文档 |

### 文档更新流程图

```
代码变更
    ↓
评估影响
    ↓
    ├─ 无影响 → 结束
    └─ 有影响 → 继续
    ↓
创建更新任务
    ↓
分配责任人
    ↓
执行更新
    ↓
    ├─ 更新内容
    ├─ 更新版本号
    ├─ 更新日期
    └─ 更新变更记录
    ↓
自动化验证
    ↓
    ├─ 通过 → 继续
    └─ 失败 → 修复 → 重新验证
    ↓
提交审查
    ↓
    ├─ 通过 → 继续
    └─ 未通过 → 修改 → 重新审查
    ↓
发布更新
    ↓
通知相关人员
    ↓
关闭任务
```

### B. 文档质量评分标准

| 评分项 | 权重 | 评分标准 |
| --- | --- | --- |
| **技术准确性** | 30% | 内容准确无误，与代码一致 |
| **内容完整性** | 20% | 内容完整，覆盖所有必要信息 |
| **格式规范** | 15% | 格式规范，符合文档标准 |
| **语言表达** | 15% | 语言简洁明了，易于理解 |
| **可读性** | 10% | 结构清晰，易于阅读 |
| **时效性** | 10% | 内容及时，反映最新状态 |

**评分等级**:
- 90-100分: 优秀
- 80-89分: 良好
- 70-79分: 合格
- 60-69分: 需要改进
- <60分: 不合格

### D. 常见问题（FAQ）

#### Q1: 文档更新不及时怎么办？

**A**: 
1. 检查代码变更是否触发了文档更新
2. 联系文档负责人了解更新进度
3. 如有紧急需求，可提交高优先级的反馈

#### Q2: 如何判断文档是否需要审查？

**A**: 
参考"审查触发条件"章节，根据变更类型和影响程度判断。

#### Q3: 自动化验证失败如何处理？

**A**: 
1. 查看验证失败报告
2. 分析失败原因
3. 根据原因修复问题
4. 重新运行验证

#### Q4: 反馈提交后多久能得到响应？

**A**: 
根据反馈优先级不同，响应时间也不同：
- 高优先级: 24小时内
- 中优先级: 3个工作日内
- 低优先级: 1周内

#### Q5: 如何参与文档维护？

**A**: 
1. 阅读本文档维护指南
2. 了解文档结构和规范
3. 提交文档改进建议
4. 参与文档审查
5. 成为文档维护者
