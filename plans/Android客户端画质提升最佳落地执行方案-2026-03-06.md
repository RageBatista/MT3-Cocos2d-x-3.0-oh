# Android 客户端画质提升最佳落地执行方案（EGL MSAA + 选择性 Mipmap + 高清资源）

## 1. 文档信息

| 字段 | 内容 |
|------|------|
| 文档版本 | v1.0 |
| 生成日期 | 2026-03-06 |
| 适用范围 | MT3 Android 客户端主链，覆盖 `common` 与各渠道工程 |
| 推荐周期 | 10-15 个工作日 |
| 目标定位 | 在不升级 Cocos2d-x 主版本、不更换 Android 主工具链的前提下，拿到真实、稳定、可回滚的画质提升 |

## 2. 核心结论

### 2.1 最佳方案

本项目 Android 端画质提升的最佳落地方案不是先升级 `Cocos2d-x`、`NDK` 或大改 `ResolutionAdapter`，而是按下面顺序推进：

1. 在 Android Java/EGL 层显式申请 `RGBA8888 + MSAA`，并实现 `4x -> 2x -> 0x` 回退。
2. 把 C++ 侧的抗锯齿和 Mipmap 开关改成真实配置，不再硬编码。
3. 在渲染器中对场景/地图/角色类纹理做选择性 `generateMipmap()` 和更合理的采样设置。
4. 增加真实的画质档位与资源档位配置。
5. 同步补一套更高分辨率资源，否则代码链路改完也不会凭空变清晰。

### 2.2 不建议先做的事

1. 不建议第一阶段升级 `Cocos2d-x` 主版本。
2. 不建议第一阶段升级 Android 主链到 `NDK r11+` 或 Gradle。
3. 不建议先改 Android 逻辑基线分辨率或做离屏超采样。
4. 不建议把“画质优化”继续等同于“提高 FPS 上限”。

## 3. 现状结论与问题定性

### 3.1 Android 启动层现状

当前 Android 启动链只是创建 `Cocos2dxGLSurfaceView`、设置 ES2 上下文并绑定 renderer，没有显式的 `EGLConfigChooser`。这意味着是否拿到 `RGBA8888`、是否启用 `sample buffer`、是否启用 `4x/2x MSAA`，目前并不由项目代码稳定控制。

涉及文件：

1. `client/android/common/src/com/locojoy/mini/mt3/GameApp.java`
2. `client/android/LocojoyProject/src/com/locojoy/mini/mt3/GameApp.java`
3. `client/android/LocojoyProject64/src/com/locojoy/mini/mt3/GameApp.java`
4. `client/android/JoysdkProject/src/com/locojoy/mini/mt3/GameApp.java`
5. `client/android/YijieProject/src/com/locojoy/mini/mt3/GameApp.java`

### 3.2 C++ 参数链现状

业务层目前把抗锯齿写死为 `4x MSAA`，但同时把 `mipmap` 写死为关闭。这两个值都不是按配置、按机型、按画质档位生效。

涉及文件：

1. `client/FireClient/Application/Framework/GameApplication.cpp`

### 3.3 Renderer 现状

`EngineParameter` 虽然把 `multiSampleType` 传入 renderer，但 `engine/renderer/nucocos2d_render.cpp` 的 `Create()` 目前没有真实消费这个参数，因此当前 `4x MSAA` 更像“名义配置”，不是“真实生效”。

同时，贴图上传路径已经是 `RGBA8888 / RGB888`，所以当前画质问题的主因不是“纹理被压成 16 位”。

### 3.4 配置系统现状

当前 `screenfresh` 配置只是在切换 FPS 档位，实际对应 `SysConfig.CFPSSetting.xml` 中的 `144/120`，并不是真正的“画质高/低”。

涉及文件：

1. `client/resource/res/table/xmltable/SysConfig.CGameconfig.xml`
2. `client/resource/res/table/xmltable/SysConfig.CFPSSetting.xml`
3. `client/resource/res/script/logic/systemsettingdlgnew.lua`
4. `client/FireClient/Application/Manager/ConfigManager.cpp`

### 3.5 ResolutionAdapter 现状

Android 当前确实存在 `1080x720` 逻辑基线，但主 viewport 仍然按物理显示尺寸设置。直接动这层会同时影响逻辑坐标、触摸映射、UI 布局、战斗视野，风险高于收益，不应作为第一阶段入口。

## 4. 本期目标与成功标准

### 4.1 本期目标

1. Android 端获得真实可验证的 `MSAA` 和更稳定的颜色缓冲格式。
2. 场景、地图、角色在缩小采样时明显减少闪烁、锯齿和远景发糊。
3. 建立一套能按设备能力回退的画质档，而不是单一硬编码。
4. 保持现有 `NDK r10e + Ant + ES2` 主链不变。

### 4.2 成功标准

1. 视觉：
   - 角色轮廓锯齿明显下降。
   - 地图和场景缩小时闪烁感下降。
   - 大背景和地表纹理远景更稳定。
2. 稳定：
   - 0 个阻断级黑屏。
   - 0 个高频 EGL 初始化失败崩溃。
3. 性能：
   - 默认发布档平均 FPS 回退不超过 12%。
   - 低端兼容档可自动回退到 `0x MSAA`。
4. 回滚：
   - 关闭新增配置后，行为回到当前基线路径。

## 5. 方案边界

### 5.1 本期范围（In Scope）

1. Android Java/EGL 创建链路。
2. `EngineParameter -> Renderer` 的画质参数链。
3. 2D 贴图的选择性 Mipmap 与采样策略。
4. 画质配置项、设置界面和运行时回退规则。
5. 高清资源包与资源档位开关。

### 5.2 非本期范围（Out of Scope）

1. 升级 `Cocos2d-x` 主版本。
2. 升级 Android 工具链到 `NDK r11+` 或 Gradle。
3. 全量重写地图渲染系统。
4. 第一阶段引入离屏 supersample、FXAA 全屏链、HDR 后处理。
5. 第一阶段直接修改 Android 逻辑分辨率基线。

## 6. 最佳技术方案总览

### 6.1 方案原则

1. 先控制真实 framebuffer 质量，再处理纹理采样质量。
2. 先打通“可观测、可配置、可回退”的参数链，再谈更激进方案。
3. 先解决高收益、低侵入的 Android 专项问题，不做大版本升级。
4. 对渠道工程采取补丁式同步，不在第一阶段引入目录级大重构。

### 6.2 目标画质档设计

建议新增 3 档：

| 档位 | MSAA | Mipmap | 高清资源 | 目标定位 |
|------|------|------|------|------|
| `compat` | `0x` | 关闭或极少量 | 关闭 | 低端兼容、故障回退 |
| `standard` | `2x` | 选择性开启 | 关闭 | 默认发布档 |
| `hd` | `4x` | 选择性开启 | 开启 | 高端机实验/灰度 |

默认发布建议：

1. 先以 `standard` 为默认。
2. `hd` 只做灰度，不直接全量发布。
3. `compat` 作为故障和低端回退档。

## 7. 分期执行方案

### Phase 0：基线采样与日志补齐（1-2 天）

#### 目标

确认 Android 当前实际拿到的 EGL 配置、颜色深度、采样数、设备 GPU 信息和渲染参数，避免后续“改了代码但不知道是否生效”。

#### 改动点

1. 在 Android Java 层输出：
   - `GL_VENDOR`
   - `GL_RENDERER`
   - `GL_VERSION`
   - 实际 `EGL_RED/GREEN/BLUE/ALPHA_SIZE`
   - `EGL_DEPTH_SIZE`
   - `EGL_STENCIL_SIZE`
   - `EGL_SAMPLE_BUFFERS`
   - `EGL_SAMPLES`
2. 在 C++ 启动层继续保留并补齐：
   - `multiSampleType`
   - `bEnableMipMap`
   - `dwRenderFlags`
3. 记录渠道差异：
   - `common`
   - `LocojoyProject`
   - `LocojoyProject64`
   - `JoysdkProject`
   - `YijieProject`

#### 完成标准

1. 至少有 1 台低端、1 台中端、1 台高端 Android 机拿到完整基线日志。
2. 能区分“请求值”和“实际生效值”。

### Phase 1：Java/EGL 真正接管 MSAA（2-3 天）

#### 目标

让 Android 启动链显式申请高质量 EGL 配置，并在失败时可靠回退。

#### 推荐实现

1. 在 `org.cocos2dx.lib.Cocos2dxGLSurfaceView` 增加自定义 `EGLConfigChooser`。
2. 申请顺序固定为：
   - `RGBA8888 + depth16/24 + stencil8 + sampleBuffers=1 + samples=4`
   - 回退到 `RGBA8888 + depth16/24 + stencil8 + sampleBuffers=1 + samples=2`
   - 再回退到 `RGBA8888 + depth16/24 + stencil8 + sampleBuffers=0 + samples=0`
3. `GameApp.java` 中在 `setRenderer()` 之前完成 chooser 设置。
4. 失败时打印明确日志，不允许静默回退。

#### 涉及文件

1. `client/android/common/src/org/cocos2dx/lib/Cocos2dxGLSurfaceView.java`
2. `client/android/common/src/com/locojoy/mini/mt3/GameApp.java`
3. 其余四套渠道工程中的同名 Java 文件

#### 风险控制

1. 第一阶段不做代码合并重构，先保证 5 套工程都可编译。
2. 如果个别渠道壳层有特殊初始化差异，允许保留微差，但 chooser 逻辑必须一致。

#### 完成标准

1. 默认高端机能拿到 `2x` 或 `4x` MSAA。
2. 不支持多采样的设备能稳定回退到 `0x`。
3. 所有渠道工程启动链路一致通过。

### Phase 2：配置化画质档与 C++ 参数链收口（2-3 天）

#### 目标

把“画质”从硬编码改成配置化、可存档、可在 UI 中表达的真实能力。

#### 改动点

1. `GameApplication.cpp`
   - `GetAntialiaseLevel()` 改为从配置读取，不再直接写死 `4x`。
   - `isSpriteUseMipmap()` 改为从配置读取，不再直接返回 `false`。
2. `ConfigManager.cpp`
   - 新增画质配置读取、默认值、应用逻辑。
   - 把 `screenfresh` 与“画质”解耦。
3. `SysConfig.CGameconfig.xml`
   - 新增建议键：
     - `renderquality`
     - `msaa`
     - `mipmap`
     - `hdresource`
4. `systemsettingdlgnew.lua`
   - 增加“画质档”设置，不再让用户误把 FPS 选项当画质选项。
   - `MSAA` 切换提示“重启后生效”。

#### 推荐策略

1. `renderquality=0/1/2` 统一表示 `compat/standard/hd`。
2. `msaa` 支持 `0/2/4`。
3. `mipmap` 支持 `0/1`。
4. `hdresource` 支持 `0/1`。

#### 完成标准

1. 修改配置后，启动日志中可看到配置值映射到真实引擎参数。
2. 用户侧能明确区分“帧率档”和“画质档”。

### Phase 3：Renderer 消费参数并做选择性 Mipmap（3-4 天）

#### 目标

把“Android 申请到了 MSAA”与“贴图缩小采样更稳定”两件事都真正接到 renderer 中。

#### 改动点

1. `engine/renderer/nucocos2d_render.cpp`
   - 让 `Create(..., mstype)` 真实消费多采样参数或至少记录最终能力。
   - 对加载后的贴图按类别决定是否生成 mipmap。
2. 优先启用 Mipmap 的资源类型：
   - 地图地表
   - 场景大背景
   - 角色/模型在远景缩小时的主纹理
3. 默认不启用 Mipmap 的资源类型：
   - UI 图集
   - 字体纹理
   - 小图标
   - 动态更新纹理
4. 对允许线性过滤的场景纹理，启用更合理的 `setAntiAliasTexParameters()`。

#### 推荐实现路径

第一阶段推荐“白名单式接入”，不要一上来改成全局强开：

1. 先按路径、目录或资源分类做白名单。
2. 后续如需更干净，可再扩展到“资源加载 flag 驱动”。

#### 为什么要选择性开启

1. 全局开 Mipmap 会让 UI、字体和小 icon 发糊。
2. Android ES2 老链路下，全局开会放大显存和包体压力。

#### 完成标准

1. 地图、远景背景、角色缩小时闪烁和锯齿下降。
2. UI 和字体清晰度不下降。

### Phase 4：高清资源包与档位联动（并行 5-10 天）

#### 目标

让代码链路的提升能真正转换成肉眼可见的高清画面。

#### 改动点

1. 美术/资源侧补高分辨率源图：
   - 重点 UI
   - 角色关键贴图
   - 场景大背景
   - 地表关键纹理
2. 技术侧增加资源档位：
   - 普通资源
   - 高清资源
3. 按设备档位决定是否启用高清资源。
4. 如需控包，优先评估继续用现有可支持的压缩纹理或 `WebP` 资源。

#### 关键原则

1. 代码优化不能替代高清源资源。
2. 先补 ROI 最高的资源，不做首轮全量重制。

#### 完成标准

1. `hd` 档在关键 UI、人物、地图上能看出比 `standard` 更高的清晰度。
2. 包体、加载时长、内存峰值在可接受范围内。

### Phase 5：兼容性、性能和发布收口（2-3 天）

#### 目标

在 Android 多机型、多渠道环境下把风险收干净，并固化回滚路径。

#### 验证维度

1. 机型维度：
   - 低端兼容机
   - 中端主流机
   - 高端灰度机
2. 渠道维度：
   - `common`
   - 至少 1 个 32 位渠道
   - `LocojoyProject64`
3. 场景维度：
   - 主城
   - 野外地图
   - 战斗
   - 高 UI 密度界面
4. 指标维度：
   - FPS
   - 内存峰值
   - 黑屏/花屏
   - EGL 初始化失败率
   - 切后台恢复稳定性

#### 完成标准

1. 默认发布档无阻断黑屏。
2. 画质收益稳定可复现。
3. 回滚配置可独立关闭 `MSAA`、`Mipmap`、`HDResource`。

## 9. 底层依赖与源码修改决策

### 9.1 需要修改的“底层依赖/基础层”

1. `client/android/*/src/org/cocos2dx/lib/*.java`
   - 这是当前项目实际打包使用的 Android 基础层副本，第一阶段必须改。
2. `engine/renderer/nucocos2d_render.cpp`
   - 这是当前 2D 渲染行为的关键落点，必须改。
3. `client/FireClient/Application/Framework/GameApplication.cpp`
   - 这是参数进入引擎的业务入口，必须改。

### 9.2 第一阶段不建议修改的“底层依赖”

1. 不建议升级 `cocos2d-2.0-rc2-x-2.0.1` 主版本。
2. 不建议升级 `NDK r10e`。
3. 不建议改 Android 主构建方式为 Gradle。
4. 不建议第一阶段大改 `ResolutionAdapter.cpp`。

### 9.3 如果必须触达 Cocos2d 基础层

只建议做补丁式修改，不建议“升级式替换”：

1. 如果 Java 层 chooser 能解决 EGL 问题，就不要动更深的 Cocos2d Android 基础库。
2. 如果选择性 Mipmap 能通过现有 `CCTexture2D::generateMipmap()` 接入，就不要改 `CCTexture2D` 本体。

## 11. 验证方案

### 11.1 构建验证

Android 构建链保持仓库既有规则：

1. 使用 `JDK 1.7/1.8 + NDK r10e + Ant + Python 2.7`。
2. 进入具体渠道目录后，先执行 `ndk-build`，再执行 `ant release`。
3. 不引入 Gradle，不切换 Clang 主链。

### 11.2 冒烟验证

1. 冷启动进入主城。
2. 切后台再恢复。
3. 切战斗。
4. 打开高 UI 密度界面。
5. 连续切换 3 张不同地图。

### 11.3 视觉验证

1. 角色边缘锯齿对比。
2. 地表缩小时闪烁对比。
3. 远景背景稳定性对比。
4. UI/字体清晰度对比。

### 11.4 性能验证

1. 对比 `compat`、`standard`、`hd` 三档 FPS。
2. 记录内存峰值。
3. 记录发热和帧率波动。

## 12. 回滚策略

回滚顺序建议固定如下：

1. 先关闭 `hdresource`。
2. 再关闭 `mipmap`。
3. 再把 `msaa` 回退到 `0`。
4. 最后将 `renderquality` 回退到 `compat`。

若出现严重兼容问题：

1. 保留 Java chooser，但默认只申请 `0x`。
2. 保留 UI 配置项，但默认隐藏 `hd` 档。
3. 暂停高清资源包灰度，仅发布 `standard`。

## 13. 风险清单

| 风险ID | 描述 | 概率 | 影响 | 应对 |
|------|------|------|------|------|
| R-01 | 个别机型申请 `4x` 后 EGL 初始化失败 | 中 | 高 | 强制 `4x -> 2x -> 0x` 回退并记日志 |
| R-02 | 全局开 Mipmap 导致 UI 发糊 | 高 | 中 | 只做白名单式开启 |
| R-03 | 渠道工程改动不一致导致某渠道回归 | 中 | 高 | 五套工程统一清单逐项回读 |
| R-04 | 高清资源提升清晰度但拉高包体和内存 | 高 | 中 | 只补关键资源，按档位控制 |

| R-06 | 误动 `ResolutionAdapter` 造成坐标和 UI 回归 | 中 | 高 | 第一阶段只加日志，不改逻辑基线 |

## 14. 最小交付定义

满足以下条件即可视为本轮 Android 画质专项完成：

1. Android Java/EGL 层已显式申请并记录真实多采样配置。
2. `GameApplication.cpp` 不再硬编码 `4x MSAA` 和 `mipmap=false`。
3. Renderer 已对地图/场景/角色纹理做选择性 Mipmap 和更合理采样。
4. 设置界面已新增真实画质档，而不是只保留 FPS 档。
5. 至少一批关键资源已有高清版本并能随档位切换。

## 15. 结论

对当前 MT3 Android 客户端，最佳落地方案是“补丁式接管 EGL + 收口 C++ 画质参数 + 选择性 Mipmap + 高清资源联动”。这是当前代码结构下收益最高、风险最低、最容易灰度和回滚的方案。

第一阶段真正需要动的不是大版本依赖升级，而是：

1. Android `org.cocos2dx.lib` Java 基础层副本。
2. `GameApplication.cpp` 参数入口。
3. `nucocos2d_render.cpp` 渲染器贴图与采样路径。

只要这三段链路打通，再叠加高清资源，Android 端画质就能获得稳定、可验证、可持续扩展的提升。
