## 1. 结论摘要

MT3 当前“地图发虚、模糊”不是单点问题，而是三条不同链路叠加后的结果：

1. **世界场景底图链**  
   走 `GameScene -> World -> Map -> Renderer`，底层资源是 `/map/*` 下的离线栅格地图，清晰度上限受 `map.rmp` 对应切片原始分辨率、场景逻辑分辨率和纹理采样策略共同限制。

2. **地图相关 UI 显示链**  
   走 `worldmap.layout + imageset + worldmapdlg.lua + logoinfo.layout`，本质是静态大图、入口按钮和若干热点图标，不是动态地图渲染。它的清晰度主要取决于 imageset 原图分辨率、布局锚点策略和 UI 在高分屏上的拉伸倍率。

说明：按当前任务口径，`xiaoditu_mtg` 小地图逻辑视为正确，本稿后续不再把小地图作为问题根因或主要改造对象。

本次全量代码分析后的核心判断是：

- **不能直接修改 `adapter->get_logic_w/h()` 的语义来“顺手提高清晰度”**。这组值已经深度绑定世界 viewport、战斗布点、投影矩阵和大量场景对象屏幕定位。
- **地图高清化要拆成两条改造路线并行推进**：
  - 场景地图：引入独立 `scene render scale / scene render size`，不改旧逻辑坐标语义。
  - 地图 UI：补齐 `worldmap / HUD 入口` 高倍率资源桶并修正横向扩展布局，不能指望世界场景那条 mipmap 优化自动覆盖 UI 地图。

## 2. 当前代码架构总览

### 2.1 分辨率与显示基线

当前 Android 端场景与 UI 的逻辑基线仍保持在 `1080x720` 兼容模式：

- `client/FireClient/Application/Framework/ResolutionAdapter.cpp:25-29`
- `client/FireClient/Application/Framework/ResolutionAdapter.cpp:227-244`

其中：

- `get_logic_w/h()`：场景逻辑宽高
- `get_ui_logic_w/h()`：UI 逻辑宽高
- `Engine::GetLogicWidth/Height()` 实际返回的是 UI logic，而不是 scene logic  
  见 `engine/engine/nuengine.cpp:1335-1347`

这意味着：

- Lua UI 脚本里的 `Nuclear.GetEngine():GetLogicWidth/Height()` 主要是 UI 坐标。
- 世界渲染链和战斗链直接依赖的是 `adapter->get_logic_w/h()`，不是 UI logic。

### 2.2 世界场景渲染链

世界场景地图加载入口：

- `client/FireClient/Application/Framework/GameScene.cpp:1505-1518`

关键链路如下：

1. `GameScene::LoadMap()` 从 `map.cmapconfig.resdir` 取地图资源目录。
2. 调用 `World::LoadMap(resdir, resdir + "/maze.dat", ...)`。
3. `World::LoadMap()` 内部创建 `Map`，最终从 `/map/<resdir>/map.rmp` 取主地图数据。  
   见：
   - `engine/world/nuworld.cpp:740-746`
   - `engine/world/numap.h:32`
   - `engine/world/numap.cpp:384-410`
4. 同时加载：
   - `maze.dat`
   - `regiontypeinfo.dat`
   - `JumpBlock.dat`
   - `Island.dat`
   - `Island2.dat`  
   见 `GameScene.cpp:1534-1555`

世界对象创建和 viewport 初始化直接吃 scene logic：

- `engine/engine/nuengine.cpp:289-290`
- `engine/engine/nucocos2d_wraper.cpp:467-468`
- `client/FireClient/Application/Framework/GameApplication.cpp:2187-2188`
- `engine/renderer/nucocos2d_render.cpp:182-183`

### 2.3 相机与 viewport 缩放链

地图场景的“清晰度”和“视野”在现实现里耦合在 `Camera` 上：

- `engine/world/nuworld.cpp:3484-3488`
- `engine/engine/nucamera.cpp:287-302`
- `engine/engine/nucamera.cpp:399-415`

`World::SetScale()` 会走到 `Camera::SetScale()`，后者会直接改变：

- viewport world 宽高
- camera 中心到左上角的换算
- 平滑跟随器的 viewport ext

也就是说，当前 `SetScale()` 的语义是“改世界视野密度”，不是“只提高渲染分辨率”。

### 2.4 区域资源预取链

地图切片/区域资源不是全量常驻，而是按 viewport 附近区域动态保证：

- `engine/world/numap.cpp:515-537`
- `engine/world/numap.cpp:783-885`

重要特征：

- `AssureRegionResource()` 以 viewport 为核心做资源激活。
- 默认额外预取边界 `extraregion = 512`。
- 同步/异步都会调用 `LoadPictureFromMem()` 或 `LoadPictureFromCCImage()` 上传纹理。

这意味着：

- 如果直接改 scene logic 导致 viewport 宽高变大，区域激活范围也会变大。
- 地图高清化如果用“增大 render scale、保持逻辑 viewport 不变”的方案，资源装载压力更可控。

## 3. 地图模糊问题的两条根因链

## 3.1 世界场景地图发虚

### 3.1.1 根因一：场景逻辑分辨率固定，高分屏会被放大显示

当前世界渲染链仍以 `get_logic_w/h()` 为场景基线：

- `nuengine.cpp:290`
- `nucocos2d_wraper.cpp:467-468`
- `GameApplication.cpp:2187-2188`
- `nucocos2d_render.cpp:182-183`

在高分屏设备上，如果物理显示尺寸远大于这组逻辑尺寸，最终会发生上采样。对离线栅格地图来说，上采样的结果就是边缘变软、细节发糊。

### 3.1.2 根因二：底图资源本身是栅格资源，清晰度上限受源图倍率限制

世界地图底图来自 `/map/<resdir>/map.rmp`，并不是矢量地图：

- `numap.h:32`
- `numap.cpp:390`

因此即便采样策略正确，只要原始地图切片分辨率不够，在更高 DPR 或更大屏幕上仍然会模糊。

### 3.1.3 根因三：当前优化只改善了缩小采样，不等于解决放大模糊

目前渲染器已经补上了 `/map/` 贴图的 mipmap 策略：

- `engine/renderer/nucocos2d_render.cpp:56-80`
- `engine/renderer/nucocos2d_render.cpp:563`
- `engine/renderer/nucocos2d_render.cpp:1288-1289`

这能改善：

- 地图缩小显示
- 远景/倾斜/移动背景等 minification 采样

但它**不能**解决：

- 原始地图资源倍率不足时的放大模糊
- 高分屏上逻辑画面被整体拉伸的发虚

### 3.1.4 根因四：世界 scale 当前是 gameplay camera scale，不适合直接当高清开关

调世界 scale 会直接改 viewport world size：

- `nucamera.cpp:291-296`
- `nucamera.cpp:405-406`

同时世界、特效、背景、对象名字等大量逻辑都直接使用 `GetViewport()` 和 `GetScale()`：

- `engine/world/nuworld.cpp:1286-1423`
- `client/FireClient/Application/SceneObj/SceneObject.cpp`
- `client/FireClient/Application/SceneObj/Character.cpp`
- `client/FireClient/Application/Battle/*`

因此不能把“地图高清化”简单实现成“把 `World::SetScale()` 调大/调小”。

## 3.2 地图相关 UI 显示发虚

### 3.2.1 世界地图是静态大图，不是动态图层

脚本只负责：

- 热点按钮事件
- 玩家头像位置
- 打开/关闭界面与入口跳转

见：

- `client/resource/res/script/logic/worldmap/worldmapdlg.lua:231-262`
- `worldmapdlg.lua:427-443`
- `worldmapdlg.lua:490-535`

世界地图主图来自布局和 imageset：

- PC：
  - `client/resource/res/ui/layouts/worldmap.layout:507-518`
  - `client/resource/res/ui/imagesets/ccditu.imageset:4`
  - `client/resource/res/ui/imagesets/ccditu.imageset:74`
- Android：
  - `client/android/梦屿西游/assets/unpacked/ui/layouts/worldmap.layout:683`
  - `client/android/梦屿西游/assets/unpacked/ui/imagesets/worldmapbg.imageset:3`
  - `client/android/梦屿西游/assets/unpacked/ui/imagesets/worldmapbg.imageset:6`

当前已知资源尺寸：

- PC 世界地图主图：`ccditutupian = 1614 x 533`
- Android 世界地图主图：`worldmapbg.bg = 1614 x 533`

所以世界地图如果在更高 DPI 设备上按 UI 逻辑尺寸再放大，清晰度一定会掉。

### 3.2.2 地图入口 HUD 与世界地图不是同一种放大模型

主场景上的地图入口区域位于 `logoinfo.layout`：

- PC：`client/resource/res/ui/layouts/logoinfo.layout`
- Android：`client/android/梦屿西游/assets/unpacked/ui/layouts/logoinfo.layout`

两端差异很明显：

- PC 侧的地图入口更接近固定像素块，只受全局 UI 放大影响。
- Android 侧入口容器使用了比例锚点，宽度会跟随父容器变化，属于“全局放大 + 横向扩展”叠加。

这意味着：

- 世界地图主图和地图入口 HUD 不能按同一种失真模型处理。
- 世界地图主图要优先补高倍率位图。
- Android 地图入口 HUD 要额外检查布局锚点，避免继续被横向撑宽。

### 3.2.3 地图 UI 采样不吃世界场景 mipmap 优化

CEGUI 静态图片当前统一使用线性过滤：

- `tools/CEGUI-0.7.1/cegui/src/RendererModules/Cocos2D/CEGUICocos2DRenderer.cpp:520-529`

而 CEGUI 并不会自动享受 `/map/*` 那条 `applyPictureTextureSampling()` 的地图贴图策略。  
因此世界地图主图、地图入口大图、装饰底板这类 UI 贴图，都要单独治理。

### 3.2.4 Android 与 PC 资源存在分叉，高清化有同步风险

同一套世界地图界面在两端存在不同资源副本：

- `client/resource/res/ui/layouts/worldmap.layout`
- `client/android/梦屿西游/assets/unpacked/ui/layouts/worldmap.layout`
- `client/resource/res/ui/imagesets/worldmapbg.imageset`
- `client/android/梦屿西游/assets/unpacked/ui/imagesets/worldmapbg.imageset`

这意味着：

- 只改 PC 端资源不会自动修正 Android
- 只改 Android unpacked 也不能说明源资源链已经治理完成

后续地图高清化必须把“资源源文件、打包产物、平台副本”一起纳入治理。

### 4.1 CEGUI 显示尺寸变更通知与 DPI 修正

- `client/FireClient/Application/Manager/GameUIManager.cpp:2421-2424`

注意：

- 这主要改善字体和 UI 系统的 DPI 感知。
- 对世界地图和地图入口这类“静态图片本身分辨率不够”的问题帮助有限。

- `engine/renderer/nucocos2d_render.cpp:56-80`
- `engine/renderer/nucocos2d_render.cpp:563`
- `engine/renderer/nucocos2d_render.cpp:1288-1289`

这能减少：

- 地图移动时的 shimmer
- 远景缩小采样的模糊/闪烁
- 斜向/非整数缩放下的采样抖动

但它仍然不是“高清地图”的终局方案。

## 5. 为什么现在不能直接改 `get_logic_w/h()`

这部分是后续所有改造的前置边界。

### 5.1 世界创建和投影矩阵直接依赖 scene logic

- `nuengine.cpp:289-290`
- `nucocos2d_wraper.cpp:467-468`
- `GameApplication.cpp:2187-2188`
- `nucocos2d_render.cpp:182-183`

### 5.2 viewport 直接参与玩法和对象屏幕定位

- `GameScene::GetViewport()` 直接返回 `World()->GetViewport()`  
  见 `GameScene.cpp:1856-1858`
- `GameScene::MousePointToPixel()` 直接用 viewport 左上角做换算  
  见 `GameScene.cpp:1719-1725`
- 战斗布点/技能定位直接吃 `get_logic_w/h()` 和 viewport  
  见：
  - `BattleManagerOperate.cpp:258-270`
  - `SkillBuilder.cpp:113-117`

### 5.3 直接改 scene logic 会引发的连锁风险

- 战斗站位偏移
- 世界对象屏幕坐标飘移
- 相机边界与地图可见区域变化
- 旧 Lua 分辨率脚本失效

因此现阶段结论仍然成立：

**地图高清化不能通过改变旧的 scene logic 基线来完成。**

## 6. 面向 MT3 的正确改造路线

## 6.1 路线一：世界场景地图高清化

### 6.1.1 架构决策

新增独立概念：

- `scene_render_scale`
- 或 `scene_render_width / scene_render_height`

要求：

- 只影响 render target / draw pass 分辨率
- 不改变 `get_logic_w/h()`、viewport world 坐标、战斗与寻路逻辑

目标：

- 逻辑视野不变
- gameplay 坐标不变
- 仅提升最终场景像素密度

### 6.1.2 推荐实施顺序

1. 先把 render-only 路径和 logic-only 路径继续拆清。
2. 在场景 draw pass 上试点独立 render scale。
3. 保持 camera viewport 和战斗分辨率表不变。
4. 仅对世界场景启用，不影响登录、UI、战斗专用绘制链。

### 6.1.3 配套资源策略

场景 render scale 只解决“逻辑画面被整体放大”的问题，不能解决“源图本身不够高清”。

所以还必须补：

- 地图资源倍率审计
- 高频主城/活动地图的高清底图桶
- 地图切片原图导出规范

建议：

- 保持 `/map/<resdir>/map.rmp` 结构不动
- 通过资源导出链补 `hd` 桶或高倍率地图包
- 运行时按设备档位选择 `resdir` 或资源变体

## 6.2 路线二：地图相关 UI 显示高清化

### 6.2.1 世界地图主图优先级最高

当前世界地图与入口 HUD 的核心问题不是逻辑计算，而是：

- 主图资源倍率不足
- Android 侧布局存在横向扩展
- PC/Android 存在双份资源与双份 layout

因此这条路线应优先做：

- `worldmapbg / ccditu` 高倍率资源桶
- Android `worldmap.layout` 主图区锚点治理
- `logoinfo.layout` 地图入口区域的宽度约束治理

### 6.2.2 地图 UI 资源建议

对世界地图与地图入口相关资源建立倍率桶：

- `1x`：兼容旧机
- `2x`：Android 主推
- `3x`：高端机或平板

原则：

- 展示尺寸不能长期大于图源像素尺寸
- Android 布局中不再让主图区通过 `right.scale = 1` 一路横向扩展
- PC/Android 资源必须同源生成，避免一端升级、一端继续回退

## 6.3 路线三：世界地图 UI 高清化

### 6.3.1 当前问题本质

当前主图 `1614x533`：

- 在 `1080x720` 逻辑时代尚可
- 到高分屏设备上被整体放大后必然变软

### 6.3.2 推荐方案

世界地图主图直接建立高清 imageset：

- `worldmapbg@2x`
- `ccditu@2x`

并同步：

- `worldmap.layout`
- Android unpacked 同名 layout/imageset
- 打包脚本/资源映射

如果短期内不改运行时选桶逻辑，至少要先把当前主图升级到更高像素，再按同样的逻辑窗口展示。

## 7. 性能与内存预算建议

## 7.1 世界场景 render scale 预算

建议从保守档位起步：

- 低端机：`1.0`
- 中端机：`1.25`
- 高端机：`1.5` 上限试点

原因：

- `1.25x` 像素数约为 `1.56x`
- `1.5x` 像素数约为 `2.25x`

它主要增加：

- 场景 fill-rate
- render target 内存
- 后处理/截图相关 pass 成本

但如果逻辑 viewport 不变，地图区域资源预取压力不会像“直接改 logic viewport”那样剧烈膨胀。

## 7.2 世界地图 / 地图入口 UI 资源预算

地图 UI 高清化是“显存换清晰度”的典型场景。

建议预算：

- 世界地图主图：进入界面时按需加载，退出后可释放
- 地图入口 HUD：优先用固定尺寸切图，避免在运行时拉伸
- 低端机避免同时常驻多套大图

## 7.3 必须补的监控

至少补三组监控：

1. 场景侧
   - map draw ms
   - render target size
   - scene fps / p95 frame time

2. 资源侧
   - `/map/*` 纹理上传次数
   - 区域资源命中/淘汰
   - 大图 imageset 载入耗时

3. UI 侧
   - 世界地图打开耗时
   - 主场景地图入口区域切图命中率
   - UI 大图显存占用
   - 高倍率资源命中率

## 8. 工程实施顺序

### 阶段 A：低风险止损

目标：先把最容易“再次发虚”的点控住。

1. 建立地图显示专项验收页：
   - 世界场景
   - 世界地图
   - 主场景地图入口 HUD
2. 记录 720p / 1080p / 1440p / 平板截图基线。
3. 统计世界地图主图当前像素尺寸与展示尺寸。
4. 统计主场景地图入口区域当前资源尺寸与展示尺寸。

### 阶段 B：资源与配置治理

1. 为世界地图主图建立高倍率 imageset。
2. 为地图入口 HUD 建立高倍率资源桶。
3. 修正 Android 世界地图与地图入口区域的横向扩展布局。
4. 把 PC/Android 地图 UI 资源做成同源输出，避免双份手改。

### 阶段 C：场景 render scale 试点

1. 新增 `scene_render_scale`。
2. 仅迁移 render-only 路径。
3. 不改 `get_logic_w/h()`。
4. 不改战斗布点和 camera gameplay 语义。
5. 先在少量地图和指定设备档位灰度。

### 阶段 D：大图与缓存策略

1. 世界地图主图改按需加载/释放。
2. 对高倍率大图建立单独缓存预算。
3. 地图入口 HUD 装饰资源与主图资源分层缓存。

## 9. 明确不建议的做法

1. 不建议直接把 Android 场景逻辑基线从 `1080x720` 改到更高。
2. 不建议把 `World::SetScale()` 当成高清开关。
3. 不建议只改 Android unpacked 或只改 PC resource，一端修好了另一端会继续回退。
4. 不建议把 Android 世界地图主图区继续交给比例锚点横向扩展。
5. 不建议把世界场景 `/map/*` 的 mipmap 优化误认为“世界地图 / 地图入口 UI 已经一起变清楚”。

## 10. 最终建议

如果目标是“结合 MT3 客户端现状，把地图高清显示做稳，不再反复出现地图发虚、模糊”，建议按下面的优先级推进：

1. **先治理地图 UI 资源倍率**
   - `worldmapbg/ccditu`
   - `logoinfo` 里的地图入口相关切图
   - 这是最直接、最稳的清晰度收益。

2. **再治理地图 UI 布局扩展方式**
   - 修 Android 世界地图主图区横向扩展
   - 修主场景地图入口区域的比例锚点扩张
   - 这是防止“换了高清图仍然被撑糊”的关键。

3. **最后进入场景 render scale 实装**
   - 保持逻辑尺寸不变
   - 只提高 render density
   - 这是提升世界场景底图观感、又不引入玩法漂移的正确路径。

换句话说，MT3 地图高清化不是一个“开关”，而是一组必须拆开的工程：

- 场景世界渲染高清化
- 世界地图与地图入口 UI 高清化
- 分辨率与玩法坐标解耦

只有按这个拆法推进，才能既改善画面，又不把地图点击、战斗站位、相机视野和旧脚本一起带偏。

## 附录 A：场景地图与地图相关 UI 放大/扩展分类表

### 分类口径

- **全局放大**：界面本身工作在 UI logic 坐标里，落屏时再按 `screen / ui_logic` 做统一缩放；在 `1920x1080`、`2340x1080` 这类常见设备上通常接近 `1.5x`，在 `2560x1440` 上通常接近 `2.0x`。
- **近似 1:1**：核心位图在布局里的显示尺寸与 imageset 原图尺寸接近，界面发虚主要来自“全局放大”，而不是布局内部的二次拉伸。
- **横向扩展**：布局里存在 `right.scale = 1` 这类锚定方式，宽度跟随父容器变化，界面会发生明显的横向撑开。

### 额外说明

1. **最容易“看起来糊”的不是所有地图相关 UI，而是“大位图 + 全局放大”这一类。**  
   所以世界地图主图是首要治理对象，地图入口按钮和挂机地图选择弹窗优先级更低。

2. **PC 世界地图和 Android 世界地图不是同一种失真模型。**  
   PC 侧核心问题更接近“近似 1:1 主图被整体放大”；Android 侧更接近“主图容器本身还在横向扩展”。

3. **地图入口 HUD 与世界地图要分开治理。**  
   前者更偏“控件区域被全局放大或横向扩展”，后者更偏“主图资源倍率不足或主图区被撑宽”；两类问题的修法不同，不能混成一套。
