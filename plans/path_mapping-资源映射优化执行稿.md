## 1. 执行摘要

这份方案的目标不是再把 `~68%` 当作默认可兑现承诺，而是把资源映射治理拆成三档更符合工程事实的目标：

- **稳定基线目标**：保持干净、可追溯、无污染输出的 `29.5% ~ 30.0%`
- **离线增强目标**：先引入 txt manifest 驱动种子，再叠加内容匹配与结构匹配，把覆盖率推进到 `38% ~ 45%`
- **运行时伸展目标**：只有在“通用运行时采集链 + 批量功能遍历 + 自动回写工具链”全部落成后，才把 `50% ~ 68%` 视为可争取的区间

结论先行：

- 仅靠当前已落地的离线能力，**无法验证覆盖率一定能达到 `~68%`**
- 当前最可靠的短期目标，是把基线稳定在 `29.56%`，优先吃下 txt manifest 的高置信增量，再把离线能力推进到 `38% ~ 45%`
- `~68%` 只能作为 **Phase 3C 完整落地后的 Stretch Goal（有条件上限）**

## 3. 根因修订版

### 3.1 结构性主因

**根因 A — 缺少同版本权威命名源**

这是当前覆盖率长期卡在 `29.56%` 左右的第一主因。

- `E:\橙子西游\assets\res\` 本身是 CRC 仓
- 当前版本没有完整、同版本、同构建的带命名原始目录可直接扫描
- 解包后已恢复命名的目录只覆盖了部分子树，剩余长尾依然是裸 CRC32 文件

结论：**没有权威命名源时，离线生成器只能依赖 seed 映射和猜测，不可能天然接近 100%。**

**根因 B — 历史 seed 映射与当前版本存在漂移**

当前映射虽然有 `74,874` 条，但对现网 `48,380` 个目标仅命中 `14,299`。  
说明现有 seed 只能覆盖交集，不能代表当前版本全集。

结论：**历史映射是“弱参考源”，不是“权威真值源”。**

### 3.2 工程性主因

**根因 C — 离线内容恢复对加密长尾的收益很低**

当前覆盖率报告已经证明，离线内容扫描尝试量很大，但有效增量很小：

- 内容变体匹配命中 `138`
- 解密后内容变体匹配命中 `101`
- 生成新增条目 `0`

结论：**当前离线内容识别链还不足以支撑大幅度 uplift。**

**根因 D — 运行时采集链还停留在局部取证阶段**

当前仓库有两类运行时相关资产：

- `tools/runtime/lj_runtime_key_probe.js`：偏解密/密钥探针
- `mapping_probe_res/runtime_owner_probe_usage_20260327_180210.md`：偏模型 owner 证据链采样

但它们都不是：

- 通用的全资源采集器
- 可直接回写正式 `path_mapping` 的自动链
- 能稳定覆盖地图、UI、技能、特效、脚本、音频等全域的系统

结论：**当前仓库还不具备直接兑现 `+15,000` 条运行时映射增量的能力。**

### 3.3 已排除或降级的假性根因

以下问题不是当前覆盖率长期受限的主因：

| 假设 | 当前判断 |
|------|----------|
| 路径大小写不一致 | 已规范化，不是主因 |
| 分隔符差异 | 已统一正斜杠，不是主因 |
| CRC32 算法不兼容 | 当前实现与工具链一致，不是主因 |
| 少量脏路径污染 | 已可控，但只影响质量，不解释大缺口 |

## 4. 目标重定义

### 4.1 三档目标

| 档位 | 覆盖率区间 | 可信度 | 含义 |
|------|------------|--------|------|
| A. 稳定基线 | `29.5% ~ 30.0%` | 高 | 当前必须守住的稳定值 |
| B. 离线增强 | `38% ~ 45%` | 中到高 | 先吃 manifest 高置信种子，再叠加 3A/3B 试验 |
| C. 运行时伸展 | `50% ~ 68%` | 低到中 | 依赖 3C 完整工程化和大规模功能遍历 |

### 4.2 对 `~68%` 的正式口径

`~68%` 应调整为：

- **Stretch Goal**
- **依赖运行时采集落地后的条件上限**
- **不能作为 Phase 1~4 完成后的默认结果**

换句话说：

- 如果只做离线链路增强，目标应写成 `38% ~ 45%`
- 只有运行时采集链完整落地，才讨论 `50% ~ 68%`

## 5. 分阶段执行方案

### Phase 0 — 基线稳固与污染收口（P0，1-2 天）

**目标**

- 保持当前 `29.56%` 基线稳定
- 确保无污染路径写入正式映射
- 确保解包输出目录不再出现错误子目录/伪文件

**交付物**

- 干净的 `path_mapping.ljpm / path_mapping.txt`
- 覆盖率报告中 `saved_mapping_drift=0`
- 解包后不再出现 `res` / `resource` / `2ei` / `2ej` / `za1` / `2nmo.re`

**验收标准**

- 生成映射成功
- GUI 重载成功
- 解包目录结构正确
- 覆盖率不低于当前基线

### Phase 1 — 缺口画像与样本基准集（P0，2-3 天）

**目标**

- 不是直接提覆盖率
- 而是把 `34,081` 个缺口拆成可行动的类型与子域

**工作项**

1. 建立缺口样本集
2. 对未命中 CRC 做文件头探测与快速分类
3. 输出目录分布、类型分布、是否加密、可否解密、是否与 MT3 同内容等统计
4. 为后续 3A/3B 制作验证集

**建议输出**

- `gap_profile.csv`
- `gap_profile_summary.md`
- 每类至少 100 条人工抽样校验记录

**验收标准**

- 能回答“哪些目录最值得优先做”
- 能回答“哪些类型离线有希望，哪些必须走运行时”

### Phase 1.5 — txt manifest 驱动种子导入（P0，2-4 天）

**目标**

- 把 `E:\jiebao` 已验证有效的 txt manifest 方法迁入当前映射治理链
- 不再依赖“只扫目录猜路径”，而是让文本清单直接成为高置信候选源

**方法来源**

- `_lj_unpacker_common.py`：路径规范化 + `CRC32(path)` 命中数字 CRC 文件
- `pipeline.py`：多 manifest 合并、多源索引、恢复计划、大小写回退、缺失诊断
- `manifest_seed_pipeline.py`：当前仓库中的落地原型，实现 manifest 命中、差集、冲突与合并候选输出

**当前可直接复用的 manifest**

- `E:\jiebao\main.txt`
- `E:\jiebao\imagesets.txt`
- `E:\jiebao\lua-layout.txt`
- `E:\jiebao\文件解密.txt`
- `E:\jiebao\model.txt`

**建议落地方式**

1. 先新增一个 Python 侧 manifest seed 管线，而不是马上把所有逻辑塞进 GUI
2. 每条 txt 清单路径先做：
   - 斜杠统一
   - 可选 lowercase
   - UTF-8 CRC32 计算
3. 只有当计算出的 CRC 存在于 `E:\橙子西游\assets\res` 时，才进入高置信候选集
4. 输出三份报告：
   - `manifest_direct_hits.tsv`
   - `manifest_new_hits.tsv`
   - `manifest_crc_conflicts.tsv`
5. 再把高置信候选合并进标准 `path_mapping.ljpm`

**当前工具入口**

```powershell
python dependencies/SuperLJFilePackUnpack/tools/manifest_seed_pipeline.py `
  --res-dir E:\橙子西游\assets\res `
  --mapping E:\橙子西游\assets\mapping\path_mapping.ljpm `
  --output-dir E:\橙子西游\assets\mapping\manifest_seed_reports `
  --jiebao-root E:\jiebao `
  --promote-dir E:\橙子西游\assets\mapping\manifest_seed_promoted
```

**当前实测收益**

- 合并后可直接命中：`10,769`
- 其中新增命中：`4,413`
- 理论新覆盖率：**`38.68%`**
- 原型脚本首轮真实并入后：**`4,430` 条新增 CRC，合并候选覆盖率 `38.71%`**

**注意**

- 这一步是“高置信 seed 导入”，不是“完全恢复所有路径”
- `model.txt` 当前收益极低，应放低优先级
- `main.txt`、`imagesets.txt`、`文件解密.txt` 应优先接入

**验收标准**

- 能稳定生成 `manifest_new_hits.tsv`
- 新增条目并入后，覆盖率显著高于 `29.56%`
- 差集报告中的 1 条 CRC 路径冲突能被单独隔离和复核
- 能输出可直接试载的 `path_mapping_manifest_seed.txt / .ljpm`

**目标**

### Phase 3A — 离线内容等价匹配试验（P1，3-5 天）

**目标**

- 先证明“内容完全一致”的条目能稳定恢复，而不是先承诺全量增益

1. 对橙子西游解密样本与 MT3 同类目录建立指纹库

- 保守：`+800 ~ +1,500`
- 乐观：`+2,500`
- 在 manifest seed 基线上叠加后的覆盖率区间：`40.3% ~ 43.9%`

**推进门槛**

- 样本 precision 必须 `>= 95%`
- 样本 uplift 必须 `>= 3%`
- 否则不进入全量扫描

### Phase 3B — 结构化模式匹配试验（P2，2-3 天）

**目标**

- 在已验证目录模式内补少量高置信条目

**适用范围**

- `model/`
- `effect/`
- `map/`
- `ui/`
- `script/`
- `table/`
- `sound/`

**约束**

- 只能在已有路径模板、类型识别和尺寸特征同时支持时生成候选

**收益预期修订**

- 保守：`+300 ~ +600`
- 乐观：`+1,000`
- 在 manifest seed + 3A 基线上叠加后的覆盖率区间：`41.0% ~ 45.9%`

**推进门槛**

- 单目录样本 precision 必须 `>= 98%`
- 任一目录若 precision 不达标，立即停做该目录模板扩展

### Phase 3C.0 — 通用运行时采集链建设（P1，5-8 天）

## 6. 重新排序后的执行顺序

```text
Phase 0 基线稳固
  -> Phase 1 缺口画像
  -> Phase 1.5 txt manifest 驱动种子导入
  -> Phase 2 工具链补完
  -> Phase 3A 离线内容等价试验
  -> Phase 3B 结构化匹配试验
  -> Phase 4 自动化与回归
  -> Phase 3C.0 通用运行时采集链建设
  -> Phase 3C.1 运行时全域采集
```

排序原则：

- 先把“能不能复验”解决，再做“能不能提覆盖率”
- 先吃掉 txt manifest 这类已被实测验证的高置信增量，再做重型猜测链
- 先做离线低风险试验，再投入高成本运行时采集
- 运行时链路放后面，不是因为不重要，而是因为它最重、最贵、最依赖环境

## 7. 验证方法与停机条件

### 7.1 通用验证指标

1. **CRC32 一致性**
   - 抽样 `1000` 条验证 `CRC32(normalized_path) == stored_crc32`
2. **正向命中率**
   - `res/` 中 `48,380` 个文件被映射覆盖的比例
3. **反向覆盖率**
   - 映射条目中有多少条实际命中目标目录
4. **污染检测**
   - 确认无低置信脏路径写入正式映射
5. **解包回归**
   - 用新映射完整解包并检查目录结构、失败项、冲突项

### 7.2 阶段停机条件

以下任一条件触发时，应暂停扩大范围，先回到根因分析：

- Phase 3A 样本 precision `< 95%`
- Phase 3B 单目录 precision `< 98%`
- 任一阶段新增条目导致解包错误目录回归
- 映射保存后重载命中率下降
- 运行时采集日志噪声过大，无法稳定回写

## 8. 风险与缓解

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 历史 seed 与当前版本差异过大 | 离线内容匹配收益低 | 优先改用 txt manifest 这种已验证的高置信候选源 |
| txt manifest 本身含旧路径或脏路径 | 新增错误映射 | 仅接受 CRC 命中当前 `assets/res` 的条目，并输出差集/冲突报告 |
| 加密链路无法稳定解密 | 缺口画像和内容匹配失真 | 先做文件头快速探测，必要时降级为类型级别统计 |
| 结构化模板误判 | 把错误路径写入正式映射 | 目录级 precision 门槛 + CRC32 回算 + 回归解包 |
| 运行时采集范围不足 | 3C 收益远低于预期 | 先建设通用采集链，再投入功能遍历 |
| 运行时环境搭建成本高 | 3C 延期 | 把 68% 改成 Stretch Goal，不把它绑定到 P0/P1 交付 |
