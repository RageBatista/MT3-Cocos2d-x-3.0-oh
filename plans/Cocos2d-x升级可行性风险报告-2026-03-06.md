# Cocos2d-x 升级可行性风险报告（面向当前高清化目标）

## 1. 文档信息

| 字段 | 内容 |
|------|------|
| 文档版本 | v1.0 |
| 生成日期 | 2026-03-06 |
| 评估范围 | MT3 客户端当前分支 |
| 评估目标 | 判断“为了更快拿到高清化收益，是否应该升级 Cocos2d-x” |
| 结论摘要 | 当前阶段不建议升级主版本；建议继续基于现有 2.0 分支做局部渲染增强 |

## 2. 执行摘要

### 2.1 最终结论

1. 对当前目标“最快看见明显提升”而言，升级 Cocos2d-x **不可取**。
2. 最优路径不是 `2.0 -> 3.x/4.x`，而是：
   - 保持当前 `cocos2d-2.0-rc2-x-2.0.1`
   - 在 `engine/renderer` 做局部增强
   - 在 `FireClient/Application` 完成接线
3. 如果一定要评估升级，应该先做隔离原型，不应进入当前 P0/P1 交付主线。

### 2.2 结论原因

1. 当前主收益点在内部分辨率、AA、后处理链和夜景/水面，不在 Cocos 主版本缺失。
2. 仓库现有代码已经具备 `CCRenderTexture`、ShaderCache、自定义 effect、水面扭曲、夜景 ColorBalance 等基础能力，足以支撑本轮高清化。
3. 升级 Cocos2d-x 会同时引爆工具链、API、CEGUI、tolua、Spine、ANGLE/EGL、多平台启动层等多条链路，收益与成本严重失衡。

## 3. 仓库现状事实

### 3.1 工具链与工程结构

1. Win32 客户端主线仍然固定在 `v120`。
2. `client/MT3Win32App/mt3.win32.vcxproj` 直接链接 `libcocos2d.lib`、`engine.lib`、`FireClient.lib`。
3. `client/MT3Win32App/FireClient.win32.vcxproj` 是可重编译静态库，且大量源码直接包含旧版 Cocos2d-x 头文件。
4. `client/FireClient/Application/Framework/LuaEngine*.cpp`、`LuaFireClient*.cpp` 绑定层体量很大，任何底层 API 变化都会放大改动范围。

### 3.2 现有渲染能力

1. 当前渲染器已经有 `CCRenderTexture`。
2. 当前渲染器已经有自定义 shader 入口和若干 effect 分支。
3. 当前世界层已经有夜景与水面逻辑。
4. 当前真正缺的是：
   - 更高内部渲染分辨率
   - 完整 AA 路线
   - 更丰富的 post-process effect

结论：这 3 个目标都可以先在现有版本内完成，不需要先升 Cocos。

## 4. 升级选项评估

### 方案 A：保持当前 2.0，做局部增强

| 维度 | 结论 |
|------|------|
| 可行性 | 高 |
| 工作量 | 中 |
| 风险 | 低到中 |
| 与当前目标匹配度 | 最高 |

说明：

1. 能直接解决 1080p/1440p、AA、LUT、锐化、柔和发光、水面/夜景。
2. 不破坏当前 v120、FireClient、CEGUI、Lua 绑定基本结构。
3. 可灰度、可回滚，符合当前项目约束。

### 方案 B：升级到 Cocos2d-x 2.2.x

| 维度 | 结论 |
|------|------|
| 可行性 | 中 |
| 工作量 | 中到高 |
| 风险 | 中 |
| 与当前目标匹配度 | 低 |

说明：

1. 可能拿到部分中间版本改进，但对当前目标的决定性收益有限。
2. 仍要承担 API 适配、兼容性验证、第三方库联调成本。
3. 这不是“最快见效”的路线。

### 方案 C：升级到 Cocos2d-x 3.x / 3.17.2-oh

| 维度 | 结论 |
|------|------|
| 可行性 | 低 |
| 工作量 | 极高 |
| 风险 | 极高 |
| 与当前目标匹配度 | 极低 |

说明：

1. 与 `v120` 工具链约束冲突明显。
2. `CC*` API 到 3.x 新 API 的迁移量不是点状修改，而是系统性重写。
3. 当前项目并非纯 Cocos2d-x 客户端，而是 `FireClient + Nuclear + CEGUI + tolua + Spine + 平台层` 混合系统，升级成本会级联放大。

## 5. 主要风险分项

### R1：工具链约束冲突

1. 当前 Win32 主线明确依赖 `v120`。
2. 一旦新 Cocos 需要更高 C++ 标准，客户端主工程、依赖库、构建脚本都会连带重做。
3. 这是硬风险，不是单纯代码量问题。

### R2：API 面大且耦合深

1. `FireClient/Application` 大量代码直接使用旧版 Cocos 类型和接口。
2. `engine/renderer` 直接依赖旧版 shader、GL 状态缓存、纹理类型。
3. 这类迁移不是“适配几处 include”，而是渲染层和调用层双向重构。

### R3：CEGUI 渲染后端联动风险

1. 当前项目 UI 不是原生 Cocos UI，而是 CEGUI。
2. 只要 Cocos 版本变化，CEGUI 的 Cocos renderer module、纹理目标、几何缓冲逻辑都要一起验证。
3. 这会显著放大 UI 回归范围。

### R4：生成代码与绑定层风险

1. Lua 绑定层不是少量手写桥接，而是大量生成代码。
2. 底层类型、枚举、接口一旦变化，就要改 `.pkg`、重新生成、再做全量回归。
3. 当前高清化目标不需要承担这类成本。

### R5：平台层风险

1. Win32 使用 EGL/GLES/ANGLE 链路。
2. iOS 启动层和 EAGLView 也有自己的历史接口。
3. 升级 Cocos 后，平台初始化和渲染上下文行为都可能变化，黑屏和兼容性问题风险高。

## 6. 收益与成本对比

| 方案 | 预计收益落地速度 | 预计改造周期 | 与当前目标的性价比 |
|------|------|------|------|
| 当前 2.0 局部增强 | 快 | 2-3 周 | 高 |
| 2.2.x 升级 | 中 | 1-2 月 | 低 |
| 3.x / 3.17.2-oh 升级 | 慢 | 3-6 月以上 | 极低 |

结论：

1. 如果目标是本季度内明显提画质，升级 Cocos 不划算。
2. 如果目标是长期做“引擎代际迁移”，那是独立立项，不应混入本轮高清化任务。

## 7. 建议决策

### 当前推荐

1. 当前主线继续保留 `cocos2d-2.0-rc2-x-2.0.1`。
2. 本轮只做：
   - 内部渲染分辨率提升
   - AA
   - 后处理链
   - 夜景 / 水面增强
3. 所有收益优先在 `engine/renderer` 和 `FireClient/Application` 实现。

### 如果管理层坚持评估升级

只能按下面方式执行：

1. 开独立原型分支，不污染当前交付线。
2. 先做最小验证：
   - 单窗口启动
   - 单场景渲染
   - 单个 CEGUI 界面
   - Lua 最小绑定
3. 原型通过前，不迁主分支，不动当前 P0/P1 目标。

## 8. 最终结论

针对当前目标“最快看见明显提升”，`升级 Cocos2d-x` 的结论是：

1. **当前不可取**
2. **不应进入本轮实施范围**
3. **应当改为现有 2.0 分支上的局部渲染增强**

换句话说，本轮最正确的工程决策不是“升级引擎版本”，而是“把现有引擎的画质潜力先吃满”。
