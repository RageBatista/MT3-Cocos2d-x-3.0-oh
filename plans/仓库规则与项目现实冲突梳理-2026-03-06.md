# 仓库规则与项目现实冲突梳理

日期：2026-03-06  
范围：`AGENTS.md`、`.claude/RULES.md`、`.claude/BUILD_GUIDE.md`、Win32 客户端工程、编码现状、构建入口  
目的：判断“规则是否与项目现实冲突”，并给出可执行的收敛方案

## 结论

存在冲突，而且是结构性冲突，不是个别表述问题。

当前仓库至少同时存在三套“真相来源”：

1. `AGENTS.md`：事实更接近当前仓库，但仍有过宽约束。
2. `.claude/RULES.md`：混合了硬约束、历史信息、教程、过时脚本，漂移最明显。
3. 实际工程与源码：编码、构建链、可改范围，比规则写得更复杂。

如果不收敛，直接后果有三类：

1. AI/开发者会误判“哪些文件能改、哪些必须重编”。
2. 编码规则会把合法的历史文件误判为违规。
3. 构建规则会把不存在的脚本和过时流程当成必经路径。

## P0 冲突

### 1. “FireClient/libcocos2d 不可改”与实际源码可重编冲突

规则现状：

- `AGENTS.md` 把 `client/FireClient/FireClient.lib` 写成预编译关键约束，并在“不可修改的库”中列出 `client/FireClient/FireClient.lib` 与 `cocos2d-2.0-rc2-x-2.0.1/**/*.lib`。
- `.claude/RULES.md` 也把 `FireClient.lib` 写成预编译库，并在编译顺序里写成“FireClient.lib (预编译)”。

实际项目：

- `client/MT3Win32App/FireClient.win32.vcxproj` 是可编译的 `StaticLibrary`，`PlatformToolset=v120`。
- `client/MT3Win32App/FireClient.win32.vcxproj:175` 直接编译 `..\FireClient\Application\Framework\ResolutionAdapter.cpp`。
- `cocos2d-2.0-rc2-x-2.0.1/cocos2dx/proj.win32/cocos2d-win32.vcxproj` 是可编译的 `DynamicLibrary`。
- `cocos2d-2.0-rc2-x-2.0.1/cocos2dx/proj.win32/cocos2d-win32.vcxproj:188` 直接编译 `..\platform\win32\CCEGLView.cpp`。
- `client/Build-MT3-v120.ps1` 的构建步骤显式包含：
  - `FireClient.win32.vcxproj`
  - `cocos2d-win32.vcxproj`
  - `mt3.win32.vcxproj`

风险：

- 会误导开发者以为 `FireClient/Application` 和 `cocos2dx/platform/win32` 不能改。
- 会误导 AI 把“不能升级 ABI”错误扩大成“不能改源码”。

优化建议：

1. 把“不可修改”改成“不可跨工具集替换或手工编辑二进制产物”。
2. 明确区分三件事：
   - `lib/.dll` 二进制产物：不可手工编辑，不可跨 ABI 替换。
   - 对应一方源码：可修改、可重编。
   - 第三方大版本升级：高风险，单独评估。
3. 在规则里把表述改成：
   - `FireClient.lib` 是由 `FireClient.win32.vcxproj` 产出的本地二进制产物。
   - 允许修改 `client/FireClient/Application/**` 并重编 Win32。
   - 禁止使用非 `v120` 工具集重编这些产物。

### 2. “所有 C++ 必须 UTF-8 BOM”与仓库真实编码分布冲突

规则现状：

- `AGENTS.md:197` 规定 `.cpp/.c/.h/.hpp` 必须 `UTF-8 with BOM`。
- `.claude/RULES.md:517` 也规定 `.cpp/.c/.h/.hpp` 必须 `UTF-8 with BOM`。
- 同时多处规则又要求“禁止混用不同编码”。

实际项目抽样与统计：

- `client/MT3Win32App/main.cpp`：`NO-BOM`，且 `UTF8Strict=False`，是非 UTF-8 历史文件。
- `client/FireClient/Application/Framework/ResolutionAdapter.cpp`：`UTF8-BOM`。
- `engine/engine/nuengine.cpp`：`UTF8-BOM`。
- `cocos2d-2.0-rc2-x-2.0.1/cocos2dx/platform/win32/CCEGLView.cpp`：`NO-BOM`，但 `UTF8Strict=True`。

目录级统计：

- `client/MT3Win32App`：`Total=10, UTF8-BOM=0, UTF8-noBOM=3, UTF16=1, NonUTF8=6`
- `client/FireClient/Application`：`Total=451, UTF8-BOM=449, UTF8-noBOM=2, UTF16=0, NonUTF8=0`
- `engine`：`Total=246, UTF8-BOM=246`
- `cocos2dx/platform/win32`：`Total=23, UTF8-BOM=0, UTF8-noBOM=18, NonUTF8=5`

风险：

- 规则把“第一方目标状态”误写成“仓库现状”。
- 一旦机械执行全仓统一转码，极容易破坏 Win32 启动层和第三方源码。

优化建议：

1. 把编码规则拆成“目标状态”和“保持策略”：
   - 第一方新改 C++：优先 `UTF-8 with BOM`
   - 已存在历史文件：保持原编码回写
   - 第三方/vendor：严禁批量转码
2. 把“禁止混合编码”改成“禁止在未确认边界的同一子系统内随意转码”。
3. 增加目录作用域：
   - `client/FireClient/Application/**`、`engine/**`：可以逐步收敛到 `UTF-8 BOM`
   - `client/MT3Win32App/**`、`cocos2dx/platform/win32/**`：先保留原编码，按文件治理

### 3. `.rc` 编码规则在 `AGENTS.md` 与实际项目冲突

规则现状：

- `AGENTS.md:198` 写的是 `.rc = UTF-8 with BOM`
- `.claude/RULES.md:518` 写的是 `.rc = UTF-16 LE with BOM（优先）或 UTF-8 with BOM`

实际项目：

- `client/MT3Win32App/mt3.rc`：`UTF16-LE-BOM`
- `client/Launcher/Launcher.rc`：`UTF16-LE-BOM`
- `tools/engine/SpriteEditor/SpriteEditor.rc`：`UTF16-LE-BOM`
- 工具和第三方目录下还有大量 `UTF8-BOM`、`OTHER/NO-BOM` 的 `.rc`

风险：

- 这是规则内部自相矛盾。
- 对客户端主线来说，实际情况明显更接近 `.claude/RULES.md`，而不是 `AGENTS.md`。

优化建议：

1. 统一成一条：
   - 主线 Win32 客户端/工具 `.rc`：保持原编码，优先 `UTF-16 LE with BOM`
2. 禁止在根规则里写“所有 `.rc` 必须 UTF-8 BOM”。
3. 为 `.rc` 单独加一个“按目录例外表”。

### 4. `.claude/RULES.md` 仍引用不存在的脚本

规则现状：

- `.claude/RULES.md:294` 仍写 `build_mt3_v120_complete.bat`
- `.claude/RULES.md:425` 仍写 `check_env.bat`
- `.claude/RULES.md:432` 还把 `build_mt3_v120_complete.bat` 当推荐编译路径

实际仓库：

- `check_env.bat`：不存在
- `build_mt3_v120_complete.bat`：不存在
- 存在的有效脚本是：
  - `client/Build-MT3-v120.ps1`
  - `tools/scripts/Check-v120Toolset.ps1`

风险：

- 文档执行即失败。
- AI/新人会沿着失效入口走。

优化建议：

1. `.claude/RULES.md` 中所有脚本入口统一替换为现存脚本。
2. 增加“已废弃脚本”表，不再把废弃脚本写进主流程。
3. 构建主入口固定为：
   - 检查：`tools/scripts/Check-v120Toolset.ps1`
   - 构建：`client/Build-MT3-v120.ps1`

### 5. `.claude/RULES.md` 的项目规模、架构、服务目录已明显过时

规则现状：

- `.claude/RULES.md:16` 仍写代码规模 `~96,000`
- `.claude/RULES.md:23` 只列了 8 个服务模块
- `.claude/RULES.md:359` 仍写“五层架构”

实际仓库：

- `AGENTS.md:50` 已更新为 `~5,300,000+`
- `AGENTS.md:84` 写的是“四层架构`
- `server/server` 实际目录有 11 个：
  - `common`
  - `game_server`
  - `game_server_f`
  - `gate_server`
  - `name_server`
  - `proxy_server`
  - `sdk_server`
  - `spirit_server`
  - `trans_server`
  - `web_app`
  - `zone_server`

风险：

- `.claude/RULES.md` 已经不适合承担“项目事实基线”的角色。

优化建议：

1. 事实类内容只保留在 `AGENTS.md`。
2. `.claude/RULES.md` 删除规模、模块数量、学习路线、教程化内容。
3. `.claude/RULES.md` 仅保留：
   - 工具链硬约束
   - ABI 约束
   - 编码边界
   - 生成代码边界

## P1 冲突

### 6. 命名与预编译头规则互相打架

规则现状：

- `AGENTS.md:745` 写函数名 `camelCase`
- `.claude/RULES.md:163` 写函数 `PascalCase`
- `AGENTS.md:750` 写“必须包含 `stdafx.h`”
- `.claude/RULES.md:174` 写“每个 `.cpp` 第一行 `#include "nupch.h"`”

实际项目：

- `client/FireClient/Application/Framework/GameApplication.cpp:1` 是 `#include "stdafx.h"`
- `client/MT3Win32App/main.cpp:1` 不是 `stdafx.h`，而是 `#include "main.h"`
- `engine/common/nustdafx.cpp:1` 用的是 `nustdafx.h`
- 代码命名风格也是子系统混合，而不是全仓单一规则

风险：

- 这是典型“把某个子系统习惯误写成全仓规则”。

优化建议：

1. 命名规则改成“优先遵循所在目录既有风格”。
2. 预编译头规则按子系统拆分：
   - `client/FireClient/Application/**`：遵循 `stdafx.h`
   - `engine/**`：遵循 `stdafx.h / nustdafx.h` 现状
   - `client/MT3Win32App/**`：按工程文件现状，不强制一刀切

### 7. “禁止混合编码”与“保持原始编码”本身冲突

规则现状：

- 一方面要求所有文件统一 UTF-8
- 另一方面又要求 AI 必须保持原始编码、同编码写回

实际项目：

- 仓库内同时存在：
  - `UTF8-BOM`
  - `UTF8-noBOM`
  - `UTF16-LE-BOM`
  - `GBK/CP936` 历史文件

风险：

- 当前版本规则不可同时满足。

优化建议：

把这条改成两级原则：

1. 第一原则：修改已有文件时，必须保持原始编码。
2. 第二原则：新增第一方文件时，按目标编码规范创建。

## 规则收敛方案

### 方案 A：角色分层

建议重新定义三份文件的职责：

1. `AGENTS.md`
   - 只写仓库事实和高层边界
   - 作为单一事实入口
2. `.claude/RULES.md`
   - 只写硬约束
   - 不写教程、不写学习路线、不写过时脚本
3. `.claude/BUILD_GUIDE.md`
   - 只写已验证可执行的命令
   - 输出路径、验证命令、已知构建陷阱

### 方案 B：作用域矩阵

建议增加一张“按目录治理”的规则矩阵：

| 范围 | 是否可改 | 编码策略 | 构建策略 |
|---|---|---|---|
| `client/FireClient/Application/**` | 可改 | 保持原编码，新增优先 UTF-8 BOM | 改后重编 `FireClient + MT3` |
| `client/MT3Win32App/**` | 可改 | 保持原编码，很多历史文件不是 UTF-8 | 改后重编 `MT3` |
| `engine/**` | 可改 | 现状基本 UTF-8 BOM | 改后重编 `engine + 下游` |
| `cocos2dx/**` 第一方补丁 | 可改但高风险 | 保持原编码 | 改后重编 `libcocos2d + 下游` |
| `dependencies/**` vendor | 原则上不改 | 保持原编码 | 仅在专项任务中处理 |
| `*.lib/*.dll` 产物 | 不手工编辑 | 不适用 | 只能由对应工程重编产出 |

### 方案 C：把“事实”与“目标”分开

建议所有规则都改成如下结构：

1. 当前现实
2. 目标状态
3. 执行策略
4. 例外目录

编码章节尤其要这样写，否则永远会和仓库现状冲突。

## 建议的立即整改顺序

### P0

1. 精简 `.claude/RULES.md`，删除过时脚本、过时规模、过时服务列表。
2. 修正 `FireClient/libcocos2d` 表述，从“不可修改”改成“不可跨 ABI 替换二进制，源码可改可重编”。
3. 统一 `.rc` 编码规则，删除 `AGENTS.md` 中“`.rc` 一律 UTF-8 BOM”。
4. 把编码规则改成“按原编码保持 + 新文件目标规范”。

### P1

1. 按目录定义预编译头与命名风格，不再写全仓单一规范。
2. 在构建文档中补充共享中间目录 `Release.win32` 的已知风险和 `MSB8028` 说明。
3. 把 `client/Build-MT3-v120.ps1` 升格为 Win32 主线唯一推荐入口。

### P2

1. 为 vendor/third-party 目录增加规则例外表。
2. 增加“历史编码白名单”。
3. 给规则增加自动校验脚本，但必须按目录和文件归属判断，不能全仓一刀切。

## 最终判断

当前规则体系的问题，不是“规则太少”，而是“规则层级混乱”：

1. 把事实、目标、教程、历史信息写在了一起。
2. 把第一方代码策略错误扩展到了历史文件和第三方代码。
3. 把“ABI 不可乱动”错误表述成了“源码不可修改”。

最优解不是继续补规则，而是先做一次“规则瘦身 + 作用域重构”。
