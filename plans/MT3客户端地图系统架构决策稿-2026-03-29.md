# MT3 客户端地图系统架构决策稿

## 文档信息

- 日期：2026-03-29
- 状态：建议评审版
- 适用范围：`Win32 / Android / iOS` 共享地图场景、小地图、大地图、地图 UI 叠层
- 决策目标：在不引入玩法坐标漂移和大规模引擎替换的前提下，提升地图场景清晰度、可维护性和性能稳定性

## 1. 结论先行

本轮对 MT3 的推荐选型不是引入第三方地图引擎，而是在现有 `Cocos2d-x 2.0 + Nuclear + FireClient + CEGUI` 体系上演进出一条适合游戏客户端的地图架构。

核心决策如下：

- 运行时地图引擎选型：保留现有 `Nuclear World + Cocos2d 渲染链`，不引入 `Mapbox / MapLibre / ArcGIS / OpenLayers` 作为游戏运行时底座。
- 地图数据形态选型：采用“离线栅格艺术底图 + 客户端对象覆盖层 + 配置驱动热点/标注”的混合架构。
- 地图 UI 形态选型：小地图、大地图、场景世界地图共享一套地图数据域，但分别使用不同的渲染预算和交互模型。
- 高清化实施策略：先做“资源倍率 + 采样链 + 缓存层 + 监控”，再做“场景 render scale”，最后才考虑接口拆分和行为迁移。
- 分辨率策略：保留现有 `scene logic` 与 `ui logic` 兼容语义，新增独立的 `scene render scale` 概念，避免直接改写旧 API。

## 2. 为什么不引入外部地图引擎

从行业能力看，`Mapbox / MapLibre / ArcGIS / Google Maps` 在在线地图、矢量瓦片、路径分析、POI 检索和地理空间生态上更强；但 MT3 的地图系统是“游戏场景地图”，主要约束并不相同。

MT3 当前不适合在运行时切换到外部地图引擎，原因有四个：

- 地图底图是美术资产，不是标准互联网地理数据，核心问题是贴图倍率、采样链和叠层逻辑，不是在线瓦片协议。
- 战斗、主城、场景对象、寻路和地图 UI 已深度绑定 `Nuclear::World`、`Scene`、Lua 配置和 C++ 调用链，替换运行时地图引擎会直接波及玩法与资源链。
- 现有问题更偏“显示发虚、资源倍率不足、布点缩放混用、缓存与加载链缺少分层”，这些问题在现有架构内就能解决。
- 迁移外部引擎的收益主要在在线 GIS 能力，不在 MT3 当前主问题域。

因此，外部地图引擎只建议作为“运营工具 / Web 编辑器 / 配置审校工具”的备选，不建议进入客户端主运行时。

## 3. 推荐目标架构

### 3.1 总体形态

推荐采用以下运行时模型：

- 底层场景：`Nuclear::World`
- 地图底图：离线艺术地图贴图，按地图区域和倍率进行资源分桶
- 地图覆盖层：NPC、任务点、传送点、路径点、战斗标记、交互热点
- 地图 UI：CEGUI 窗口与小地图/大地图面板
- 地图配置源：`map.cmapconfig`、`map.cworldmapconfig`、`SysConfig.resolution` 以及运行时场景对象

### 3.2 模块划分

建议新增或显式收敛为 7 个逻辑模块：

| 模块 | 责任 | 输入 | 输出 |
|---|---|---|---|
| `MapResourceDomain` | 地图底图、缩略图、标注贴图、路径点图标的资源装载与倍率选择 | 地图 ID、资源路径、设备档位 | 纹理句柄、尺寸元数据、资源命中率 |
| `MapSceneRenderDomain` | 场景地图底图渲染、地图相关 viewport、采样策略、mipmap 策略 | 场景逻辑尺寸、屏幕尺寸、render scale | 地图场景画面 |
| `MapOverlayDomain` | NPC、任务点、队友、路径、区域高亮、交互热点叠加 | 场景对象、任务数据、地图配置 | 覆盖层渲染批次、命中测试结果 |
| `MapUIDomain` | 小地图、大地图、地图筛选、地图搜索、悬浮提示 | UI 逻辑尺寸、地图元数据、覆盖层数据 | CEGUI 窗口与交互 |
| `MapNavigationDomain` | 寻路投影、路径采样、路径点稀疏化、终点落点 | 场景坐标、地图坐标、寻路结果 | 地图路径与目标点 |
| `MapCacheDomain` | GPU / 内存 / 文件 / 包体四级缓存与淘汰 | 资源请求、设备档位、地图切换事件 | 缓存命中率、回收事件 |
| `MapTelemetryDomain` | FPS、纹理峰值、加载时延、路径刷新频率、截图回归埋点 | 运行时指标、采样事件 | 性能面板、报警、对比报告 |

### 3.3 当前代码锚点

当前建议优先围绕以下锚点推进，不做跨域混改：

- `client/FireClient/Application/Framework/ResolutionAdapter.*`
- `client/FireClient/Application/Framework/GameApplication.cpp`
- `engine/engine/nuengine.cpp`
- `engine/engine/nucocos2d_wraper.cpp`
- `engine/renderer/nucocos2d_render.cpp`
- `client/resource/res/script/logic/mapchose/smallmapdlg.lua`

## 4. 地图资源与缓存层级

### 4.1 资源组织策略

地图相关资源建议按“地图域 + 倍率桶 + 资源类型”组织：

- 地图底图：`1x / 2x / 3x`
- 小地图图标：`1x / 2x`
- 路径点、目标点、任务标记：统一进入地图 UI 图标集
- 高频地图 UI：优先补齐 `2x`；仅高端机型启用 `3x`

不建议当前就引入运行时 SVG/矢量绘制。MT3 更适合“设计源可矢量，运行时产物仍是分倍率位图 atlas”。

### 4.2 缓存层级

建议建立四级缓存：

| 层级 | 目标 | 建议内容 | 淘汰策略 |
|---|---|---|---|
| `L0 GPU Cache` | 保证当前视口稳定渲染 | 当前地图底图、当前覆盖层图标、当前字体 atlas | 地图切换或显存阈值触发 |
| `L1 RAM Cache` | 降低频繁解码和 IO 抖动 | 已解码纹理、地图元数据、路径点图标 | LRU，按地图域与大小分组 |
| `L2 File Cache` | 降低 PFS/文件读取压力 | 地图图片二进制、缩略图、图标包、元数据 | 最近访问地图优先保留 |
| `L3 Package Cache` | 保证离线可用与版本回滚 | PFS / 包体内地图资源、缩略图与标注资源 | 版本包管理，不做运行时删改 |

### 4.3 缓存命中目标

- 小地图打开首帧：`L0/L1` 命中率目标 `> 95%`
- 切大地图 1 秒内：`L1/L2` 命中率目标 `> 90%`
- 同地图内路径刷新：不允许触发底图重新解码

## 5. 地图清晰度策略

### 5.1 底图

- 地图底图优先补齐 `2x` 资源桶，主城、常驻地图和高频活动地图优先补 `3x`
- 对 `/map/` 资源启用 `mipmap`，并维持线性过滤作为默认基线
- 只在扩展可用且设备白名单命中的情况下评估各向异性过滤，不做 Android 默认能力

### 5.2 覆盖层

- 覆盖层图标统一进入独立 atlas，避免小地图与 UI 通用大图集导致采样发虚
- 路径点、目标点、队伍标识统一使用整数像素对齐后的布局坐标
- 热点图标与小字体标注避免在同一批次里反复切纹理

### 5.3 字体与标签

- 小地图与地图悬浮提示统一改成语义字体 token，不再直接散落使用固定字号名称
- 标签字号优先依赖 `ui logic`，不跟 `scene logic` 走
- 地图上的文字提示优先走 UI 叠层，不直接混入场景底图

## 6. 性能预算

### 6.1 帧预算

目标帧率：

- `Win32`：大地图与场景地图目标 `60 FPS`
- `Android / iOS`：常规场景与小地图目标 `45~60 FPS`
- 极限弱机：允许降到 `30 FPS`，但地图拖动与寻路反馈必须稳定

建议预算：

| 子系统 | 目标预算 |
|---|---|
| 场景地图底图绘制 | `4.0 ms` |
| 地图覆盖层 | `2.0 ms` |
| 地图 UI | `2.0 ms` |
| 纹理绑定与状态切换 | `1.5 ms` |
| 留给其他场景内容 | `7.0 ms` |

### 6.2 内存预算

建议按设备档位限制地图工作集：

| 档位 | 地图纹理工作集 | 覆盖层/图标 | 字体 atlas | 说明 |
|---|---|---|---|---|
| 低端机 | `32 MB` | `8 MB` | `4 MB` | 仅启用 `1x/2x`，弱化预取 |
| 中端机 | `64 MB` | `12 MB` | `6 MB` | 默认目标档位 |
| 高端机 | `96 MB` | `16 MB` | `8 MB` | 可启用重点地图 `3x` |

### 6.3 绘制预算

- 小地图覆盖层 draw call 目标：`< 25`
- 大地图覆盖层 draw call 目标：`< 50`
- 地图 UI 打开时新增纹理绑定：`< 12`
- 单次切换地图允许的同步加载尖峰：`< 50 ms`

## 7. 监控与回归

必须补齐以下监控项：

- `map_open_ms`
- `map_texture_bind_count`
- `map_overlay_draw_calls`
- `map_gpu_resident_mb`
- `map_decode_ms`
- `map_cache_hit_l0/l1/l2`
- `smallmap_path_refresh_ms`
- `scene_map_fps_p50/p95`

回归建议至少覆盖：

- `720p`
- `1080p`
- `1440p`
- `21:9` 超宽屏
- 高 DPI Android 竖屏设备上的地图弹出链路

## 8. 分阶段实施建议

### Phase A：快赢阶段

- 主城、登录场景、高频地图补 `2x` 底图
- 地图图标独立 atlas
- 地图底图维持 `mipmap`
- 接入地图性能埋点

### Phase B：稳定阶段

- 建立 `MapCacheDomain`
- 抽离 `MapOverlayDomain`
- 小地图、大地图统一走地图元数据服务
- 设备档位驱动资源倍率选择

### Phase C：高清阶段

- 增加 `scene render scale`
- 将“渲染尺寸”和“玩法逻辑尺寸”分离
- 为高端设备开放重点地图 `3x`
- 接入地图截图回归

## 9. 不建议当前就做的事项

- 不建议直接把第三方互联网地图引擎塞进客户端主运行时
- 不建议直接修改 `adapter->get_logic_w/h()` 现有语义
- 不建议在旧渲染链上一次性全面上矢量地图
- 不建议先改 Lua 地图脚本坐标基线，再反推 C++ 适配

## 10. 最终决策

MT3 地图系统的推荐路线是：

- 架构选型：`现有引擎体系内演进`
- 地图模型：`离线栅格艺术底图 + 客户端覆盖层`
- 资源策略：`分倍率桶 + 分层缓存`
- 高清策略：`先采样与资源，再 render scale，最后接口迁移`
- 风险控制：`不直接改旧逻辑尺寸 API 语义`

这条路线能同时兼顾地图清晰度、玩法安全性、资源链现实和现有团队维护成本。
