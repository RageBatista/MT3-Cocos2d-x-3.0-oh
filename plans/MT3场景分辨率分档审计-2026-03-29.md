# MT3 场景分辨率分档审计

## 文档信息

- 日期：2026-03-29
- 状态：审计结论版
- 审计目标：梳理 `battle / viewport / Lua` 中对 `adapter->get_logic_w/h()` 及相关逻辑尺寸接口的依赖，判断是否可以安全拆分 `scene render scale` 与 `UI logic scale`

## 1. 审计结论

当前结论非常明确：

- `UI logic scale` 与 `scene logic scale` 在接口层已经部分分离。
- `scene render scale` 还没有成为独立的一等概念。
- 不能直接改写 `adapter->get_logic_w/h()` 的现有语义，否则会同时影响世界创建、投影矩阵、renderer display mode、战斗布点和 viewport 映射。
- 可以继续往地图清晰度推进，但正确路径应是“新增 render scale 能力”，而不是“修改旧逻辑尺寸返回值”。

因此，本轮决策为：

- 保持 `adapter->get_logic_w/h()` 继续表示“场景逻辑尺寸”
- 保持 `Engine::GetLogicWidth/Height()` 继续表示“UI 逻辑尺寸”
- 新增独立的 `scene render scale / render target size` 设计，不直接复用旧 API

## 2. 关键语义现状

`ResolutionAdapter` 当前同时维护两套逻辑尺寸：

- `get_logic_w/h()`：场景逻辑尺寸
- `GetLogicWidth/Height()` 与 `get_ui_logic_w/h()`：UI 逻辑尺寸

代码证据：

- `client/FireClient/Application/Framework/ResolutionAdapter.h`
- `client/FireClient/Application/Framework/ResolutionAdapter.cpp`
- `engine/engine/nuengine.cpp:1335`
- `engine/engine/nuengine.cpp:1342`

从 `Engine::GetLogicWidth/Height()` 的实现看，Lua 侧常见的 `Nuclear.GetEngine():GetLogicWidth()` 实际拿到的是 `ui logic`，而不是 `scene logic`。

## 3. 依赖点分层结果

本轮在运行时主链里共确认：

- `6` 个 C++ 文件直接依赖 `adapter->get_logic_w/h()` 或 `m_adapter->get_logic_w/h()`
- `3` 个主资源 Lua 脚本直接依赖 `Nuclear.GetEngine():GetLogicWidth/Height()`

### 3.1 一级风险：引擎与渲染硬依赖

这类调用一旦语义变化，会直接改变世界尺寸、投影矩阵或 render path。

| 文件 | 位置 | 当前用途 | 风险级别 |
|---|---|---|---|
| `engine/engine/nuengine.cpp` | `:290` | `World(this, m_adapter->get_logic_w(), m_adapter->get_logic_h())`，世界创建尺寸 | P0 |
| `client/FireClient/Application/Framework/GameApplication.cpp` | `:2187` | `BeginDraw(get_logic_w, get_logic_h)`，场景绘制入口 | P0 |
| `engine/engine/nucocos2d_wraper.cpp` | `:467-468` | 场景投影矩阵、视口中心、触摸/显示转换 | P0 |
| `engine/renderer/nucocos2d_render.cpp` | `:182-183` | renderer display mode 返回值 | P0 |

判断：

- 这些点都是“画面空间”和“场景空间”的基础语义。
- 任何直接修改 `get_logic_w/h()` 返回值的方案，都属于高风险方案。

### 3.2 一级风险：战斗布点与 viewport 数学依赖

战斗系统当前把 `get_logic_w/h()` 当成 battle resolution 的缩放基线。

| 文件 | 位置 | 当前用途 | 风险级别 |
|---|---|---|---|
| `client/FireClient/Application/Battle/SkillBuilder.cpp` | `:113-117` | 战斗方位点缩放、左右阵营布点 | P0 |
| `client/FireClient/Application/Battle/BattleManagerOperate.cpp` | `:265-268` | 观战布点缩放 | P0 |
| `client/FireClient/Application/Battle/BattleManagerOperate.cpp` | `:346-350` | 战斗 UI 布点缩放 | P0 |
| `client/FireClient/Application/Battle/BattleManagerOperate.cpp` | `:427-431` | 战斗实体布点缩放 | P0 |

配套 Lua 配置来源：

| 文件 | 位置 | 当前用途 |
|---|---|---|
| `client/resource/res/script/globalfunctionsforcpp.lua` | `:1039-1087` | 读取 `SysConfig.resolution` 的 `longa / wide / positions*` |

判断：

- 战斗布点不是简单“拿屏幕宽高居中”。
- 当前算法是“逻辑尺寸 ÷ 配置分辨率”得到缩放系数，再把布点映射进当前 viewport。
- 如果把 `scene logic` 改成新的高清尺寸，而 battle 配置仍沿用旧 resolution 表，极易出现站位偏移、技能特效偏移、观战 UI 错位。

### 3.3 二级风险：Lua UI 逻辑尺寸依赖

Lua 主资源脚本当前命中的 3 个文件都走 `Engine::GetLogicWidth/Height()`，本质上依赖的是 `ui logic`。

| 文件 | 位置 | 当前用途 | 风险级别 |
|---|---|---|---|
| `client/resource/res/script/logic/mapchose/smallmapdlg.lua` | `:73-74` | 小地图居中与窗口尺寸计算 | P1 |
| `client/resource/res/script/logic/login/loginbackground.lua` | `:82-83` | 登录背景 Spine 缩放 | P1 |
| `client/resource/res/script/logic/item/depot.lua` | `:683-686` | 仓库道具 tip 左右停靠 | P2 |

判断：

- 这 3 处与 `adapter->get_logic_w/h()` 没有直接耦合。
- 只要维持 `Engine::GetLogicWidth/Height()` 继续返回 `ui logic`，这批 Lua 不需要因为场景高清化而先改。

## 4. 风险归类

### 4.1 当前不能直接做的事

- 不能把 `ResolutionAdapter::get_logic_w/h()` 直接改成“更高 render 分辨率”
- 不能让 battle 继续使用旧 `SysConfig.resolution` 表，却改掉 `scene logic` 的数学基线
- 不能在未迁移 renderer / world / battle 之前，让 Lua 或 UI 先假设新的场景尺寸语义

### 4.2 当前可以安全做的事

- 继续增强地图贴图资源倍率与采样链
- 继续完善地图底图 mipmap 与缓存层
- 新增“仅用于渲染”的 render scale 概念
- 为 render-only 路径补充新的 accessor，而不破坏旧逻辑尺寸

## 5. 推荐拆分方案

推荐新增三组概念，避免旧接口语义漂移：

- `scene_logic_w/h`
  当前 `get_logic_w/h()` 的语义，继续服务玩法坐标、战斗布点、世界尺寸
- `ui_logic_w/h`
  当前 `GetLogicWidth/Height()` 的语义，继续服务 CEGUI 与 Lua UI
- `scene_render_w/h` 或 `scene_render_scale`
  新增语义，只服务渲染清晰度、离屏 buffer、贴图采样和高端机画质档位

### 5.1 推荐迁移顺序

第一步：

- 在 `ResolutionAdapter` 明确补出 render-size 设计接口，但默认返回当前兼容值
- 打日志观测 `scene logic / ui logic / render target / screen size`

第二步：

- 只迁移 render-only 调用点使用新接口
- 这一步不改战斗、不改世界逻辑尺寸、不改 Lua 语义

第三步：

- 若未来确实要做更深层场景高清化，再单独迁移 battle 相关算法
- battle 迁移必须与 `SysConfig.resolution` 表和布点算法一起评审

## 6. 对地图清晰度的直接影响

这次审计的含义不是“不能继续做高清化”，而是明确高清化的正确落点：

- 地图发虚可以继续通过 `高倍率资源 + mipmap + 更稳定的采样链 + render scale` 改善
- 不应该通过“修改战斗/场景逻辑尺寸 API”去换取清晰度
- 地图 UI 清晰度可以继续沿 `ui logic + 字体/DPI + 资源倍率` 这条线提升

## 7. 最终决策

本轮建议如下：

- 决策 1：不直接拆改旧 `get_logic_w/h()` 语义
- 决策 2：把 `scene render scale` 设计成新增能力，而不是兼容层魔改
- 决策 3：battle、viewport、world 创建链继续视为 P0 兼容区
- 决策 4：地图高清化继续推进，但先落在渲染与资源链，不先落在玩法尺寸链

这意味着下一阶段可以继续做地图清晰度提升，但实施口径应是：

- “新增 render scale，保持 logic scale 稳定”

而不是：

- “提高 logic size，寄希望于所有旧逻辑自然兼容”
